## HTTP 协议

HTTP（HyperText Transfer Protocol，超文本传输协议）为客户和服务器间的如何沟通提供清晰的规则，如：
- 只有用户可以制定 HTTP 请求，然后只会发送到服务器。服务器只能响应客户端的 HTTP 请求。
- 当通过 HTTP 请求一个文件时，客户必须提供这个文件的URL。
- 网络服务器必须应答每一个 HTTP 请求，至少也要回复一个错误信息。

### 状态码

- `1xx`：指示信息--表示请求已接收，继续处理
- `2xx`：成功--表示请求已被成功接收、理解、接受
- `3xx`：重定向--要完成请求必须进行更进一步的操作
- `4xx`：客户端错误--请求有语法错误或请求无法实现
- `5xx`：服务器端错误--服务器未能实现合法的请求

### Verbs

在 HTTP 协议中，GET、POST、PUT、PATCH 和 DELETE 是常用的请求方法（HTTP Verbs）

1. **GET**
	- **用途**：**获取资源**（幂等操作）
	- **特点**：
	    - 仅请求数据，不修改服务器状态。
	    - 参数通过URL传递（查询字符串，如 `?key=value`）。
	    - 可被缓存、收藏为书签。
	    - 有长度限制（因浏览器和服务器对URL长度的限制）。

2. **POST**
	- **用途**：**创建资源**或提交数据（非幂等）
	- **特点**：
	    - 向服务器提交数据（如表单、文件上传）。
	    - 数据在请求体（Body）中发送，支持多种格式（JSON、XML等）。
	    - 无长度限制。
	    - 不幂等（多次调用可能创建多个资源）。

3. **PUT**
	- **用途**：**完整更新资源**（幂等操作）
	- **特点**：
	    - 替换目标资源的全部内容（需提供完整字段）。
	    - 若资源不存在，可能创建新资源（取决于实现）。
	    - 幂等（多次调用结果相同）。

4. **PATCH**
	- **用途**：**部分更新资源**（非幂等或幂等，取决于实现）
	- **特点**：
	    - 仅更新提供的字段，其余字段保持不变。
	    - 请求体包含操作指令（如JSON Patch）。
	    - 可能非幂等（例如，若指令是“increase age by 1”）。

5. **DELETE**
	- **用途**：**删除资源**（幂等操作）
	- **特点**：
	    - 删除指定资源。
	    - 幂等（多次调用结果相同，资源仅删除一次）。

| 特性           | GET | POST | PUT | PATCH | DELETE |
| ------------ | --- | ---- | --- | ----- | ------ |
| **请求体**      | ❌   | ✅    | ✅   | ✅     | ❌      |
| **幂等性**      | ✅   | ❌    | ✅   | 可能    | ✅      |
| **安全性**      | ✅   | ❌    | ❌   | ❌     | ❌      |
| **可缓存**      | ✅   | ❌    | ❌   | ❌     | ❌      |
| **HTML表单支持** | ✅   | ✅    | ❌   | ❌     | ❌      |

#### POST 和 GET区别

- 请求参数：GET 请求参数是通过 URL 传递的，多个参数以&连接，POST 请求放在 request body 中。
- 请求缓存：GET 请求会被缓存，而 POST 请求不会，除非手动设置。
- 收藏为书签：GET 请求支持，POST 请求不支持。
- 安全性：POST 比 GET 安全，GET 请求在浏览器回退时是无害的，而 POST 会再次请求。
- 历史记录：GET 请求参数会被完整保留在浏览历史记录里，而 POST 中的参数不会被保留。
- 编码方式：GET 请求只能进行 URL 编码，而 POST 支持多种编码方式。
- 对参数的数据类型：GET 只接受 ASCII 字符，而 POST 没有限制。



## HTTPS


HTTPS 协议（HyperText Transfer Protocol over Secure Socket Layer），可以理解为 HTTP + SSL/TLS， 即 HTTP 中加入 SSL 层，HTTPS 的安全基础是 [SSL TLS](SSL%20TLS.md)，因此加密的详细内容就需要 SSL/TLS，用于安全的 HTTP 数据传输。


### 数字证书

数字证书由受信任的第三方机构（证书颁发机构，CA）签发，用于向访问者证明“我正在访问的网站就是它声称的那个网站”，并且在此基础上建立安全的加密连接。

数字证书是为了解决两个问题：
1. **身份认证**：我访问的 `www.mybank.com` 是真的银行网站，还是一个黑客伪造的“钓鱼网站”？
2. **加密通信**：我和网站之间的所有数据传输（密码、聊天内容、交易信息）都应该是密文，防止被窃听和篡改。

#### 核心内容

1. **持有者信息**：
    - 网站域名（`Common Name` 或 `Subject Alternative Name`，这是最重要的，用于匹配你访问的网址）
    - 公司/组织名称
    - 所在地等
2. **颁发者信息**：
    - 签发此证书的证书颁发机构名称
3. **公钥**：
    - 这是证书的**核心**。该公钥属于网站服务器，用于加密数据和验证签名。
4. **有效期**：
    - 证书的生效日期和过期日期。证书不是永久的，必须定期更新。
5. **数字签名**：
    - **这是证书可信的根源**。由签发证书的 CA 使用自己的**私钥**对整个证书内容进行加密签名。

#### 工作原理

当你的浏览器访问一个 HTTPS 网站时：
1. **发送证书**：网站服务器将其数字证书发送给你的浏览器。
2. **验证签名**：浏览器查看证书的“颁发者”，并使用自己信任的根证书库中对应 CA 的**公钥**，去解密证书上的**数字签名**。
3. **校验内容**：解密签名后得到一个摘要（哈希值），浏览器再用同样的算法对收到的证书内容计算一个摘要。如果两者**完全一致**，则证明：
    - 证书内容在传输过程中没有被篡改。
    - 该证书确实是由那个受信任的 CA 签发的。
4. **检查有效性**：浏览器还会检查证书是否在有效期内，以及证书上写的域名是否与你正在访问的域名完全匹配。
5. **建立安全连接**：**全部验证通过后**，浏览器才确信对方的身份。随后，它会使用证书里包含的网站的**公钥**，来协商生成一个临时的对称会话密钥，用于加密后续所有的通信数据。
