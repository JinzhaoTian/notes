限流（API Rate Limiting，速率限制）是一种通过限制系统处理请求的速率或数量来保护系统免受过载的技术。在高并发场景下，限流可以防止系统因瞬间涌入的大量请求而导致资源耗尽、响应变慢甚至崩溃。限流就像一个阀门，能够有效地控制进入系统的流量，确保系统在其处理能力范围内稳定运行。

## 目的

- **保护系统资源**：系统的资源（如 `CPU`、内存、网络带宽、数据库连接等）是有限的，当大量请求同时到达时，可能会导致资源耗尽。通过限流，可以将请求速率控制在系统能够承受的范围内，避免因资源过度消耗而导致系统故障。
- **保证服务质量**：当系统负载过高时，响应时间会显著增加，甚至出现超时现象，这将严重影响用户体验。限流可以确保系统在高并发情况下仍能保持一定的响应速度和服务质量，为用户提供稳定可靠的服务。
- **防止恶意攻击**：某些恶意攻击者可能会通过发送大量请求来对系统进行 `DDoS`（分布式拒绝服务）攻击，试图使系统瘫痪。限流可以有效地抵御这类攻击，通过限制单个 `IP` 或用户的请求速率，防止恶意请求对系统造成损害。


## 常见算法

- **令牌桶算法**：令牌桶算法是一种广泛应用的限流算法。其核心思想是系统以固定的速率生成令牌，并将令牌放入一个桶中。当请求到达时，尝试从桶中获取令牌，如果桶中有足够的令牌，则请求被允许通过；否则，请求将被拒绝或等待。令牌桶算法的特点是允许一定程度的突发流量，因为桶可以存储一定数量的令牌，当有突发请求时，可以消耗桶中积累的令牌。例如，假设系统以每秒 10 个令牌的速率生成令牌，令牌桶的容量为 100 个。如果在某一时刻，桶中有 50 个令牌，此时突然来了 80 个请求，由于桶中有足够的令牌（50 个），这 80 个请求中的 50 个可以立即通过，剩余 30 个请求则需要等待新的令牌生成或者被拒绝。
- **漏桶算法**：漏桶算法与令牌桶算法类似，但工作方式略有不同。漏桶算法将请求看作水流，请求进入一个固定容量的桶中，桶以固定的速率将请求流出（即处理请求）。如果桶已满，新的请求将被丢弃。漏桶算法的优点是能够平滑地处理请求，确保请求以稳定的速率被处理，不会出现突发流量。但其缺点是对突发流量的处理能力较弱，当突发大量请求时，可能会导致部分请求被丢弃。例如，假设漏桶的容量为 100，流出速率为每秒 10 个请求。如果在某一时刻，突然来了 150 个请求，由于桶的容量限制，只能容纳 100 个请求，剩余 50 个请求将被丢弃，而桶中的请求将以每秒 10 个的速率被逐步处理。
- **固定窗口计数器算法**：固定窗口计数器算法是一种简单直观的限流算法。它将时间划分为固定的窗口，例如每秒、每分钟等，并在每个窗口内统计请求的数量。当请求到达时，检查当前窗口内的请求数量是否超过了设定的阈值，如果超过，则拒绝该请求；否则，允许请求通过并将计数器加 1。固定窗口计数器算法的实现简单，但存在明显的临界问题。例如，假设限流阈值为每分钟 100 个请求，窗口时间为 1 分钟。如果在第 1 分钟的最后几秒和第 2 分钟的最初几秒内，分别有 90 个请求到达，虽然在每个单独的 1 分钟窗口内请求数量都未超过阈值，但在这两个窗口的重叠时间段内，请求总数达到了 180 个，已经超过了限流阈值，可能导致系统过载。
- **滑动窗口计数器算法**：滑动窗口计数器算法是对固定窗口计数器算法的改进，它通过将大的时间窗口划分为多个小的子窗口，每个子窗口独立统计请求数量，并随着时间的推移滑动窗口，从而更精确地控制请求速率。滑动窗口计数器算法能够有效解决固定窗口计数器算法的临界问题，提高限流的准确性。例如，将 1 分钟的时间窗口划分为 60 个 1 秒的子窗口，每个子窗口内统计请求数量。当时间从第 1 秒滑动到第 2 秒时，第 1 秒的子窗口统计数据被移除，同时加入第 61 秒的子窗口统计数据。这样，无论请求在时间上如何分布，都能更准确地进行限流控制。



## 应用场景

限流在各种高并发场景中都有广泛的应用，以下是一些常见的应用场景：
- **秒杀活动**：在电商平台的秒杀活动中，由于参与人数众多，瞬间会产生大量的请求。通过限流可以控制每秒进入秒杀系统的请求数量，避免系统因高并发请求而崩溃，同时保证每个用户都有公平参与秒杀的机会。例如，可以根据系统的处理能力，设置每秒只允许 1000 个请求进入秒杀系统，超出部分的请求将被限流提示用户稍后再试。
- **API 接口访问**：对于一些提供对外 API 服务的平台，为了保护自身系统的稳定性和资源，需要对 API 接口的调用频率进行限制。例如，限制每个用户每分钟最多调用某个 API 接口 100 次，超出次数的调用将返回错误信息，提示用户调用频率过高。这样可以防止个别用户或应用程序滥用 API 接口，对平台造成过大的压力。
- **登录注册**：在用户登录和注册功能中，为了防止恶意用户通过暴力破解密码或频繁注册账号进行攻击，可以对单个 IP 地址或用户的登录注册请求频率进行限流。例如，限制每个 IP 地址每分钟最多进行 5 次登录尝试或 10 次注册操作，超出限制的请求将被暂时封禁一段时间，以提高系统的安全性。
- **视频直播**：在视频直播场景中，为了保证直播的流畅性和稳定性，需要对观众的并发访问数量进行限流。例如，根据服务器的带宽和处理能力，限制每个直播间同时在线观看的人数不超过 10000 人，当人数达到上限时，新的观众将无法进入直播间，只能等待其他观众离开后才有机会进入。



## 实现方式

限流可以在不同的层次进行实现，常见的实现方式包括：
- **应用层限流**：应用层限流是在应用程序内部实现的限流逻辑，通常可以通过编写代码来实现。例如，在 Java 应用中，可以使用 Guava 库中的 RateLimiter 类来实现令牌桶算法的限流功能。在应用层实现限流的优点是可以根据业务需求进行灵活定制，能够精确控制每个业务模块的限流策略。但其缺点是如果应用程序部署在多个服务器上，应用层限流只能对单个服务器上的请求进行限制，无法实现全局统一的限流。
- **网关层限流**：网关作为系统的入口，是进行限流的理想位置。通过在网关层设置限流规则，可以对所有进入系统的请求进行统一的流量控制。常见的网关软件如 Nginx、Kong 等都提供了强大的限流功能。例如，Nginx 可以使用 limit_req_zone 指令来实现基于令牌桶算法的速率限流，使用 limit_conn_zone 指令来实现基于并发连接数的限流。网关层限流的优点是可以对整个系统的流量进行集中管理和控制，并且可以很方便地对不同的服务或接口设置不同的限流策略。同时，由于网关通常具有较高的性能和并发处理能力，能够承受大量的请求流量，因此在网关层进行限流不会对系统的性能产生较大影响。
- **中间件限流**：除了应用层和网关层，还可以利用中间件来实现限流功能。例如，使用 Redis 作为分布式缓存中间件时，可以结合 Lua 脚本来实现基于 Redis 的限流。通过在 Redis 中维护一个计数器，每次请求到达时，通过 Lua 脚本原子性地增加计数器的值，并与限流阈值进行比较，从而实现限流控制。中间件限流的优点是可以利用中间。
