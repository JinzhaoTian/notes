在微服务出现线上问题时，进行调试和捕捉错误需要谨慎、高效且尽量避免影响线上用户，直接附加调试器到生产环境通常不是最佳实践（风险高、影响性能、安全性差）。

**核心原则**
1. **最小化影响：** 优先使用非侵入性监控和日志。
2. **快速恢复：** 优先考虑缓解措施（回滚、重启、限流、熔断）。
3. **事后分析：** 在安全的环境（非生产）中分析根本原因。
4. **自动化：** 尽可能依赖自动化工具收集数据。


## 实时监控与错误捕捉（第一道防线）

1. **集中式日志 (Centralized Logging - 必备):**
    - **工具:** ELK Stack (Elasticsearch, Logstash, Kibana), Seq, Splunk, Azure Application Insights, AWS CloudWatch Logs。
    - **关键实践:**
        - **结构化日志:** 使用 `Serilog`, `NLog` 等库输出结构化日志 (JSON)。包含关键信息：时间戳、日志级别、消息、异常堆栈、请求ID、用户ID（脱敏后）、服务名、机器名、线程ID、相关业务ID。
            
        - **记录上下文:** 确保日志包含足够上下文（如 HTTP 请求方法、路径、查询字符串 - 注意敏感信息过滤；数据库操作的关键参数）。
            
        - **错误日志:** 使用 `ILogger` 的 `LogError` 或 `LogCritical` 记录捕获和未捕获的异常，**务必记录完整的异常堆栈**。
            
        - **关联ID:** 在请求入口（Middleware）生成唯一 `CorrelationId` 并贯穿整个调用链（包括对其他服务的调用），在日志、错误报告、追踪中都带上它。使用 `Activity.Current?.TraceId` 或自定义 ID。
            
        - **健康检查日志:** 记录健康检查失败的原因。
            
        - **实时查询与告警:** 配置日志平台对 `ERROR`/`FATAL` 级别的日志进行实时告警（邮件、Slack、PagerDuty）。

2. **Application Performance Monitoring (APM - 强烈推荐):**
    - **工具:** Azure Application Insights, Datadog, New Relic, Dynatrace, Elastic APM, OpenTelemetry (OTel) based solutions.
    - **功能:**
        - **自动异常捕获:** 自动捕获并报告未处理的异常，包含堆栈、请求上下文、关联ID。
        - **请求跟踪:** 端到端追踪请求在微服务内部的流转（Controller -> Service -> Repository -> DB）以及跨服务调用（HTTP, gRPC, Message Queue）。可视化调用链路，定位性能瓶颈和错误点。
        - **依赖监控:** 监控外部依赖（数据库、缓存、其他微服务、外部API）的调用成功率和性能。
        - **性能指标:** 实时监控 CPU、内存、GC、HTTP 请求率/延迟/错误率、数据库查询性能等。
        - **实时仪表盘与告警:** 基于性能指标和错误率设置告警。

3. **健康检查端点 (Health Checks - 必备):**
    - 检查关键依赖状态（数据库连接、缓存连接、下游服务可达性、磁盘空间、自定义业务健康）。
    - 暴露 `/health` 或 `/hc` 端点供监控系统（K8s Liveness/Readiness Probe, 负载均衡器, APM）轮询。
    - 当健康检查失败时，确保日志中有明确原因。

4. **分布式追踪 (Distributed Tracing - 强烈推荐):**
    - **标准:** OpenTelemetry (OTel) 是当前事实标准。
    - **实现:**
        - 在应用中集成 OTel SDK (`OpenTelemetry.Exporter.*`, `OpenTelemetry.Instrumentation.*` NuGet包)。
        - 自动或手动创建 `Span` 来标记操作（HTTP 请求、数据库调用、关键业务逻辑）。
        - 通过 `W3C Trace Context` 标准传播追踪上下文 (TraceId, SpanId)。
        - 导出追踪数据到后端如 [Jaeger](../../DevOps/Monitoring/Jaeger.md)，Zipkin，Azure Monitor，Grafana Tempo。
    - **作用:** 当请求涉及多个服务时，通过 `TraceId` 将所有相关日志、错误、性能数据串联起来，构建完整的调用链路图，是诊断复杂分布式问题的利器。


## 诊断工具与深入排查（当监控和日志不够时）

1. **分析日志和 APM 数据:**
    - 这是**最常用、最安全**的方式。利用日志平台的搜索、聚合、关联功能，结合 APM 的调用链和错误详情，定位问题根源。
    - **关键点:** 利用 `CorrelationId`/`TraceId` 串联所有相关信息。

2. **Dump 文件分析 (捕获进程快照):**
    - **场景:** 诊断内存泄漏、死锁、CPU 100%、进程崩溃、线程阻塞等高难度问题。
    - **捕获方式:**
        - **自动捕获:** 配置操作系统或容器平台在进程崩溃时自动生成 Dump 
	        - Windows: WER
	        - Linux: `core_pattern`
	        - Docker: `--cap-add=SYS_PTRACE` + `dotnet-dump`/`createdump`
	        - K8s: `kubectl debug`
	        - Azure App Service 有内置诊断工具。
        - **手动捕获 (谨慎使用！):**
            - **Linux:**
                - `dotnet-dump collect -p` - 最推荐，轻量级，跨平台。
                - `gcore` - 传统方式。
            - **Windows:**
                - Task Manager (右键进程 -> "Create Dump File")。
                - `procdump -ma` (Sysinternals 工具)。
                - DebugDiag。
    - **分析工具:**
        - **Visual Studio / VS Code:** 强大的分析工具，支持加载 Dump 文件。
        - **dotnet-dump analyze:** 命令行工具，功能强大 (`clrstack`, `dumpheap`, `gcroot`, `syncblk` 等)。
        - **WinDbg / CDB (Debugging Tools for Windows):** 配合 SOS/SOSEX 扩展。
    - **关键点:** 捕获 Dump 通常需要重启进程或影响性能，**仅在必要时且在运维配合下进行**。分析通常在**非生产环境**进行。

3. **Metrics 和 Profiling (性能计数器):**
    - **工具:** `dotnet-counters` (CLI), Prometheus + Grafana, APM 内置指标。
    - **监控:** GC 频率/耗时、线程池状态、锁竞争、HTTP 活动、JIT 编译等运行时关键指标。
    - **场景:** 持续监控性能基线，或在出现性能问题时实时观察指标变化定位瓶颈区域。`dotnet-counters` 可以实时监控。

4. **临时性诊断日志 (谨慎增加):**
    - 如果现有日志不足，可以**临时**修改日志级别（例如，将某个特定命名空间的日志级别从 `Information` 提升到 `Debug` 或 `Trace`）。
    - **实现方式:**
        - **配置中心:** 如果使用配置中心（如 Consul, Apollo, Azure App Configuration），动态调整 `appsettings.json` 的 `Logging:LogLevel` 部分并推送到服务。
        - **环境变量:** 通过容器编排平台（K8s）或部署工具临时设置环境变量 `ASPNETCORE_LOGLEVEL` 或 `Logging__LogLevel__Microsoft=Debug`。
        - **管理端点 (谨慎暴露！):** 实现自定义管理端点（需严格认证授权）来动态修改日志级别。
    - **关键点:** 增加日志级别会显著增加日志量和性能开销，**只能短暂开启**，问题解决后立即恢复。避免记录敏感信息。

5. **远程调试 (Last Resort - 非常谨慎！):**
    - **工具:** Visual Studio Remote Debugger。
    - **场景:** 当所有非侵入性手段都无法定位极其复杂或难以复现的问题时。
    - **巨大风险:** 严重影响目标进程性能，可能导致服务停滞或超时；安全风险（调试端口暴露）；需要生产环境网络可达和权限。
    - **强烈建议:**
        - 仅在维护窗口期或流量极低时进行。
        - 严格限制访问权限（IP 白名单、VPN）。
        - 尽可能快地连接、捕获所需信息后立即断开。
        - **优先考虑捕获 Dump 文件在本地分析，这比远程调试安全得多。**


## 错误处理最佳实践（预防与改进）

1. **全局异常处理:**
    - 使用 `UseExceptionHandler` Middleware 捕获管道中未处理的异常。
    - 自定义 `ExceptionHandler` 返回结构化的错误响应（包含 `CorrelationId`），**同时确保记录详细错误日志**。
    - 避免在生产环境中返回原始堆栈给客户端（安全考虑）。

2. **使用 ProblemDetails:** 遵循 IETF RFC 7807 标准，通过 `AddProblemDetails()` 返回一致的错误信息格式。

3. **防御性编程与验证:**
    - 输入模型验证 (`ModelState.IsValid`)。
    - 参数校验（使用 `Guard Clauses` 或类似库）。
    - 处理 `null` 引用。
    - 对关键操作使用 `try-catch`，**但只捕获你能处理的异常**，否则抛出让全局处理器处理。在 `catch` 块中记录**有意义的上下文信息**。

4. **断路器与重试:** 使用 `Polly` 等库处理对不稳定外部依赖的调用，防止级联故障。

5. **压力测试与混沌工程:** 在预生产环境模拟故障，提前发现弱点。

6. **完善日志与监控:** 持续优化日志内容和结构，配置关键指标告警。


## 线上调试流程总结

1. **告警触发:** APM 或日志告警通知出现问题（高错误率、性能下降、健康检查失败）。
2. **快速缓解:** 评估影响，优先采取恢复措施（重启实例、回滚版本、扩容、启用熔断/降级）。
3. **信息收集:**
    - 查看集中式日志，按 `CorrelationId`/`TraceId` 或错误特征搜索相关请求。
    - 查看 APM 仪表盘：错误详情、调用链路、依赖性能、主机指标。
    - 查看分布式追踪链路图。
4. **初步分析:** 结合日志、错误堆栈、调用链、指标，判断问题大致方向（代码缺陷？配置错误？依赖故障？资源不足？）
5. **深入诊断 (如果需要):**
    - 如果日志不足：**临时**提升相关日志级别（通过配置中心/环境变量）。
    - 如果怀疑运行时问题（内存、线程）：捕获 **Dump 文件**，下载到本地分析。
    - 如果怀疑性能瓶颈：使用 `dotnet-counters` 或 APM 性能剖析器实时观察。
6. **定位根因:** 分析收集到的数据，确定根本原因。
7. **修复与验证:** 在开发或测试环境修复问题，充分测试。
8. **安全部署:** 将修复部署到生产环境。
9. **复盘 (Post-mortem):** 记录事故详情、原因、处理过程、经验教训、改进措施（如完善日志/监控/告警/容错机制）。


## 重要提醒

- **安全第一:** 任何线上诊断操作都必须考虑安全策略和最小权限原则。避免在生产环境暴露调试端口或未授权访问管理端点。
- **性能影响:** 日志级别、APM 采样率、诊断工具（尤其是 Dump 和 Profiler）都可能影响服务性能，需权衡利弊。
- **自动化优先:** 尽可能让监控、日志、告警、健康检查、Dump 自动捕获等机制自动化，减少人工介入的紧迫性和风险。
- **非生产环境重现:** 终极目标是能在预生产环境稳定重现问题，这是最安全、最高效的调试方式。
