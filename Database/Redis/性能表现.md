> 基于 2020 年数据测算。

在讨论 Redis 的性能表现时，核心指标是[QPS](../../Backend/系统指标/QPS.md)和[TPS](../../Backend/系统指标/TPS.md)，主要取决于以下几个因素：
1. **网络带宽**：网络带宽和延迟会直接影响 Redis 的性能。可以通过 Gbit/s 来粗略估算系统所需带宽，例如：若每秒处理 100,000 个请求，每个请求携带 4KB 数据，则大约需要 3.2 Gbit/s 的带宽。因此这在 10 Gbit/s 的网络环境下是可行的，但在 1Gbit/s 的网络中就会成为瓶颈。在很多实际场景中，Redis的性能瓶颈并不在于CPU，而在于网络带宽。因此，在部署高吞吐量的 Redis 实例时，建议使用 10 Gbit/s 的网卡，或者使用多块 1Gbit/s 的网卡并通过 TCP/IP 绑定来提高带宽。
2. **CPU 配置**：Redis 是单线程的（从客户端操作的角度来看），因此更适合使用主频高、缓存大的 CPU，而不是核心数多的 CPU。在这方面，Intel 的处理器通常表现优于其他品牌，如果你有多颗 CPU，建议在同一台机器上运行多个 Redis 实例，以充分利用多核资源。
3. **内存**：对于小对象（10 KB 以下），RAM 的速度和内存带宽影响不大；但当对象大小超过 10 KB 时，内存性能的影响就可能变得明显。不过，购买昂贵的高端内存并不是一项性价比很高的投资。因此在选择内存配置时需要在性能和成本之间权衡。
4. **数据大小**：使用的数据结构和数据大小（如上所示）也会影响性能。与字符串相比，有序集合（sortedset）的 QPS 和 TPS 通常会更低。
5. **运行载体**：相比在虚拟机中运行，Redis 在使用本地磁盘的物理机上运行时性能更好，因为虚拟化层可能引入额外开销，影响整体响应速度和处理能力。
6. **流水线命令的使用**：当通过以太网访问 Redis 时，使用流水线技术可以显著提升性能，尤其在单个命令的数据量控制在以太网数据包大小（约 1500 字节）以内时效果尤为明显。实际上，无论处理的是 10 字节、100 字节还是 1000 字节的请求，吞吐量几乎没有区别。流水线的核心在于将多个 Redis 命令批量打包发送，从而减少网络往返带来的延迟开销。
7. **磁盘持久化**：启用 AOF（追加文件日志）和快照（Snapshotting）功能可能会对性能产生影响。只有当确定需要数据持久性保障，或者需要将 Redis 与具备事务功能的数据存储进行对比时，才建议开启这些功能。
8. **连接数**：在高性能场景中，客户端连接数也是 Redis 性能的一个关键因素。得益于 epoll（Linux）或 kqueue（BSD/macOS）等高效的事件驱动模型，Redis 的事件循环具备很好的可扩展性。在超过 6000 个连接的测试环境中，Redis 依然能够维持 50,000 QPS 的处理能力。但根据实际经验，一个 Redis 实例在连接数达到 30,000 时，其吞吐量可能只有连接数为 100 时的一半左右。Redis 的 QPS 和 TPS 粗略估计可达 200,000 次/秒。在部署 Redis 集群的情况下，这一数值甚至可以扩展到 500,000 次/秒或更高。需要注意，读取 QPS 和写入 TPS 的性能大致处于同一水平。

### QPS 典型范围

#### 单节点 Redis

简单命令，如 SET/GET

|场景|QPS 范围|说明|
|---|---|---|
|**单线程基准测试**（`redis-benchmark`，本地环回）|80,000 - 120,000|简单命令（如 `SET`/`GET`），无持久化，低延迟网络|
|**生产环境（千兆网络）**|50,000 - 80,000|受网络延迟、客户端库效率影响|
|**生产环境（复杂命令）**|10,000 - 50,000|如 `HGETALL`、`ZRANGE` 等操作大 Key|
|**云服务（如 AWS ElastiCache）**|30,000 - 100,000|取决于实例规格（如 `cache.m6g.xlarge`）|

#### 集群模式（线性扩展）

- 每增加一个分片，QPS 可近似线性增长（如 3 分片集群可达 150,000 - 300,000 QPS）。


### TPS 典型范围

Redis 的事务（`MULTI`/`EXEC`）性能取决于事务内命令的数量和类型：

|场景|TPS 范围|说明|
|---|---|---|
|**简单事务（1-5 个命令）**|20,000 - 50,000|如 `MULTI; SET a 1; SET b 2; EXEC`|
|**长事务（10+ 命令）**|5,000 - 15,000|命令越多，阻塞时间越长|
|**含复杂命令的事务**|1,000 - 5,000|如包含 `ZUNIONSTORE`、`LUA` 脚本|

> **注意**：Redis 事务是弱事务（无回滚），实际业务中更常用 **LUA 脚本**（原子性更强，但性能更低）。


### 不同数据结构的 QPS 对比

|数据结构|典型操作|QPS 范围（单节点）|
|---|---|---|
|**String**|`SET`/`GET`|80,000 - 120,000|
|**Hash**|`HSET`/`HGET`|50,000 - 100,000|
|**List**|`LPUSH`/`LPOP`|40,000 - 80,000|
|**Set**|`SADD`/`SMEMBERS`|30,000 - 60,000|
|**Sorted Set**|`ZADD`/`ZRANGE`|20,000 - 50,000|
