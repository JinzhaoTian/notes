## 学习路线

先推荐 HKUDS 的 [HKUDS/CLI-Anything](https://github.com/HKUDS/CLI-Anything) 。
1. **概念**：Agent 应用开发的本质 = 传统后端 + LLM 能力 + 自动化工作流，所以工程化永远躲不开后端基建，核心特点是接受用户输入，理解意图，调用 LLM 进行推理决策，执行工具，返回结构化结果并应用。
2. **Python 基础与异步编程**：Agent 应用要处理大量的 IO 密集型操作，落地是需要对性能进行提升的，这里的核心是 async 事件循环/协程、并发控制（限流、批量执行）、线程池、类型注解与数据模型。会应用于并发调用、批量上传、流式输出场景下（一般都会有这样的需求）
3. **Web 框架**：FastAPI（必学），Agent 开发的必学框架，很适配（原生异步支持）。核心点是路由设计 / APIRouter、依赖注入、请求验证与响应模型、Websocket（流式输出）。
4. **数据存储**：数据在 Agent 项目中是非常重要的，因为需要持久化会话历史、任务状态、知识库数据，这里的重点在关系型数据库（SQLAIchemy ORM）、Redis（缓存）。
5. **异步任务队列**：Celery，因为 Agent 任务都比较长，需要进行异步执行，避免阻塞，Celery 的核心是 Broker + Worker + Backend、任务的定义和调度、重试与超时处理、任务状态追踪，通常和 Redis 组合。
6. LLM + Prompt + Agent 架构 **Pipeline 编排**：这一块没什么好说的 Agent 开发与工程化学习路线的必经之路。

## 技术原理

### Coding Agent Harness 

Harness 通常指一套评测/训练框架，用来让 Coding Agent 在受控环境中生成代码、执行代码、获取反馈。

一个典型的 Coding Agent Harness 包含：
- 任务集：例如修 bug、写函数、跑测试用例；
- 沙箱执行器：Docker / gVisor / Firecracker 等隔离环境；
- 测试 runner：把模型生成的代码/命令送进沙箱，执行测试并收集结果；
- 反馈生成：把 stdout/stderr/退出码/测试结果拼成 prompt 返回给模型；
- 失败处理：超时、资源限制、解析失败、沙箱启动失败等。

### 沙箱执行

**关键点**：
- 隔离性：限制网络、文件系统、CPU、内存、执行时间；
- 可恢复性：执行失败后能否重新拉起；
- 并发性：多个任务同时执行时，沙箱的调度、冷启动、资源争抢；
- 安全性：防止模型生成恶意命令逃逸。

真实做过沙箱的人，通常会提到：
- 容器冷启动延迟；
- 多个沙箱并发时 I/O 争抢；
- 沙箱内命令超时与重试；
- 资源限制导致 OOM；
- 文件系统写满；
- 沙箱状态污染导致后续任务受影响。

如果只能讲“加了重试”，大概率没有真正设计过 Harness。

### 失败处理与重试机制

失败处理不是简单“失败就重试”。真实系统里需要区分：
- **可重试失败**：网络超时、沙箱启动失败、工具返回格式错误、临时资源不足；
- **不可重试失败**：语法错误、逻辑错误、测试用例失败、安全违规；
- **有副作用失败**：已经写入文件/调用了外部 API，重试可能造成重复操作。

常见的重试策略：
- 指数退避；
- 最大重试次数；
- 仅对特定错误码/异常类型重试；
- 重试前重置状态；
- 重试后改变策略，例如换一个工具参数或让模型解释错误。

**面试官追问“什么样的失败会重试”**，就是看你有没有做过错误分类和重试策略设计。

### 模型死循环 / 反复调用同一工具

这是 Agent 系统中最常见的问题之一。

**表现**：
- 模型连续调用同一个工具，参数不变；
- 模型在几个工具之间来回切换，但状态不推进；
- 模型输出空谈，不调用工具，或调用无效工具；
- 轨迹步数不断增加，但任务没有进展。

**原因**：
- 环境返回的信息不够明确；
- 模型没有利用历史信息；
- 工具定义太相似，模型分不清；
- 策略退化，尤其在 RL 训练后期；
- Reward 设计诱导模型重复某个高奖励动作。

**解决方案**：
- 设置最大步数 / 最大 token 预算；
- 动作去重：记录 `(tool_name, args_hash)`，连续重复超过阈值则终止或强制换动作；
- 检测状态无变化：如果环境状态没有变化，则终止；
- 给重复动作惩罚：在 RL 奖励中加重复惩罚；
- 在 prompt 中明确禁止重复调用；
- 使用语法约束/工具调用 schema，降低无效调用概率；
- 训练时加入 “反复调用同一工具” 的负样本。

如果候选人没遇到过死循环，说明他可能没有跑过真实长任务，或者没有观察过 agent 的 rollout。

### Agentic RL 与 GRPO

Agentic RL 是指用强化学习训练 LLM 智能体，让它在多轮交互中学会使用工具完成目标。

与普通 SFT 的区别：
- 不是简单模仿人类，而是根据环境反馈优化策略；
- 奖励来自环境：最终成功与否、中间步骤是否合理；
- 需要管理 rollout、优势估计、策略更新。

**GRPO：Group Relative Policy Optimization**

GRPO 是 DeepSeek 提出的 PPO 改进版，核心是**去掉价值函数 critic**，用同一 prompt 采样的一组输出的相对奖励作为基线。

简化目标：

$$
J_{GRPO}(\theta) = E_{q,\{o_i\}^G_{i=1}}\frac{1}{G} \sum^G_{i=1}min⁡(\frac{π_θ(o_i∣q)}{π_{θ_{old}}(o_i∣q)}\hat{A}_i,clip(\frac{πθ(oi∣q)}{πθold(oi∣q)},1−ϵ,1+ϵ)\hat{A}_i)−βD_{KL}(π_θ∥π_{ref})
$$

其中：
- 对每个问题 $q$ 采样 $G$ 条轨迹；
- 用组内奖励的标准化作为优势 $\hat{A}_i= \frac{r_i−mean(r)}{std(r)}$
- clip 限制策略更新幅度；
- KL 惩罚防止策略偏离参考模型太远。

**多轮工具调用训练时，GRPO 的难点**：
- 轨迹长度变化大，序列可能非常长；
- 奖励稀疏：只有最终结果对错；
- 中间工具调用可能格式非法，导致 rollout 中断；
- 组内采样成本高：同一个任务要跑 G 条轨迹，每条都要真实执行工具；
- 策略容易塌缩或 reward hacking。

### 结果奖励 vs 过程奖励

- **结果奖励**：只给最终状态一个奖励，例如测试通过 = 1，失败 = 0；
- **过程奖励**：对中间步骤也给出奖励，例如每一步工具调用是否合理、是否接近目标。

**过程奖励的引入是为了缓解稀疏奖励**，但也很容易导致 reward hacking。

**Reward Hacking 抑制：**

Reward Hacking 指模型通过非预期方式获得高奖励，而不是真正学会任务。

常见例子：
- 反复调用某个简单工具刷过程奖励；
- 输出很长但无意义的内容，利用长度奖励；
- 生成格式正确但内容错误的答案；
- 利用奖励模型漏洞，输出高奖励模板；
- 重复输出某个高分短语。

**抑制方法**：
- 以结果奖励为主，过程奖励只作为弱信号；
- 加入 KL 惩罚，限制策略偏离参考模型；
- 对重复动作、无效动作加惩罚；
- 长度惩罚；
- 奖励归一化；
- 人工审计高频高奖励模式；
- 动态奖励模型 / 对抗训练；
- 减少易被 hack 的中间奖励，或使用规则型过程奖励，而不是可学习的奖励模型。

如果候选人不能具体说出“怎么抑制 reward hacking”，说明他可能没有遇到过模型刷分，或者根本没有监控奖励分布。


### 多轮 Trajectory 截断长度

在 RL 训练中，每条 rollout 轨迹都需要有一个最大长度限制。这个限制会直接影响：
- 显存占用；
- 训练速度；
- 是否学得会长程任务；
- 是否浪费大量计算在无效轨迹上。

**截断长度怎么定？**

- 统计真实任务中轨迹长度的分布，取 p95/p99；
- 根据显存和训练时间预算反推；
- 根据任务复杂度：简单任务短，复杂任务长；
- 根据模型上下文长度上限；
- 观察训练过程中平均轨迹长度变化，动态调整。

**截断带来的问题**：
- 如果截断太短，很多成功轨迹会被砍掉，模型学不到完整策略；
- 如果截断太长，显存爆炸，无效轨迹占用大量资源；
- 被截断的轨迹要标记为“未完成”，不能直接当失败样本，否则会误导训练。

真实做过的人会提到：

> 我先统计了 rollout 步数分布，发现 90% 任务在 20 步内完成，但有些任务会跑到 50 步以上。我一开始设 max_steps=30，发现长任务成功率掉了很多。后来改成动态截断：先设 40，再对超过 40 的轨迹做 padding + mask，并且给截断样本一个特殊处理。

而不是：

> 截断长度就是设了个 512。

### Policy Collapse 与 Rollout 排查

**Policy Collapse** 是 RL 训练中常见灾难：策略突然退化，输出变得单一、重复、无意义，奖励下降但熵也下降。

常见信号：
- 策略熵急剧下降；
- 输出多样性变少，甚至所有输出都一样；
- KL 散度爆炸；
- reward 均值/方差异常；
- 轨迹长度异常缩短或变长；
- 工具调用模式变得单一。

**怎么排查 Rollout？**

- 看 rollout 的 token 分布：是否大量重复 token；
- 看策略熵：是否趋近于 0；
- 看 KL：是否相对参考模型偏离过大；
- 看 reward 分布：是否塌缩到某个固定值；
- 看 clip 比例：PPO/GRPO 的 clip 比例是否过高；
- 看梯度 norm：是否突然增大；
- 看步数长度分布：是否异常；
- 看采样温度是否过低；
- 看奖励设计是否有漏洞。

**应对措施：**

- 降低学习率；
- 增大 KL 惩罚系数；
- 加入熵正则；
- 降低 clip 范围；
- 调整采样温度；
- 奖励归一化；
- 回滚 checkpoint；
- 检查是否有奖励被 hack。

如果候选人没听过“策略熵”“KL 爆炸”“clip 比例”，那基本可以判断他没有真正训练过 RL。

### 长 Trajectory 显存溢出 / 解析失败

这是两个非常典型的工程 bug。

#### 长 Trajectory 显存溢出

在训练中，长轨迹意味着序列很长，显存占用包括：

- KV cache；
- 激活值；
- 梯度；
- 优化器状态。

当轨迹长度超过预设时，很容易 OOM。

解决方案：

- 梯度累积；
- 重计算 / checkpoint；
- 截断轨迹；
- 减少 batch size；
- 使用 FlashAttention / vLLM 等；
- 将 rollout 和训练分离；
- 使用 CPU offload；
- 限制最大 token 数；
- 对长轨迹做采样截断。

#### 解析失败

Agent 输出工具调用时，可能是非结构化文本，例如：

- JSON 格式错误；
- 工具名拼错；
- 参数缺失；
- 多余文本；
- 多个工具调用混在一起。

解决方案：

- 使用 function calling 的 schema 约束；
- 使用 grammar decoding / constrained decoding；
- 在 prompt 中给 few-shot；
- 写鲁棒的解析器；
- 解析失败时重试，或让模型重写；
- 解析失败给负奖励或终止轨迹。

如果候选人只能讲“环境变量配置错误”，说明他没有处理过这些高频、高价值的 bug。


### 消融实验与指标异常

真实 RL 项目里，你不可能“调参效果都挺好”。很多时候你改了一个超参，成功率反而下降。这时候需要做消融。

**消融实验的原则：**

- 一次只改一个变量；
- 记录改动前后的指标：成功率、平均步数、奖励均值、熵、KL、显存、延迟；
- 用多个随机种子；
- 对比 baselines；
- 分析指标下降的原因：是奖励设计问题、数据问题、优化器问题，还是策略退化。

**面试官问“有没有哪次改动之后效果反而变差了”**，是看你有没有做过失败分析。如果你连一次失败都没有，要么是项目太简单，要么是你没有认真观察。

### 沙箱并发与延迟瓶颈

如果重做项目，只想到“换更大的 BaseModel”，说明你没有分析过系统瓶颈。

真实沙箱 Harness 的瓶颈通常不在模型大小，而在：

- 沙箱冷启动延迟；
- 并发沙箱数量限制；
- 文件系统 I/O 瓶颈；
- 网络请求阻塞；
- 测试运行时间过长；
- 资源争抢导致超时；
- 容器镜像拉取慢；
- 内存/CPU 配额不足；
- 调度器效率低。

优化方向：

- 沙箱池化：预创建容器，复用；
- 异步执行：工具调用与测试并行；
- 限制并发数，排队调度；
- 使用轻量级隔离：gVisor / Firecracker / Wasm；
- 缓存依赖和环境；
- 对超时任务提前 kill；
- 优化反馈生成，减少 token 数。

如果你能讲出“我 profiling 后发现 40% 时间花在容器冷启动上，后来做了沙箱池化，p95 延迟从 12s 降到 4s”，这个回答就非常有说服力。
