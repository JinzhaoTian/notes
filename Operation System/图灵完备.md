图灵完备是计算机科学里用来衡量一个计算系统“通用计算能力”的核心概念，即**如果一个系统能够模拟任意一台[图灵机](图灵机.md)，那它就是图灵完备的**。这意味着，只要给它足够的时间和存储空间，它就能解决所有“可计算”的问题也就是任何能够用算法描述的问题。

一个系统要成为图灵完备，通常需要满足两个关键能力：
- **条件分支**：能根据当前数据决定下一步做什么（比如 `if`/`else`）。
- **能够重复执行并修改内存**：有某种形式的循环或跳转（比如 `while`、`goto`、递归），并且能够读写一个理论上可以无限增长的存储空间。

现实里，由于物理内存有限，没有任何实际系统是“严格”图灵完备的（因为纸带不是无限的），但在理论上，我们忽略内存限制，只要它的指令集或规则具备**模拟任何图灵机**的能力，就称其为图灵完备。

## 常见的图灵完备系统

1. 几乎所有通用编程语言：
	- C++
	- Java
	- Python
	- JavaScript 
	- 等等...
2. 汇编语言、甚至某些极为精简的指令集（比如 Brainfuck）。
3. 很多让人意想不到的东西：
	- Excel 的公式（有足够多单元格的话）
	- Minecraft 的红石电路
	- 《魔法风云会》卡牌游戏规则
	- 部分 HTML+CSS 的特定组合（事实上需要借助用户交互）
	- 一些汇编器宏系统等

相比之下，**非图灵完备**的语言则故意限制了计算能力，比如：
1. 纯 HTML、CSS（不考虑最新怪招）只能表达结构样式，不会计算。
2. 正则表达式。
3. 很多配置语言（如 JSON、YAML）、某些类型检查或查询语言（如 SQL 的基础部分，但加上递归 CTE 后常常变成图灵完备）。

## 重要性

图灵完备代表了一个系统计算能力的上限。如果你设计一门新语言并证明它是图灵完备的，说明它原则上可以做任何计算。

但图灵完备也带来了代价：**停机问题**。对于一个图灵完备的系统，你无法写出一个通用程序来判定任意程序是否会最终停止，这直接关联到软件验证的极限。


## 利弊

图灵完备本身是一个**中性属性**，说它是好是坏，完全取决于你用在**什么地方**和**目的是什么**。图灵完备意味着一个系统能计算任何可计算函数，也就不可避免地引入了**停机问题**——你无法在事先总是判断一段代码（或类型计算）是会结束，还是会永远跑下去。


### 对于通用编程语言：绝对的好

对于 Java、Python、JavaScript、C++ 这种通用语言，**图灵完备是必须的，是底线**。

- 如果一门语言不是图灵完备的，就意味着存在一些算法它永远写不出来（比如复杂的循环、递归业务逻辑）。
- 没有人会接受“对不起，这个功能用我们的语言实现不了，因为它不是图灵完备的”。

在这个语境下，图灵完备是**绝对的好**，没有它，通用语言就失去了存在的意义。

### 对于非通用语言 / DSL / 配置：常常是坏的

如果目标是**配置语言、标记语言、样式语言、查询语言**，那么图灵完备常常被视为一个**潜在缺陷或设计失误**。

**典型例子**：
- **HTML / CSS** 不是图灵完备的（CSS 后来加入了某些能力，有争议，但本质上是声明式的），这使得浏览器可以安全、并行地解析渲染，而不用担心死循环。
- **纯 YAML / JSON / XML** 不是图灵完备的，因此是纯粹的数据，可预测、可静态分析、无副作用。
- **SQL（标准）** 图灵完备性一直有争议，但很多方言加入了循环/递归，使其图灵完备，随之而来的就是可能写出跑不出的查询。

一旦这些东西变得图灵完备，就会出现几个严重问题：

- **不可预测**：无法保证配置解析会终止（停机问题）。
- **安全风险**：配置文件可能变成攻击载体（比如无限循环让解析器挂掉）。
- **工具困难**：静态分析、验证、IDE 功能（如“查找所有引用”）变得极其复杂甚至不可能。
- **可维护性崩塌**：人们开始在配置文件里写复杂业务逻辑，配置文件不再是配置，而是未经测试的散装代码。

所以，对于**声明式、数据描述**为目的的系统，图灵完备**常常是“坏”的**。
