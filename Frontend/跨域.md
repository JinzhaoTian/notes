跨域是指浏览器出于安全考虑，限制一个“源”的网页去访问另一个“源”的资源。如果两个页面的协议、域名或端口任意一项不同，就构成了跨域。

## 同源策略

浏览器的核心安全机制叫做**同源策略**，一个“源”由三部分组成：
- **协议**：如 `http` 或 `https`
- **域名**：如 `www.example.com`
- **端口**：如 `80`（默认）、`443` 等 

只要这三者**完全相同**，才算是“同源”。

| 当前页面源               | 要请求的源               | 是否同源 | 原因    |
| ------------------- | ------------------- | ---- | ----- |
| `http://a.com`      | `http://a.com/test` | ✅ 同源 | 仅路径不同 |
| `http://a.com`      | `https://a.com`     | ❌ 跨域 | 协议不同  |
| `http://a.com`      | `http://b.com`      | ❌ 跨域 | 域名不同  |
| `http://a.com:8080` | `http://a.com:3000` | ❌ 跨域 | 端口不同  |
**同源策略**主要防止恶意脚本读取另一个源的敏感数据，具体限制包括：
- 无法用 Ajax/Fetch 读取另一个源的 HTTP 响应
- 无法读取另一个源的 Cookie、LocalStorage、IndexedDB
- 无法通过 JS 获取另一个源页面的 DOM
- **注意**：跨域请求可以**发出**，服务器也处理了，但浏览器会**拦截响应**，不让你的 JavaScript 拿到数据。

## 跨域限制

假设你登录了银行网站 `bank.com`，Cookie 里存有你的身份信息。此时，你不小心点开了一个恶意网站 `evil.com`。

如果没有同源策略，`evil.com` 的页面就能用你的 Cookie 直接向 `bank.com` 发起转账请求，并读取账户余额——这就是著名的 **CSRF（跨站请求伪造）** 攻击。跨域限制正是为了阻止这种事情发生。

当然，像 `<script>`、`<img>`、`<link>` 标签引用外部资源，以及表单提交，出于历史原因默认是允许跨域的，但它们也有一些相应的安全防护机制。


## 跨域场景

现在的前后端分离开发非常普遍，所以开发时几乎一定会遇到跨域问题：
- 前端运行在 `http://localhost:3000`（开发服务器）
- 后端 API 运行在 `http://localhost:8080`
- 此时前端请求后端，端口不同，浏览器会直接报错，比如：

```
Access to fetch at ‘[http://localhost:8080/api](http://localhost:8080/api)‘ from origin ‘[http://localhost:3000](http://localhost:3000/)‘ has been blocked by CORS policy…
```

生产环境中，域名也常常不同：`www.my-site.com` 请求 `api.my-site.com`，这也是跨域。

## 如何解决跨域问题？

主要手段是让服务器告诉浏览器“这个跨域请求是安全的”，以下是几种主流方案：
### CORS（跨源资源共享）

这是现代的**标准方案**，需要后端在响应头中设置 `Access-Control-Allow-Origin` 等字段。
- 浏览器在跨域请求时会自动带上 `Origin` 头。
- 服务器验证后，返回 `Access-Control-Allow-Origin: http://localhost:3000`（或 `*`）。
- 浏览器看到这个头部后，才允许 JavaScript 读取响应。

### 代理服务器

利用**同源策略是浏览器限制，而不是服务器限制**这一点。

- 在开发时，可以用前端开发工具（如 Vite、Webpack Dev Server）配置代理，把 `/api` 请求转发到后端服务器。
- 这样，浏览器始终在和“同源”的开发服务器通信，开发服务器再帮你去请求后端。
- 生产环境通常用 Nginx 反向代理实现同样的效果。

### JSONP（传统方案，仅限 GET）

利用 `<script>` 标签不受同源策略限制的特点。
- 前端动态创建一个 `<script>` 标签，把 URL 和回调函数名传过去。
- 服务器返回一段 JavaScript 调用代码，比如 `handleData({…})`，数据就传过来了。
- **缺点**：只支持 GET 请求，有安全风险（XSS），现在已很少使用。
