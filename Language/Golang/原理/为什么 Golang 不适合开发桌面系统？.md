首先，GUI 系统设计的基本要求是啥？

1. 低延迟。任何操作都应该得到快速的反馈（按下键盘两秒之后才显示字符，那就别用了）
2. 高并发。移动鼠标不应该影响打字，边用鼠标变打字也不应该导致UI出bug（比如鼠标从文字上移动过去，字就消失了，因为两个事件同时更新了同样的像素）

基于这些需求，就不难发现 event loop 基本是唯一可行的UI架构。任何多线程或阻塞的编程语言都不适合。

而 Go 的调度器模型和 goroutine 的设计很难实现一个真正的 event loop，任何阻塞的调用（比如打开链接）都会导致整个 event loop 被挂起（event loop本身也是个 goroutine ，那么它也受到 Go 调度器的制约，阻塞的系统调用将G与P一起从当前的系统线程M解绑，放到专用的阻塞线程上去）。而 Go 没有 Promise 和 async/await 这种细粒度的调度机制，所以要想实现类似的功能，以现在的语言版本，只有两种选择：

1. 任何阻塞调用都必须放到单独的 goroutine 里，结尾再调用剩下的（等于是 await 之后的）代码。本质上是一种简陋的协程机制。
2. 开发一整套带 callback 的库，代替现有的标准库。

1的问题是无法保证线程安全（除非把 GOMAXPROCS 设为1，等于像 JS 一样变成单线程），需要各种同步。2的问题是回调地狱

所以 Go 的设计初衷就不是为了写 UI 的
