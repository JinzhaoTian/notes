**ECMAScript 是 JavaScript 的语言标准**，由 ECMA 国际组织制定（规范编号 ECMA-262）。你可以把它理解为一份官方说明书，规定了这门语言应该有哪些关键字、数据类型、语法结构（如 `if`, `for`, `function`）等。

> [!quote] ECMAScript 规范的妥协与统一
> 由于 JavaScript 特殊的历史导致了其包含了许多设计缺陷，**过早的标准化**使得这些缺陷在充分暴露之前就成了既定标准，由于早期就被广泛采用，“向后兼容”成为了语言演进不可动摇的底线。
> 
> ECMAScript 规范**在承认这些历史现实的前提下，努力为这门语言建立一个统一、稳定且可演进的“运行时契约”**。
> 
> ECMAScript 规范的核心作用体现在：
> 1. **统一“运行时契约”**：规范的首要任务是定义所有 JavaScript 引擎（如 V8、SpiderMonkey）都必须遵守的**语言核心标准**，确保同一段代码在不同环境中行为一致。这解决了早期浏览器各自为政带来的兼容性问题。
> 2. **将“事实标准”法典化**：规范并非凭空创造，它经常将实践中形成的**事实标准（de facto standard）** 纳入其中。例如，ES5 就正式“编纂”（codified）了浏览器实现中已成为共识的解释和行为。
> 3. **明确“遗留”与“现代”的边界**：规范并非对所有历史问题照单全收。它通过设立**“Legacy”子条款**，明确标识出那些仅为兼容而保留的、不推荐使用的不佳特性，将其与现代特性区分开来。同时，像 **“严格模式”（Strict Mode）** 这样的机制被引入，允许开发者在代码中选择“退出”部分不合理的遗留行为，从而获得更干净、更安全的语义。
> 
> ECMAScript 规范明确指出，一个合规的实现**可以**提供超出规范定义的额外功能，但**不得**重新定义那些非实现定义的核心设施。这意味着：
> 1. **新特性是“加法”**：语言的发展以**添加新特性**为主，而不是修改旧有语法或行为，确保旧代码永远能运行。
> 2. **避免破坏性升级**：这种策略避免了类似 Python 2 到 3 那样痛苦的、不兼容的迁移，降低了整个生态的升级成本和心智负担。


**JavaScript 是 ECMAScript 标准的一个具体实现**，浏览器（如 V8 引擎）和 Node.js 都在遵循这份标准来运行代码。我们常听到的 ES5、ES6（ES2015）、ES2023 等，指的就是这份标准的**不同版本**，每个版本都会引入新语法和新特性。所以，ECMAScript 本身**不负责**定义“模块”该怎么写（虽然后来的 ES Module 成为了标准的一部分，那是另一回事）。

TypeScript 是 JavaScript 的一个“超集”（Superset）。这意味着，**任何合法的 JavaScript 代码，同时也是合法的 TypeScript 代码**。JavaScript 是动态类型语言，很多错误只有在代码运行时才会暴露（比如你把一个数字当成函数来调用）。TypeScript 则让你在写代码时就声明类型（如 `let name: string`），并在代码运行前（编译阶段）就检查出类型错误，这能帮你避免大量潜在的 Bug，尤其在大型项目中。

## 全局对象（Global Object）

在 ECMAScript 规范中规定，**全局对象在控制权进入任何执行上下文之前，就已经被创建了**。它是唯一的，承载着脚本运行所需的最基础环境。

从 ECMAScript 规范角度，它有几个决定性特征：
- **它不是一个函数**：全局对象没有 `[[Call]]` 和 `[[Construct]]` 内部方法，这意味着你不能把它当作函数调用，也不能用 `new` 来构造它。
- **它的属性有两类来源**：
    - **规范定义的内置属性**：例如 `NaN`、`Infinity`、`undefined`，以及 `Object`、`Function`、`Array`等构造函数，它们都是全局对象的属性。
    - **宿主定义的属性**：宿主环境（如浏览器、Node.js）可以向全局对象添加额外属性。规范甚至允许宿主添加一个**值指向全局对象自身**的属性。

在 ECMAScript 规范中的全局对象是一个抽象概念，是一种对**执行环境**的封装。在不同的 JavaScript 运行时中，它通过不同的具体对象暴露给你。

- **浏览器**：你接触到的全局对象通常是 `window`。但更精确地说，由于 HTML 标准的安全和导航机制，`window` 实际上是一个 **`WindowProxy`（代理）**。它代理了真正的全局对象 `Window`，并在页面导航时保持身份不变，而背后的 `Window` 可能已被替换。真正的全局对象 `Window`，在 JavaScript 中是无法被直接访问到的。
- **Node.js**：全局对象通常通过名为 `global` 的对象来访问。
- **Web Workers**：全局对象通常通过 `self` 来访问。


### `globalThis`

正因为历史上不同环境的全局对象名称各异，ES2020 引入了 **`globalThis`**，**提供一个标准、统一的入口来访问全局对象**，解决了历史上因环境而异（`window`、`global`、`self`）的混乱问题。

在实际开发中，围绕它最重要的原则是：**主要用于“读”，极力避免“写”**。在向 `globalThis` 添加属性，就相当于创建了全局变量。不过，规范也允许宿主为 `globalThis` 提供一个**与全局对象不同**的值，这是规范保留的灵活性。

> [!caution] 严格限制“写入”
> **在绝大多数业务代码和库代码中，绝对不要直接通过 `globalThis.xxx = ...` 来创建全局变量。**
> - **硬性约束**：SSR 指南强调，库代码**绝不能**直接访问或修改 `globalThis`，否则会影响宿主应用，在 SSR 环境中造成意外副作用。
> - **为什么危险**：直接修改全局对象会让**状态的创建位置变得模糊**，难以追踪；并且极易**意外覆盖**已有的全局属性，引发难以排查的 bug。ESLint 甚至有专门的规则（`no-global-object-property-assignment`）来禁止这种行为。

现代 JavaScript 已经不需要靠污染全局来共享代码了。对于需要跨模块共享的数据或工具，正确的做法是使用**模块作用域**。

1. **错误做法（污染全局）**
```javascript
globalThis.myGlobalConfig = { apiUrl: '...' };
```

2. **正确做法（使用模块作用域）**
```javascript
// config.js
export const myGlobalConfig = { apiUrl: '...' };
// 在其他模块中使用
import { myGlobalConfig } from './config.js';
```

这种显式导入导出的方式，让依赖关系清晰可见，也避免了意外的全局覆盖。

### 内存管理中的核心

全局对象在内存管理中的核心角色是**作为垃圾回收（GC）的“根”（Root）**。在 V8 等引擎的可达性分析算法中，GC 会从一组根对象出发，递归遍历所有可达的对象。**任何从全局对象出发能够访问到的对象，都会被标记为“存活”，不会被回收**。因此，全局对象是内存生命周期的绝对起点，这也解释了为什么“全局变量”常常与内存泄漏联系在一起。

#### 从全局对象派生的内存泄漏模式

理解了全局对象是 GC 的根，就能明白任何无意间建立的、从**全局对象**到某个数据的**强引用**，都会强制该数据活到进程结束。
- **意外的全局变量**：在非严格模式下，给未声明的变量赋值（`bar = []`）或函数内 `this` 指向全局时，变量会**隐式挂载到全局对象**上，永久存活。修复方式是**始终使用 `'use strict'` 或 ES 模块**，并用 ESLint 拦截。
- **未清理的定时器/事件监听**：`setInterval` 的回调、绑定在 `window` 上的监听器，会形成从全局对象到回调（及其闭包捕获的大对象）的强引用链。即使组件销毁，这些数据也因全局引用无法释放。修复是**保存句柄并在清理阶段 `clearInterval` 或 `removeEventListener`**。
- **脱离 DOM 的引用**：用全局变量或模块级变量缓存了 DOM 节点，即使节点已从文档树移除，该引用依然能通过全局对象可达，导致整个节点及关联数据无法回收。
- **无界的全局缓存**：用 `Map` 或普通对象做缓存且没有上限。由于 `Map` 的键是**强引用**，缓存会无限增长，所有键值对都永久存活。修复是使用**有容量上限和淘汰策略（如 TTL）的 LRU 缓存**。

#### 精细化管理：使用“弱引用”切断非必要链接

对于必须建立、但又不应阻止对象回收的关联，需要使用弱引用机制。

- **`WeakMap` / `WeakSet`**：它们的键是**弱引用**。如果某个对象仅被 `WeakMap` 的键引用，GC 就可以回收它，对应条目也会自动消失，无需手动清理。这非常适合**为对象关联元数据**或**缓存与对象生命周期绑定的计算结果**。
- **`WeakRef` 与 `FinalizationRegistry`**：提供更底层的控制。`WeakRef` 允许你**持有对象的弱引用**而不阻止其回收，通过 `deref()` 访问（可能返回 `undefined`）。`FinalizationRegistry` 允许你在对象被回收后**注册清理回调**。**注意**：`FinalizationRegistry` 的回调**不保证执行时机，甚至不保证执行**，因此**绝不能**将关键的业务逻辑（如释放文件句柄）放在其中。
