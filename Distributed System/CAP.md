在一个分布式系统中，
- **一致性（[Consistency](Consistency.md)）**：系统的所有节点，在同一时间看到的数据是完全相同的，否则报错。
- **可用性（[Availability](Availability.md)）**：系统始终能响应请求（不保证数据最新），不会因为节点故障而拒绝服务。
- **分区容错性（[Partition Tolerance](Partition%20Tolerance.md)）**：由于分布式系统通过网络进行通信，网络是不可靠的。系统在节点间通信中断（即：**网络分区**）时仍能继续运行。

**CAP 原则**：**一致性、可用性、分区容错性这三个要素最多只能同时实现两点，不可能三者兼顾**。

## 权衡

- **CA（放弃P）**：单机数据库（如 MySQL 主从架构），但无法容忍网络分区，不适合分布式场景。
- **AP（放弃C）**：如 NoSQL（Cassandra、DynamoDB），保证高可用，但可能返回旧数据（最终一致性）。
- **CP（放弃A）**：如 ZooKeeper 、 Redis Cluster ，强一致性优先，但在分区时可能拒绝服务。


**注意**

1. **P是必选项**：分布式系统中**网络分区不可避免**，实际通常在 CP 或 AP 之间选择。
2. **灵活权衡**：现代系统（如MongoDB、Kafka）通过设计（如副本同步、超时机制）在CAP间动态调整。
3. **最终一致性**：AP 系统常通过异步复制（如 DNS 、Git ）实现数据的最终一致。



### 典型应用

- **支付系统**：通常选择 CP ，确保金额准确（一致性优先）。
- **社交网络**：可能选择 AP ，允许短暂数据不一致（可用性优先）。




## BASE

BASE（Basically Available，Soft state，Eventually consistent）是对 CAP 定理中 AP 架构（高可用 + 分区容错）的延伸，通过牺牲强一致性（C），换取系统的高可用性和可扩展性。

- **基本可用（Basically Available）**：系统在故障时仍能提供**核心功能**，但可能降级（如响应变慢、返回简化数据）。
- **软状态（Soft state）**：允许系统中的数据存在**中间状态**（不同节点间短暂不一致），无需实时同步。
- **最终一致性（Eventually consistent）**：经过一段时间后（无新写入时），所有节点数据最终会达成一致。

BASE 是 NoSQL 数据库（如 Cassandra 、MongoDB ）和现代分布式系统（如电商、社交网络）的核心设计思想。


### 典型应用

1. **电商库存**
    - 扣减库存时允许超卖（软状态），后续通过补货或订单取消修复（最终一致）。
2. **社交媒体**
    - 用户发布的动态可能延迟几秒同步到所有好友（最终一致）。
3. **支付系统**
    - 支付成功通知可能延迟（基本可用），但最终保证账务平衡。
