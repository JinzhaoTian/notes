ECS（Entity-Component-System，实体-组件-系统）是一种常用于游戏开发的软件架构模式，是一种数据导向的设计模式，其指导思想是[面向数据编程 DOP](../../Language/Programming%20Paradigm/面向数据编程.md)，与传统的面向对象编程方法有所不同。

## 核心概念

1. **实体（Entity）**
    - 其只是一个唯一的标识符（ID）
    - 其用于表示游戏中的基本对象/事物
    - 其本身不包含数据或行为
> [!tip]
> Entity 一般设计成结构体，其中一般包含实体的 version 字段（ Entity 复用一次计数加1），以及实体唯一 ID；
> 
> 实体的创建和销毁必须延迟到所有系统更新结束后的帧末执行。

2. **组件（Component）**
    - 其为数据的载体，纯数据容器
    - 代表实体的某个特定方面（如位置、外观、健康值等）
    - 不包含任何行为或逻辑
> [!tip]
> Component 一般设计为结构体，其中没有行为，只有简单的字段或属性访问器；字段属性应尽量紧凑、连续存储、避免指针、使用简单类型、字段数量适中、只包含必要数据、减少频繁修改，并选择合适的数据结构等。
> 
> 一切为了提高缓存命中率、减少内存访问延迟和同步开销，从而提升系统的整体性能；
> 
> 组件应当区分属于实体还是系统，对于系统组件，做成 SharedComponent（或者叫做SingletonComponent）；
>  
> 组件的添加和移除（如有）必须延迟到所有系统更新结束后的帧末执行。

3. **系统（System）**
    - 处理具有特定组件组合的实体
    - 包含行为和逻辑
    - 例如：渲染系统处理所有具有位置和外观组件的实体，物理系统可能会遍历所有包含位置和速度组件的实体，并根据速度更新位置。
> [!tip]
> System 之间通过 Pipeline 等机制来严格控制执行顺序；System 之间不可相互通信，如确有需要，可通过 SharedComponent 和 Command Buffer 来实现相关需求；System 仅含无副作用的纯方法函数，不含字段属性数据，没有内部状态；System 通过 Query 和 Archetype 来查询和操作关心的 Entity 的 Component ；多个 System 的公共函数做成静态函数，称为工具（Utility）函数；为了性能，一个 System 的 Tick 中可以执行多个查询操作。


## 高级概念

### Storage

Storage（存储）是 ECS 架构中用于管理组件数据的存储机制，不同的存储策略可以影响系统的性能和内存使用：
1. **原型块存储**：将相同组件集合的实体组存储在同一块内存中，适合需要高内存局部性和高效批处理的场景。
2. **数组存储**：将组件数据存储在数组中，按实体 ID 索引，适用于组件数量较少且访问频繁的情况。
3. **稀疏数组**：使用稀疏数组存储组件数据，适用于组件数量较多且分布稀疏的情况。
4. **结构化存储**：将组件数据按结构化方式存储，减少内存碎片和访问延迟。
5. **压缩存储**：使用压缩技术减少内存占用，适用于内存受限的情况。

> [!tip] 缓存友好性
> 现代游戏引擎在每帧处理对象时，缓存不友好会导致性能下降。例如，物理模拟子系统更新对象位置时，若对象包含大量无关数据（如 name、color），会降低缓存命中率，增加内存访问延迟。
> 
> **解决方案**是将需要定期迭代的数据紧密打包在一起（格式通常为 [C++ POD](../../Language/C++/原理/C++%20POD.md) ），以提高缓存命中率。这是 ECS 架构的核心思想，处理器更喜欢迭代连续数据数组，减少内存跳转次数。此外，紧密打包的数据有助于进行 [SIMD](../../Operation%20System/SIMD.md) 优化。


### Archetype

Archetype（原型）是 ECS 架构中的一种数据组织方式，用于将具有相同组件组合的实体分组在一起。通过这种方式，可以高效地管理和访问实体及其组件。

1. **组件组合**：每个 Archetype 表示一组具有相同组件组合的实体，例如，具有位置和速度组件的实体可以属于同一个 Archetype。
2. **内存布局**：将属于同一 Archetype 的实体及其组件数据连续存储在内存中，以提高缓存命中率和访问效率。
3. **快速查询**：通过 Archetype，可以快速查询和遍历具有特定组件组合的实体，减少不必要的遍历和检查。


### Chunk

Chunk 是 ECS 中用于存储实体及其组件数据的内存块，每个 Chunk 通常包含多个实体的数据，并且这些实体都属于同一个 Archetype。

Chunk 的设计目的是为了优化内存布局和访问速度，通过将相关数据紧密地存储在一起，减少缓存未命中和内存碎片。

一个 Chunk 通常包含以下内容：
1. **Entity ID 列表**：存储 Chunk 中所有实体的 ID。
2. **Component 数据**：存储 Chunk 中所有实体的组件数据，每种组件类型的数据通常存储在连续的内存区域中。

#### Archetype 和 Chunk 的联系

Archetype 是逻辑上的 Entity 分组，而 Chunk 是物理上的数据存储单元。每个 Archetype 由一个或多个 Chunk 组成，这些 Chunk 存储了属于该 Archetype 的所有 Entity 及其 Component 数据。

具体来说，当一个 Entity 被创建并分配给一个 Archetype 时，该 Entity 的 Component 数据会被存储在该 Archetype 的一个 Chunk 中。如果该 Chunk 已满，则会分配一个新的 Chunk 来存储更多的 Entity 及其 Component 数据。

假设我们有一个 Archetype，包含 Entity A 和 B。这个 Archetype 可能由多个 Chunk 组成，每个 Chunk 存储了一部分具有 Entity A 和 B 的 Component 数据：
```
Archetype: {A, B}
  ├── Chunk 1
  │     ├── Entity 1: {A, B}
  │     ├── Entity 2: {A, B}
  │     └── ...
  ├── Chunk 2
  │     ├── Entity 3: {A, B}
  │     ├── Entity 4: {A, B}
  │     └── ...
  └── ...
```


### 内存布局

以内存 Chunk 形式组织数据可以提高缓存性能，即在处理完一个缓存块的所有计算后再调入下一个块。Archetype 的数据存放在多个连续的大块内存中，每个 Chunk 记录了 Archetype 类型、Entity 容量和当前存放的 Entity 数量等信息。

这种内存组织方式模拟了 DOD（数据导向设计）中的 SOA（数组结构）数据结构，相比传统的 AOS（结构数组）存储方式更高效。Entity 的 Storage 中存储了某个 Entity 存储的 Chunk 及其在 Chunk 中的索引，并包含分代索引信息，便于索引。


Archetype Chunk 方案和内存布局下，可以很效率地通过 Entity 拿到 Archetype ，进而拿到 Chunk，又已知 Component 类型的情况下，可以很效率地对 Component 数据进行访问。因为所有这些操作都是在一片连续内存上进行的，CacheMiss 概率很低。


### 结构性变化

Archetype Chunk 或者说内存块的变化会影响性能，导致 Chunk 变化的操作成为结构性变化，实体的创建和销毁、组件的添加和移除等都会导致结构性变化（实体会”移动“到其他 Chunk）。

可以通过 Command Buffer 来解决结构性变化带来的并行问题，但是不能彻底解决性能问题。需要注意的是这并非 ECS 的问题，而是 Archetype Chunk 这种方案的 ECS 的问题。


### Query

Query（查询）机制通过高效的组件存储结构、明确的查询条件定义和优化的查询执行策略，实现了对特定类型实体和组件的高效检索和操作，并支持并发执行和数据同步，确保系统的高性能和线程安全。

1. **组件存储结构**：组件数据通常以稀疏数组、结构化数组（SOA）或紧凑数组的形式存储，以便高效地进行查询和访问。
2. **查询条件定义**：查询条件定义包括指定需要检索的组件类型和访问权限（只读、只写、读写）。这通常通过模板或类型列表来表示。
3. **查询执行**：查询执行涉及遍历实体和组件存储结构，检索符合查询条件的实体和组件。框架会根据查询条件过滤出符合条件的实体。
4. **并发和同步**：为了提高性能，ECS 框架通常支持并发查询和系统执行。通过读写锁或任务调度器来管理组件的访问权限，确保线程安全。

### Entity Prefabs

Entity Prefabs（实体预制件）是一种模板机制，用于预定义一组具有特定组件组合和初始状态的实体。通过实体预制件，可以快速创建和初始化实体，简化开发流程。

通过 Entity Prefabs 创建的实体可以根据其组件组合自动归类到相应的 Archetype 中。

1. **预定义模板**：定义一组具有特定组件组合和初始状态的实体模板。
2. **实例化**：根据预定义的模板，快速创建和初始化实体。
3. **模板管理**：管理和维护实体预制件，支持模板的创建、修改和删除。


### Context（World）

Context（上下文）或者 World（世界），也有直接叫做 WorldContext 。Context 是 ECS 架构中的一种管理机制，用于管理和协调多个系统和组件。Context 通常包含实体管理器、组件管理器和系统管理器等。

1. **实体管理器**：负责创建、销毁和管理实体。
2. **组件管理器**：负责添加、移除和管理组件数据。
3. **系统管理器**：负责注册、更新和管理系统。


### Command Buffer

Command Buffer（命令缓冲区）是 ECS 架构中的一种命令记录和执行机制，用于在系统更新过程中记录对实体和组件的操作，并在适当的时机批量执行这些操作。

1. **命令记录**：在系统更新过程中，记录对实体和组件的操作，如添加、移除和修改组件。
2. **命令缓冲区**：将记录的命令存储在缓冲区中，等待批量执行。
3. **命令执行**：在适当的时机（如系统更新结束后），批量执行缓冲区中的命令，确保操作的原子性和一致性。

> [!tip]
> 对实体和组件的写操作（如实体的创建和销毁，组件的添加和移除等），会破坏操作的原子性和一致性，引发框架内部的结构性变化，导致**无法并行处理**。
> 
> 处理方案是把这些操作记录到缓冲区（Command Buffer）中，延迟到全部系统更新完毕后统一进行。


### Pipeline

Pipeline（管道）是 ECS 架构中的一种处理机制，用于定义系统的执行顺序和依赖关系。通过 Pipeline，可以确保系统按正确的顺序执行，并处理系统间的依赖关系。

1. **系统排序**：根据系统的依赖关系，对系统进行排序，确保按正确的顺序执行。
2. **阶段划分**：将系统划分为多个阶段，每个阶段包含一组独立的系统，可以并行执行。
3. **依赖管理**：管理系统间的依赖关系，确保依赖关系得到正确处理。


### Job System

Job System 是一种并行处理机制，用于将系统的更新逻辑分解为多个独立的任务，并在多个线程上并行执行这些任务。Job System 可以显著提高系统的并行性和性能。

1. **任务分解**：将系统的更新逻辑分解为多个独立的任务，每个任务可以在独立的线程上执行。
2. **任务调度**：使用任务调度器管理任务的执行，确保任务按正确的顺序和依赖关系执行。
3. **任务同步**：使用同步机制（如锁、信号量等）确保任务间的数据一致性和同步。


### System Prioritization

在 ECS 架构中，不同的系统可能具有不同的优先级。通过设置系统的优先级，可以控制系统的执行顺序，确保关键系统优先执行。

System Prioritization（系统优先级）主要用于定义系统的执行顺序，管理依赖关系和优化执行效率；而管道则用于将系统的执行过程分成多个阶段，组织和管理复杂的系统逻辑，并实现并行处理。

1. **优先级设置**：为每个系统设置优先级，根据优先级确定系统的执行顺序。
2. **优先级队列**：使用优先级队列管理系统的执行顺序，确保高优先级系统优先执行。
3. **动态调整**：根据运行时的需求和条件，动态调整系统的优先级，以适应不同的场景和需求。



## 相关概念

### AOI

AOI（Area of Interest）是指在大型多人在线游戏（MMO）中，玩家只需要关注其周围一定范围内的其他玩家和对象，而不需要处理整个游戏世界的所有信息。AOI 技术通过限制玩家的视野范围，可以显著减少网络带宽和服务器负载或者客户端的性能压力。

1. **网格划分**：将游戏世界划分为多个网格，每个网格只包含一定范围内的对象。玩家只需要处理其所在网格及相邻网格的对象。
2. **圆形范围**：以玩家为中心，定义一个圆形范围，玩家只需要处理该范围内的对象。
3. **动态调整**：根据玩家的移动速度和方向，动态调整AOI范围，以确保玩家始终关注其感兴趣的对象。


### QBI

QBI（Query-Based Interest Management）是一种基于查询的兴趣管理技术，用于确定哪些实体对某个玩家或系统是重要的。QBI 通过定义查询条件，可以灵活地筛选出感兴趣的实体，从而减少不必要的计算和数据传输。

1. **查询条件**：定义一组查询条件，如位置、类型、状态等，用于筛选感兴趣的实体。
2. **索引结构**：使用索引结构（如空间哈希、四叉树、八叉树等）加速查询过程，提高效率。
3. **动态更新**：根据实体的状态变化，动态更新查询结果，确保实时性。


### EQS

EQS（Environment Query System）是一种环境查询系统，常用于 AI 和游戏逻辑中，用于在复杂环境中进行高效的查询和决策。EQS 通过定义一组查询规则，可以快速找到满足特定条件的环境信息，从而支持智能决策。

1. **查询规则**：定义一组查询规则，如距离、视野、遮挡等，用于筛选环境信息。
2. **评分机制**：为每个查询结果打分，根据评分选择最佳结果。
3. **缓存和优化**：使用缓存和优化技术，减少重复计算，提高查询效率。



### Spatial Partitioning

Spatial Partitioning（空间分区）技术用于将游戏世界划分为多个区域，以加速空间查询和碰撞检测。常见的空间分区技术包括四叉树、八叉树、BVH 等，广泛应用于游戏开发中。


## 实现方案

### Archetype and Chunk

- **优点**：
	- 内存局部性好：批量操作效率高。
	- 高效的批处理：适合需要高效批处理的场景。
- **缺点**：
	- 管理复杂度高：特别是在实体组件频繁变化时。

#### 适用场景

适合需要高内存局部性和高效批处理的场景。


### Sparse Set

Sparse Set（稀疏集）：
1. 稀疏数组：索引是实体 ID，值是紧凑数组中的索引。
2. 紧凑数组：存储实际的组件数据。


- **优点**：
	- 查找和访问速度快：通过稀疏数组快速定位组件数据。
	- 适合稀疏数据：适合处理大量稀疏数据。

- **缺点**：
	- 内存占用较大：特别是当实体 ID 范围很大时。

#### 适用场景

适合实体数量多且组件数据稀疏的场景。


### SOA

SOA（半连续数组，Structure of Arrays）
1. 组件数组：每种组件类型的数据存储在一个连续的数组中。
2. 实体 ID 索引：通过实体 ID 索引这些数组。


- **优点**
	- 内存访问效率高：适合 SIMD（单指令多数据）操作。
	- 数据对齐：有利于缓存命中率。

- **缺点**
	- 多数组访问：访问多个数组可能导致缓存未命中。

#### 适用场景

适合需要高效 SIMD 操作的场景。



### Bitset

Bitset（位集）：
1. 位图：使用位图表示实体和组件关系。
2. 位向量：每个实体对应一个位向量，每个位表示该实体是否具有某个组件。


- **优点**：
	- 内存占用小：适合快速检查实体是否具有某个组件。
	- 快速检查：快速检查组件关系。

- **缺点**：
	- 不适合存储实际数据：通常需要与其他数据结构结合使用。

#### 适用场景

适合需要快速检查组件关系的场景。


### Direct Array

Direct Array（直接数组）：
1. 实体数组：一个大数组，存储所有实体的组件数据。
2. 固定位置：每个实体的组件数据在数组中占据固定的位置。


- **优点**：
	- 简单易懂：实现方式简单，易于理解和实现。
	- 访问速度快：通过实体 ID 直接计算数组索引，访问速度非常快。

- **缺点**：
	- 内存浪费：如果实体 ID 范围很大但实际实体数量较少，会导致大量内存浪费。
	- 不灵活：不适合动态性较强的场景。

#### 适用场景

1. 小规模 ECS 系统：适合实体数量较少且实体 ID 范围不大的小规模 ECS 系统。
2. 固定组件集合：适合实体的组件集合相对固定、不频繁变化的场景。


### Hash Table

Hash Table（哈希表）：
1. 哈希表：使用哈希表存储实体的组件数据，实体 ID 作为键，组件数据作为值。
2. 动态扩展：哈希表可以动态扩展，适应实体数量的变化。



- **优点**：
	- 动态性强：适合动态性较强的场景，实体的组件集合可以灵活变化。
	- 内存利用率高：只存储实际存在的实体和组件数据，不会浪费内存。

- **缺点**：
	- 访问速度较慢：相比直接数组，通过哈希表查找和访问数据的速度较慢。
	- 实现复杂度高：哈希表的实现和管理相对复杂，特别是在处理哈希冲突时。

#### 适用场景

1. 动态 ECS 系统：适合实体数量和组件集合频繁变化的动态 ECS 系统。
2. 大规模 ECS 系统：适合实体数量较多且实体 ID 范围较大的大规模 ECS 系统。


## 对比 OOP 架构

### 优点

1. **OOP 方式**：
	- 开发速度快，逻辑集中，一目了然。
	- 调试​​便捷，在 `Update` 方法里设断点，一步步看它的状态机、变量，流程很清晰。
2. **ECS 方式**：
	- 处理大规模具有简单、统一行为的实体有性能优势，为极致性能和数据局部性而设计。

### 缺点

1. **OOP 方式**：
	- 性能问题
2. **ECS 方式**：
	- 数据驱动的、高度解耦的思维模式反直觉。
	- 开发速度慢，直观性和灵活性不够。
	- 随着项目规模扩大，系统依赖关系图会变得极其复杂，维护困难。
	- 不擅长处理逻辑复杂、实体间交互独特的游戏。
	- 调试困难，纯粹的数据驱动架构，当一个实体行为出错时，你很难快速定位问题。


### 更新流程

如，做一个玩家按下空格键跳跃的功能。
- **OOP 方式**：
	- 在 `Player` 类的 `Update` 方法里，检查输入，然后直接调用 `Jump` 方法修改速度。
- **ECS 方式**：
	- `InputSystem` 检测到空格键按下，为玩家实体添加一个 `JumpCommandComponent`
	- `JumpSystem` 查询所有拥有 `JumpCommandComponent` 和 `VelocityComponent` 的实体，根据其重力等参数修改速度值
	- `CleanupSystem` 移除 `JumpCommandComponent`，确保下一帧不会再次跳跃。

## 典型应用

ECS 架构特别适合需要高性能和灵活性的游戏引擎，有很多引擎内置了 ECS 支持，虽然名字乃至关键概念可能不尽相同，但改变不了其 ECS 本质，如游戏引擎两巨头 Unity 和 UE 使用的 ECS 框架都是 Archetype 的。

### Unity DOTS

Unity 的 DOTS（Data-Oriented Technology Stack）就是基于 ECS 理念构建的，是一个高性能的编程模型，旨在通过数据导向的设计来提高游戏的性能和可扩展性。

DOTS 主要由三个核心部分组成：
1. **ECS**
2. **C# Job System**：允许开发者将工作分解为多个并行执行的任务，从而提高性能。 
3. **Burst Compiler**：一个高性能的编译器，能够将 C# 代码编译为高效的机器代码，从而显著提高性能。


### Unreal Engine 5 MASS

Unreal Engine 5 中的 MASS（Mass Entity System）提供了一套高效的 ECS 框架，特别适用于需要处理大量实体的场景，如大规模的 AI 行为和复杂的物理模拟。

MASS 的核心概念有：
1. **Entity（实体）**：
	- Entity 是一个轻量级的标识符，用于标识一组 Fragments，Entity 本身不包含数据或行为。
2. **Fragment（片段）**：
	- Fragment 是纯数据结构，存储特定类型的数据，每个 Entity 可以拥有多个 Fragments。
3. **Processor（处理器）**：
	- Processor 负责执行特定的逻辑操作，Processor 会遍历所有包含特定 Fragments 的 Entity ，并对其进行处理。
4. **Archetype（原型）**：
	- Archetype 是一种 Entity 的模板，定义了一组 Fragments 的组合。通过 Archetype，可以高效地创建和管理具有相同 Fragments 组合的 Entity。
5. **Query（查询）**：
	- Query 用于从 Entity 集合中筛选出符合特定条件的 Entity，Processor 使用 Query 来确定需要处理的 Entity 集合。


### Bevy ECS

Bevy 是一个用 Rust 编写的开源游戏引擎，具有现代化的 ECS（Entity Component System）架构。Bevy 的 ECS 设计旨在提供高性能和灵活性，适用于各种规模的游戏开发




## 深入理解


### ECS 中的 System 与游戏引擎中的子系统的关系

ECS 中的 System（系统） 在职责划分上，确实对应着游戏引擎中的那些子系统（渲染、动画、物理等），但是，它们的工作方式和设计哲学有根本性的不同

#### 相似之处：职责

从宏观功能上看，两者是高度对应的：

1. **渲染系统（Rendering System）**：
	- 负责遍历所有拥有 `Transform`（变换）、`MeshRenderer`（网格渲染器） 或 `SpriteRenderer`（精灵渲染器） 等组件的实体，并将它们绘制到屏幕上。
2. **物理系统（Physics System）**：
	- 负责遍历所有拥有 `Transform`、`Rigidbody`（刚体）、`Collider`（碰撞体） 等组件的实体，进行物理模拟（速度、重力、碰撞检测等）。
3. **动画系统（Animation System）**：
	- 负责遍历所有拥有 `Animator`（动画控制器） 和 `Sprite` 或 `Mesh` 等组件的实体，更新它们的动画状态和当前帧。
4. **音频系统（Audio System）**：
	- 负责遍历所有拥有 `AudioSource`（音频源） 组件的实体，根据其位置和状态播放声音。

所以，您的直觉是正确的：**一个 System 封装了一个特定的、领域相关的功能，就像传统引擎中的一个子系统模块。**


#### 关键区别：设计哲学与工作方式

传统的子系统通常是面向对象（OOP）和命令式的，而 ECS 中的 System 是数据导向（Data-Oriented）和声明式的。

| 特性         | 传统游戏引擎子系统 (OOP风格)                                 | ECS 中的 System (数据导向风格)                                         |
| ---------- | ------------------------------------------------- | -------------------------------------------------------------- |
| **核心工作方式** | **主动查询/管理对象**。例如，渲染循环调用 `GameObject.Render()` 方法。 | **被动遍历处理数据**。系统在一个实体集合上运行，处理其拥有的组件数据。                          |
| **数据存储**   | 数据和行为封装在对象内部。数据可能分散在内存中（缓存不友好）。                   | **数据与行为完全分离**。组件是纯数据，紧密排列（缓存友好）。系统是纯行为。                        |
| **逻辑位置**   | 逻辑分布在各个游戏对象的方法中（如 `Update()`）。                    | 逻辑集中在系统内部。实体和组件不知道自己会被哪个系统处理。                                  |
| **关系**     | 通过继承和多态建立关系，容易导致复杂的继承树。                           | 通过**组合**建立关系。实体拥有哪些组件，就决定了它属于哪个系统的处理范围。                        |
| **控制流**    | `for each GameObject: gameObject.Update()`        | `System.Update(for all Entities that have Components A, B, C)` |

如，我们处理所有实体的移动：
1. **传统方式（OOP）**：
```cpp
// 在游戏主循环中
foreach (GameObject obj in allGameObjects) {
    obj.Update(); // 每个对象自己更新位置
}

// 在某个GameObject的子类（如MovableObject）中
public override void Update() {
    position += velocity * Time.deltaTime;
}
```
- **存在问题**：
	- CPU 需要在内存中跳来跳去调用每个对象的 Update，缓存命中率低。

2. **ECS方式（数据导向）**：
```cpp
// MovementSystem 的 Update 逻辑
// 1. 获取所有拥有 VelocityComponent 和 PositionComponent 的实体
var entities = entityManager.GetEntities<VelocityComponent, PositionComponent>();

// 2. 在紧密排列的数组上顺序处理（CPU缓存友好，性能极高）
foreach (var entity in entities) {
    ref var velocity = ref entity.GetComponent<VelocityComponent>();
    ref var position = ref entity.GetComponent<PositionComponent>();

    position.Value += velocity.Value * deltaTime;
}
```
- **优势**：
	- 系统一次性获取所有需要处理的数据，这些数据在内存中是连续存储的，非常适合 CPU 高速缓存，从而极大提升了性能。


#### 相互关系

##### 理论上：ECS 可以完全取代传统子系统

从纯架构的角度看，ECS 是一种完备的范式。所有游戏逻辑都可以被分解为：
1. **数据**（组件）
2. **行为**（系统）
3. **标识**（实体）

因此，一个理想的、纯粹的 ECS 引擎可以这样构建：

- **渲染子系统** -> **渲染系统**：处理包含 `MeshData`, `MaterialData`, `WorldTransform` 组件的实体。
- **物理子系统** -> **物理系统**：处理包含 `RigidBody`, `Collider`, `WorldTransform` 组件的实体。
- **音频子系统** -> **音频系统**：处理包含 `AudioSource`, `WorldTransform` 组件的实体。
- **动画子系统** -> **动画系统**：处理包含 `Skeleton`, `AnimationClip`, `AnimationState` 组件的实体。

在这种理想情况下，传统的、厚重的子系统被彻底拆解和重构为一系列高效的、数据驱动的系统，在统一的 ECS 框架下运行，**这也是 Unity DOTS 的终极愿景**。


##### 实践中：挑战与现实

然而，完全抛弃传统子系统面临着巨大的挑战：

1. **底层硬件和 API 的抽象**：
    - 显卡是通过渲染API（如Vulkan, DirectX, OpenGL）来通信的，这些 API 本身是**面向过程的命令式接口**。
    - 物理模拟通常依赖于高度优化的、独立的物理引擎（如NVIDIA PhysX, Havok），它们有自己的对象和内存管理方式。
    - 音频播放依赖于音频API（如XAudio2, OpenAL）。
> [!tip]
> 无法用纯粹的 ECS 组件去直接驱动显卡或声卡，总需要一个翻译层或边界，将 ECS 中的数据转换为底层 API 能够理解的命令。
> 
> 这个边界本身，看起来就很像一个传统的子系统。
 
2. **生态和工具链**：
    - 整个游戏开发产业是建立在现有工具链之上的（如 3D 建模软件、动画制作工具、音频中间件 FMOD/Wwise ）。
    - 这些工具输出的资源（模型、动画、声音）需要被引擎识别和管理。传统的子系统作为这些资源的管理器和处理器已经非常成熟。用 ECS 从头重建一整套资源管线、编辑器工具、调试可视化功能，是一个浩大的工程。

3. **开发复杂度和适用性**：
    - ECS 的优势在于处理大规模、高度模拟密集型的对象（如数千个单位的 RTS 游戏、沙盒游戏中的大量实体）。
    - 但对于一些逻辑复杂但数量不多的对象（如游戏剧情状态机、UI管理、存档系统），使用传统的 OOP 或其他范式可能更直观、开发效率更高。强行用 ECS 实现一切可能会杀鸡用牛刀，增加不必要的复杂性。


#### 融合模式

因此，当前最先进且实用的做法是一种**混合架构**：
1. **底层基础设施层**：
	- 仍然使用高度优化的、传统的**渲染引擎**、**物理引擎**、**音频引擎**等，作为基础服务存在。
2. **核心游戏玩法层**：
	- 使用 ECS 来驱动所有游戏逻辑和状态，这是 ECS 大放异彩的地方。
    - 你的游戏单位、技能、道具、Buff/Debuff 等全部用实体和组件来表示。
    - 你的移动、伤害计算、技能释放等逻辑全部用系统来实现。
3. **桥梁（The Bridge）**：需要编写专门的**渲染同步系统**、**物理同步系统**等。
    - **渲染同步系统**：遍历所有有渲染需求的实体（包含 `RenderMesh` 和 `WorldTransform` 组件），将它们的变换矩阵和网格数据收集起来，批量提交给传统的渲染管线。
    - **物理同步系统**：在物理模拟前，将 ECS 中 `RigidBody` 组件的位置、速度等数据同步到物理引擎的刚体对象中；在物理模拟后，再将物理引擎计算出的新位置、碰撞信息等写回对应的 ECS 组件。
