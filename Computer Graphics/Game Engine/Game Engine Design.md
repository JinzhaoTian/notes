
## 适合做成单例

> [!attention] 注意事项
> - **谨慎使用**：不要仅仅为了“方便访问”而使用单例，单例本质上是全局变量，会带来耦合性高、难以进行单元测试、隐藏依赖关系等问题。在决定使用单例前，先考虑是否可以通过依赖注入（Dependency Injection）来传递实例。
> - **线程安全**：在现代多线程引擎中，确保单例的初始化和访问是线程安全的至关重要（例如，在 C++ 中使用 Meyers' Singleton 或  `std::call_once` ）。
> - **惰性初始化** vs **显式初始化**：
> 	- **惰性初始化**：在第一次被访问时才创建，简单，但可能会在不可预测的时间点（如游戏运行时）引发加载卡顿。
> 	- **显式初始化**：在引擎启动时按特定顺序手动创建所有单例，这提供了更好的控制，可以管理初始化顺序并提前暴露问题。
> - **考虑服务定位器模式（Service Locator）**：这是一种更灵活、更易于测试的替代方案，定义一个全局的服务定位器，它负责提供各种服务（如渲染、音频、输入）的接口。单例是这些接口的具体实现并被注册到定位器中。这样，你可以在测试时用模拟对象（Mock）替换掉真实的渲染器或音频管理器。


1. **日志管理器（LogManager / Logger）**
	- **为什么适合**：整个引擎的任何模块（渲染、物理、音频、脚本等）都需要向同一个地方输出日志信息，用于调试、跟踪和错误报告。全局只有一个日志输出目标（可能是文件、控制台、IDE等）是合理且必要的。
	- **职责**：接收所有日志消息，附加时间戳、严重等级（Info, Warning, Error等）、模块信息，并统一输出和管理。

2. **资源管理器（ResourceManager / AssetManager）**
	- **为什么适合**：负责加载、缓存、管理和提供游戏资源（纹理、模型、音频、字体等）。它必须保证同一份资源（例如一个纹理）只在内存中存在一份，并被所有需要它的对象共享。如果存在多个资源管理器实例，会导致资源重复加载，严重浪费内存。
	- **职责**：使用类似字典或映射的结构来缓存资源，提供 `GetTexture("path/to/texture.png")` 这样的接口，内部实现引用计数或垃圾回收机制。

3. **渲染管理器/渲染器（RenderManager / Renderer）**
	- **为什么适合**：引擎通常只与一个图形API（如OpenGL, DirectX, Vulkan）上下文交互。渲染器封装了所有底层图形操作，管理着渲染状态（如混合、深度测试）、渲染队列和图形设备。拥有多个渲染器实例通常没有意义且会导致冲突。
	- **职责**：初始化图形API，设置渲染状态，接收渲染命令（绘制网格、设置着色器等），并最终将画面提交到屏幕。

4. **音频管理器（AudioManager）**
	- **为什么适合**：管理所有音频的播放、暂停、停止和音量控制。声音输出设备通常也是全局唯一的，由一个中心系统来混音所有音源是最合理的。
	- **职责**：加载音频文件，管理音效和音乐通道，处理3D音效的空间化计算，提供简单的播放接口。

5. **输入管理器（InputManager）**
	- **为什么适合**：键盘、鼠标、手柄等输入设备是系统级的全局资源。所有游戏系统都需要查询同一套输入状态（如“A键是否按下”、“鼠标光标位置”）。如果每个系统都各自读取输入，会导致状态不一致和性能浪费。
	- **职责**：每一帧轮询所有输入设备的当前状态，并将其转换为抽象的输入动作（如“Jump”、“MoveHorizontal”），提供查询接口。它通常维护当前帧和上一帧的状态，以检测“按下”和“释放”事件。

6. **场景管理器（SceneManager）**
	- **为什么适合**：在大多数情况下，引擎一次只运行和更新一个游戏场景（如主菜单、第一关、第二关）。场景管理器作为全局入口点来加载、卸载、切换和更新当前活动场景是非常合适的。
	- **职责**：持有当前活动场景的根节点，驱动场景的加载和卸载流程，调用场景内对象的 `Update` 和 `Render` 方法。

7. **配置管理器（ConfigurationManager）**
	- **为什么适合**：游戏和引擎的设置（如图形质量、音量、按键绑定）通常存储在一个全局的配置文件中。由一个单例来统一管理这些设置的读取、修改和保存，可以避免代码散落各处。
	- **职责**：解析配置文件（如INI, JSON, XML），在内存中保存配置键值对，提供 `GetInt("Graphics.ResolutionWidth")` 和 `SetFloat("Audio.MasterVolume", 0.8f)` 这样的接口，并负责将修改写回文件。

 8. **物理世界（PhysicsWorld）**（在某些设计中）
	- **为什么适合**：物理模拟需要一个统一的上下文来进行碰撞检测和刚体动力学计算。所有物理物体（刚体、碰撞体）都存在于同一个世界中。虽然物理引擎（如Box2D, Bullet）本身通常提供一个“世界”对象，但引擎封装它的管理器常常被设计为单例，以方便其他系统访问。
	- **注意**：对于复杂的多人游戏或需要多个独立物理空间的情况，这可能不适用。
