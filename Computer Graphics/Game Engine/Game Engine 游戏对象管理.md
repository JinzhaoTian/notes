## 面向对象方式

GameObject 模式，是通过继承来表达 GameObject 之间的关系，不同的 GameObject 通过继承来获得特定的功能。

- **优点**：
	- 直观
- **缺点**：
	- 无法实现功能之间的任意组合；
	- 使用多重继承会导致代码混乱，难以维护；
	- 无法实现功能的动态添加和删除。

## 组合方式

（Unity 的 GameObject-Component 模式，Unreal Engine 的 Actor-Component 模式）

- 强调组合优于继承，由 GameObject 作为统一的容器，通过插入各种组件 Component 来实现不同的功能，也是 Unity 早期使用的模式。
- **注意**：
	- 此处的 Component 与 ECS 中的 Component 不是一个概念，此处的 Component 包含了所有处理逻辑。
- **优点**：
	- 灵活性高：可以动态地为实体添加、移除组件，从而在运行时改变其行为。
	- 高度模块化：`HealthSystem` 只关心 `HealthComponent`，而不需要知道这个组件是属于玩家、箱子还是一扇门。
- **缺点**：
	- 组件间通信复杂：当一个组件需要影响另一个组件时（例如，`CollisionComponent` 检测到碰撞后需要通知 `HealthComponent` 扣血），需要引入消息/事件系统，这增加了架构的复杂性。
	- 逻辑与数据分离不彻底：虽然数据在组件里，但处理这些数据的逻辑通常仍然存在于系统中，但这些系统可能仍然需要访问多个不同的组件，导致跨内存查询。
	- 随着游戏的体量越来越大，会出现性能问题，每个 Component 由所属的 GameObject 管理，在内存上是离散存储的，因此每次需要需要遍历某一类组件时（如对于渲染系统和物理系统），必须遍历所有 GameObject，如果 GameObject 该有对应组件，再跳转到组件所在内存。内存分散会导致缓存命中率低，程序性能下降；
	- 查找特定 Component 的效率也较低。

> [!tip] 
> 组合模式在灵活性和复杂性之间取得了很好的平衡，是当今游戏引擎最实用的架构之一，尤其适合逻辑复杂、需要大量动态组合的游戏。

## ECS 方式

Entity-Component-System 模式，使用 DOP（Data Oriented Programming，面向数据编程）思想。在这种架构中，Entity 作为纯 ID 代表一个 GameObject，Component 作为纯数据，在内存中连续存储，而 System 不含数据，是处理特定种类 Component 的逻辑。通过将 Entity 的 ID 映射到不同 Component，表达 GameObject 持有不同 Component。

- **优点**：
	- **极致性能**：这是 ECS 的首要目标。通过缓存友好和并行化，可以轻松支持数万甚至数十万个游戏实体。
	- **清晰的结构**：严格的分离使得代码职责非常清晰，易于理解和测试。
	- **天生适合并行**：架构本身就减少了资源竞争，使得多线程编程更安全。
- **缺点**：
	- **高学习曲线**：思维方式与传统的 OOP 截然不同，需要时间来适应。
	- **实现复杂**：需要自己或依赖一个成熟的 ECS 库（如 EnTT, Flecs）来处理复杂的实体-组件查询和内存管理。
	- **不适用于所有情况**：对于某些需要复杂、顺序逻辑的“单例”实体（如游戏状态机），ECS 可能显得笨重。
	- **组件间通信更困难**：由于系统是独立运行的，一个系统如何影响另一个系统管理的组件需要严格的定义（通常通过命令缓冲或事件）。
