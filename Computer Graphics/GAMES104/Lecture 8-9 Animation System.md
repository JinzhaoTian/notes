游戏动画系统是游戏引擎中技术复杂度最高的模块之一。它需要在极其严苛的实时性能约束下，将静态的三维模型驱动成栩栩如生、能与环境交互的角色。

## 动画的本源与核心挑战

### 动画的基本原理

动画的本质是利用人眼的**视觉暂留效应 (Persistence of Vision)**，通过快速连续播放一系列静态图像，制造出运动的幻觉。

**关键参数**：人眼在观察一个物体后，其影像会在视网膜上保留约 $\frac{1}{24}$ 秒。现代显示设备利用这一特性，以 24fps / 30fps / 60fps 等频率刷新画面，形成流畅动画。

**游戏动画的历史脉络**：

| 阶段 | 代表作品 | 核心技术 | 特点 |
|------|----------|----------|------|
| 2D 精灵 | 《波斯王子》(1989) | 转描 (Rotoscoping) + 逐帧绘制 | 动作流畅，利用真人拍摄逐帧描绘 |
| 伪3D | 《DOOM》(1993) | 光线投射场景 + 多角度2D精灵 | 根据摄像机角度切换精灵集合 |
| 早期3D | 初代《生化危机》 | 刚性骨骼，直接驱动部件 | 关节处生硬，容易穿模 |
| 蒙皮时代 | 现代3A游戏 | 蒙皮动画 + 动捕 + 物理 | 平滑形变，高度自然感 |

**电影技术的启示**：离线渲染（《阿凡达》）→ Motion Capture（《阿丽塔》）→ 实时渲染电影（游戏引擎驱动），实时化是动画制作的未来方向。

### 现代游戏动画系统的三大核心挑战

#### 性能挑战 (Performance Challenge)

- **时间预算**：所有计算（渲染、物理、AI、**动画**）必须在 $\frac{1}{30}s \approx 33.3ms$ 或 $\frac{1}{60}s \approx 16.67ms$ 内完成
- **资源竞争**：动画系统与渲染、物理、AI 共同争夺有限的 CPU/GPU 资源
- 随着同屏角色数量增加，大量骨骼更新和蒙皮计算会带来巨大性能压力

#### 数据挑战 (Data Challenge)

- **数据量庞大**：高精度角色动画产生海量数据（大量 Animation Clip）
- **内存访问模式不友好**：动画计算常需不连续读取内存，导致严重的 **Cache Miss**
- 关键解决方案：**动画压缩 (Animation Compression)**

#### 真实感挑战 (Realism Challenge)

| 挑战 | 描述 | 前沿解决方案 |
|------|------|--------------|
| **自然交互** | 角色需流畅响应实时输入，而非播放预设"罐头"动画 | Motion Matching（实时在大型数据库中匹配最佳片段） |
| **物理互动** | 角色需与环境产生符合物理规律的互动 | 基于物理的动画 (Physics-Based Animation) |
| **面部表情** | 人类对表情极度敏感，微小不自然即被察觉 | 高密度面部关节 + Morph Target |
| **高保真虚拟人** | 4K/8K/VR 需求下期望与真人无异的虚拟角色 | 全套现代动画管线 |

## 2D 动画技术

### 精灵动画 (Sprite Animation)

**核心原理**：将角色或物体的连续动作逐帧绘制成一系列独立图片，在游戏中按顺序循环播放，即"快速翻动画册"。

**经典演进**：

- **《超级马里奥》**：只有两张图片来回翻转 (Flipping)，即创造出生动的行走动画——极致的资源优化
- **《DOOM》**：为角色在多个视角（正面/侧面/背面）各制作一套精灵序列，引擎根据摄像机相对角度选择对应序列，制造3D错觉

**现代引擎中的应用**：精灵动画在**粒子系统 (Particle System)** 中焕发新生。

```
每个粒子 = 一个独立的序列帧动画 (Flipbook)
烟雾粒子 = 由小变大、逐渐消散的帧序列
成千上万粒子组合 → 逼真动态烟雾/爆炸/魔法特效
```

### Live2D：赋予 2D 角色生命力

Live2D 是一套革命性的 2D 动画方案，通过对静态图片进行拆分和变形，以 2D 成本实现媲美 3D 的流畅动画，广泛应用于二次元和卡牌游戏。

> [!tip] Live2D 的精髓
> **"拆分—网格化—变形"**：将复杂的 3D 动画流程简化为艺术家友好的 2D 操作，实现低成本、高表现力的角色动画。

**核心技术流程**：

1. **部件拆分 (Decomposition)**：将角色拆分成独立图层（头发、眼睛、嘴唇、身体等），称为**图源**
2. **深度排序 (Depth Sorting)**：为每个图源设置深度值，正确处理遮挡关系
3. **网格化与变形 (Meshing & Warping)**：
   - 为每个图源创建**控制网格 (Control Mesh)**并添加**控制点 (Control Points)**
   - 移动控制点扭曲/拉伸网格，产生平滑形变
   - 底层实现：对三角形进行**仿射变换 (Affine Transformation)**
4. **关键帧动画 (Keyframe Animation)**：在不同时间点设置所有图源的变换状态，系统自动插值

| 优点 | 说明 |
|------|------|
| **艺术家友好** | 无需掌握复杂的3D建模和绑定知识 |
| **表现力强** | 能以2D成本实现细腻的角色表情和动作 |
| **生态成熟** | Unity、Unreal等主流引擎广泛支持 |

## 3D 动画技术基础

### 自由度 (Degree of Freedom, DOF)

> [!important] DOF 是所有动画系统的基础
> 动画的本质就是控制物体在各个自由度上的状态随时间变化。

**刚体的 6-DOF**：

| 自由度类型 | 轴 | 数量 |
|------------|-----|------|
| **平移 (Translational DOF)** | 沿 X, Y, Z 轴移动 | 3 |
| **旋转 (Rotational DOF)** | 围绕 X, Y, Z 轴旋转 | 3 |

*应用：6-DOF VR 眼镜可同时追踪头部平移和旋转*

### 游戏中的动画技术分类

#### 顶点动画 (Vertex Animation)

直接驱动模型上每一个顶点的位置来产生动画效果。

**实现方式：顶点动画纹理 (Vertex Animation Texture, VAT)**

将动画数据"烘焙"到纹理中：

| 纹理 | U 轴 | V 轴 | RGB 像素值 |
|------|------|------|------------|
| **位置纹理 (Position Texture)** | 顶点索引 (Vertex ID) | 动画帧号 (Frame Number) | 该顶点在该帧的位置**偏移量** |
| **法线纹理 (Normal Texture)** | 顶点索引 (Vertex ID) | 动画帧号 (Frame Number) | 该顶点在该帧的**表面法线** |

**工作流程**：
```
离线：物理/动画软件模拟 → 每帧每顶点的位置+法线数据 → 写入两张纹理
实时：顶点着色器根据当前时间和 Vertex ID → 采样纹理 → 获取偏移量和法线 → 应用到模型
```

**应用场景**：飘扬的旗帜、流动的水面/瀑布、弹幕特效（骨骼难以表达的复杂形变）

#### 变形目标动画 (Morph Target Animation)

在多个预定义的**关键姿态 (Key Pose)** 之间进行权重插值，直接在不同网格形状之间混合。

| 特点 | 描述 |
|------|------|
| **不使用骨骼** | 直接在不同网格形状之间插值 |
| **主要应用** | 角色面部表情（喜/怒/哀/乐）；游戏捏脸系统 |
| **优势** | 比骨骼缩放产生更自然的效果，尤其是面部 |

*游戏捏脸系统原理：调整"蒜头鼻""高尖鼻"等特征时，背后是多个 Morph Target 在进行权重混合*

#### 蒙皮动画 (Skinned Animation)

**现代游戏中针对角色（人、动物）最主流的动画技术。**

**核心思想**：用一套内部的刚性**骨骼 (Skeleton)** 驱动外部的柔性**皮肤 (Mesh)**。每个顶点同时受多根骨骼影响，每根骨骼的影响力由**权重 (Weight)** 决定。

**核心优势**：
- 解决了早期单骨骼影响导致的刚性、机器人般的运动
- 保证关节处平滑过渡，不穿插不撕裂，保持模型的**水密性 (Watertight)**

> [!note] 蒙皮的跨领域应用
> 2D 动画（Spine, Live2D）也借鉴了蒙皮思想——为 2D 图片部件建立网格和骨骼并刷写权重，背后的数学与 3D 完全一致。

#### 基于物理的动画 (Physics-Based Animation)

利用物理模拟实时生成或增强动画效果，使其对环境和外力做出逼真、不可预测的反应。

| 技术 | 描述 | 关键点 |
|------|------|--------|
| **布娃娃系统 (Ragdoll)** | 角色死亡/击倒时切换到纯物理模拟 | 现代趋势：动画+物理混合，避免"沙袋感" |
| **布料/流体模拟 (Cloth/Fluid)** | 模拟衣物飘动或水体流动 | 游戏物理中最具挑战性的部分 |
| **反向动力学 (Inverse Kinematics, IK)** | 给定末端目标点，反向计算各关节旋转 | 实现手扶墙壁、脚踩高低不平地面的关键技术 |

> [!tip] IK vs FK
> **正向动力学 (FK)**：给定骨骼旋转 → 得到末端位置（动画师手K常用）
> **反向动力学 (IK)**：给定末端目标点 → 计算各关节旋转（环境交互关键）

### 动画创作流程 (Animation Creation)

| 方式 | 描述 | 特点 |
|------|------|------|
| **手K动画 (Keyframe)** | 动画师在3D软件中手动设置关键帧，软件自动生成中间帧 | 最传统，最考验动画师功底 |
| **运动捕捉 (Motion Capture, Mocap)** | 光学/惯性设备捕捉真人演员动作，驱动虚拟骨骼 | 高效产出极其逼真自然的动画，3A游戏标准 |

## 蒙皮动画核心原理

### 坐标系层次

> [!important] 变换流程核心
> 动画数据的计算是"自下而上"的累积过程：骨骼局部空间 → 逐级累积 → 模型空间 → 世界空间

#### 三个关键坐标系

| 坐标系 | 定义 | 原点 | 转换关系 |
|--------|------|------|----------|
| **局部坐标系 (Local Space)** | 每根骨骼/关节专属。定义单个关节相对其父关节的变换 | 父关节位置 | Animation Clip 存储的就是这一层 |
| **模型坐标系 (Model Space)** | 以角色模型自身为中心的坐标系 | Root 骨骼位置 | 从根关节开始，逐级累积相乘各局部变换（正向动力学） |
| **世界坐标系 (World Space)** | 整个游戏场景的全局唯一坐标系 | 场景原点 | 对角色整体施加 Model Transform（由游戏逻辑控制） |

**完整变换链**：
```
关节局部变换 (Local Space)
  → 累积计算 (FK 正向动力学)
  → 关节模型空间姿态 (Model Space)
  → 应用角色世界变换 (Model Transform)
  → 关节世界空间姿态 (World Space)
  → 视图变换 + 投影变换
  → 渲染输出
```

### 骨骼系统 (Skeleton)

#### 骨骼层级结构

骨骼系统是一个**树状层级 (Tree Structure)**：唯一根节点，其他骨骼通过父子关系链接。

**人形骨骼 (Biped) 的解剖学起点**：通常是**胯部 (Pelvis)**——向上分支出脊柱和手臂，向下分支出双腿。

**标准化意义**：统一骨骼结构使动画资源（尤其是 Mocap 数据）可以在不同角色间复用和迁移。

| 骨骼类型 | 说明 |
|----------|------|
| **Biped（两足生物）** | 人类等双足角色，有业界通用的标准骨骼结构 |
| **Quadruped（四足动物）** | 马、怪兽等四足角色，骨骼结构与 Biped 有显著不同 |

#### 关节 (Joint) vs. 骨骼 (Bone)

> [!important] 底层操作的是关节，不是骨骼
> 尽管日常交流中习惯将两者混称为 "Bone"，理解其本质差异对于实现动画系统至关重要。

| 概念 | 定义 | 自由度 | 存储数据 |
|------|------|--------|----------|
| **关节 (Joint)** | 变换节点，拥有位置、旋转、缩放等数据 | 有 DOF（如肘关节可旋转） | 是动画数据的存储和驱动单元 |
| **骨骼 (Bone)** | 连接两个关节的刚性连杆 | 无 DOF（由两端关节决定姿态） | 不存储独立数据 |

*为什么存储关节？蒙皮计算需要关节的变换；手臂扭转等形变效果的根源也是关节的变换差异。*

#### 游戏引擎中的实用骨骼扩展

| 扩展类型 | 说明 |
|----------|------|
| **面部骨骼** | 头部增加数十甚至上百个微小关节，控制眉毛、眼睛、嘴唇 |
| **附件骨骼** | 翅膀、斗篷、长发、裙摆等飘逸物的骨骼链条 |
| **武器挂点 (Weapon Mount)** | 手部专用武器关节，武器"挂"上去后自动跟随手的运动 |
| **骑乘骨骼 (Mount Point)** | 角色骑乘时，角色根节点挂载到坐骑的对应挂点上 |

#### 特殊的 Root 骨骼

**Root 骨骼**是游戏引擎在解剖学骨骼之外定义的最顶层骨骼，通常位于角色**双脚之间的地面上**。

> [!tip] Root 骨骼的作用
> 类比：Root 骨骼就像是手办（模型）下方的支架——无论手办摆出什么姿势，移动的都是那个支架。

**核心功能**：
- **逻辑分离**：将动画驱动的运动（原地跑步动作）与游戏逻辑驱动的位移（世界中实际移动）解耦
- **简化定位**：判断角色离地高度、处理跳跃逻辑等，只需操作 Root，无需关心内部骨骼动画状态

*实践案例（四足动物）：马的 Pelvis 在解剖学位置（尾椎），但 Root 放在腹部正下方，作为整体位置的逻辑中心点。*

### 绑定姿势 (Bind Pose)

为模型绑定骨骼时所用的标准初始姿势：

| 姿势 | 描述 | 优/缺点 |
|------|------|---------|
| **T-Pose** | 双臂水平伸直，呈"T"字形 | 早期行业标准；肩部被拉伸，肩部动画变形精度差 |
| **A-Pose** | 双臂自然下垂，与身体呈"A"字形 | 现代3A趋势；更接近自然站姿，肩部变形精度更高 |

### 绑定动画 (Bound Animation)

**绑定动画**实现角色与载具（如马、汽车）的交互同步。

**实现机制**：
1. **匹配关节**：在两个模型的交互点各创建一个"空关节"（如马鞍上和骑手臀部各一个关节）
2. **完全对齐**：绑定瞬间，两个关节的位置 (Position) 和旋转 (Rotation) 完全对齐（坐标系贴合）
3. **父子关系**：将角色根节点设为载具关节的子节点，载具的所有运动自动传递给角色

*经典案例：玩家角色执行上车动画，当角色接触座椅的那一帧触发绑定，此后汽车行驶/颠簸/转弯角色均随之而动。*

### 蒙皮动画的实现流程

```
1. 建模 (Modeling)
   └── 美术师创建静态网格（Mesh），初始姿态称为"绑定姿势 (Bind Pose)"

2. 创建骨骼 (Skeleton Creation)
   └── 在模型内部创建符合结构的骨骼层级

3. 刷权重 (Skinning / Weight Painting)
   └── 为每个顶点指定受哪些骨骼影响及各自的权重

4. K帧 (Animation)
   └── 动画师通过旋转/移动骨骼制作动画序列

5. 驱动顶点 (Vertex Deformation)
   └── 引擎每帧根据当前骨骼姿态和权重，实时计算每个顶点最终位置
```

> [!note] 实现陷阱
> 蒙皮动画涉及复杂的矩阵变换，在顶点着色器 (Vertex Shader) 中实现时，一个微小的公式错误或矩阵顺序颠倒，都会导致**模型被写炸 (Exploded Mesh)**——顶点飞散到屏幕各处。这是初学者最常见的"噩梦"。

## 旋转的数学表达

### 姿势 (Pose) 与自由度

**姿势 (Pose)**：骨骼动画在某一帧的静态快照，定义了该时刻所有骨骼的局部变换信息。

每个骨骼（关节）的变换由 **9个自由度** 构成：

| 变换类型 | 分量 | DOF |
|----------|------|-----|
| **平移 (Translation)** | X, Y, Z | 3 |
| **旋转 (Rotation)** | 绕 X, Y, Z 轴 | 3 |
| **缩放 (Scale)** | X, Y, Z | 3 |

*缩放在写实骨骼动画中不常用，但在卡通弹性 (Squash and Stretch) 和面部夸张变形中非常有用。*

### 欧拉角 (Euler Angles)

**核心思想**：将任意三维旋转分解为三次绕标准坐标轴（X, Y, Z）的连续旋转，角度分别为 $\alpha, \beta, \gamma$（即常说的 Roll, Pitch, Yaw）。

**单轴旋转矩阵**（以绕 X 轴旋转 $\alpha$ 角为例）：

$$R_x(\alpha) = \begin{pmatrix} 1 & 0 & 0 \\ 0 & \cos\alpha & -\sin\alpha \\ 0 & \sin\alpha & \cos\alpha \end{pmatrix}$$

类似地可以写出 $R_y(\beta)$ 和 $R_z(\gamma)$。

**组合旋转**（旋转顺序 Z→Y→X）：

$$R = R_z(\gamma) \cdot R_y(\beta) \cdot R_x(\alpha)$$

**现实世界应用（航空航天）**：

| 欧拉角 | 旋转轴 | 描述 |
|--------|--------|------|
| **Yaw（航向角）** | 垂直轴 | 决定飞行器朝向（左右转向） |
| **Pitch（俯仰角）** | 横轴 | 决定机头上扬或下俯 |
| **Roll（翻滚角）** | 纵轴 | 决定机身左右倾斜 |

**万向节 (Gimbal)**：欧拉角最完美的物理模型——三个可独立旋转的环，让内部物体保持稳定朝向。
- 相机/无人机稳定器（微云台）
- 陀螺仪惯性导航（通过测量各环角度积分推算飞行姿态）

### 欧拉角的固有缺陷

| 缺陷 | 描述 | 影响 |
|------|------|------|
| **旋转顺序依赖** | 相同角度值，不同旋转顺序得到完全不同的最终姿态 | 必须全局约定统一旋转顺序 |
| **万向节死锁 (Gimbal Lock)** | 中间轴旋转90°时，第一和第三轴的旋转轴重合，丢失一个旋转自由度 | 无法实现某些方向旋转，动画插值时产生突变 |
| **插值困难** | 对两组欧拉角进行线性插值不是最短路径的平滑旋转 | 在死锁附近产生剧烈抖动 |
| **组合困难** | 两次旋转的欧拉角不能直接相加，需转为矩阵再相乘 | 计算成本高，不直观 |
| **任意轴旋转复杂** | 绕任意轴旋转的欧拉角表达非常不直观 | 难以表达和计算 |

> [!important] 万向节死锁 (Gimbal Lock)
> 当按 X-Y-Z 顺序旋转时，若 Y 轴旋转了 90°，X 轴和 Z 轴会重合。此时无论旋转 X 还是 Z，效果相同——系统丢失了一个旋转自由度，仿佛被"锁死"。在动画插值时尤为致命，会导致旋转突变和不自然。

## 四元数 (Quaternion)

四元数是解决欧拉角所有问题的更强大数学工具，是**现代游戏引擎和动画系统的基石**。

### 历史背景

爱尔兰数学家**威廉·哈密尔顿 (William Rowan Hamilton)** 致力于寻找像复数处理二维旋转一样，用代数运算组合三维旋转的方法。复数 $a + bi$ 可优雅地表示二维旋转（乘法对应旋转叠加）。

> [!quote] 关键认知
> 哈密尔顿的突破：不是将复数扩展到三维（$a + bi + cj$，数学上行不通），而是增加两个虚数单位，共三个虚数单位 (i, j, k) 加一个实部，构成**四个分量**的四元数。灵感诞生于他走过的一座桥上。

### 基本定义

**标准形式**：

$$q = a + bi + cj + dk$$

其中 $a$ 是**实部 (Real Part)**，$b, c, d$ 是**虚部 (Imaginary Part)** 的系数。

**常见表示法**：

| 表示形式 | 符号 | 说明 |
|----------|------|------|
| 四维向量形式 | $q = [a, b, c, d]$ | 存储和计算时常用 |
| 标量-向量形式 | $q = [s, \mathbf{v}]$，其中 $s=a$，$\mathbf{v}=(b,c,d)$ | 推导运算更清晰 |

### 乘法法则

**基础定义**：

$$i^2 = j^2 = k^2 = ijk = -1$$

**循环关系（非对易）**：

$$ij = k, \quad ji = -k$$
$$jk = i, \quad kj = -i$$
$$ki = j, \quad ik = -j$$

> [!important] 非对易性的意义
> 乘法顺序改变导致结果符号相反（$q_1 q_2 \neq q_2 q_1$），恰好与三维旋转的顺序依赖性对应——先绕 X 轴再绕 Y 轴旋转，与先 Y 后 X 结果不同。

**标量-向量形式的乘法**（更简洁）：

若 $q_1 = [s_1, \mathbf{v_1}]$，$q_2 = [s_2, \mathbf{v_2}]$，则：

$$q_1 q_2 = [s_1 s_2 - \mathbf{v_1} \cdot \mathbf{v_2}, \; s_1\mathbf{v_2} + s_2\mathbf{v_1} + \mathbf{v_1} \times \mathbf{v_2}]$$

其中 $\mathbf{v_1} \cdot \mathbf{v_2}$ 为点积，$\mathbf{v_1} \times \mathbf{v_2}$ 为叉积。

### 重要属性

| 属性 | 公式 | 说明 |
|------|------|------|
| **模 (Norm)** | $\|q\| = \sqrt{a^2 + b^2 + c^2 + d^2}$ | 四元数的"长度" |
| **单位四元数** | $\|q\| = 1$ | **所有用于表示旋转的四元数必须是单位四元数** |
| **共轭 (Conjugate)** | $q^* = a - bi - cj - dk = [s, -\mathbf{v}]$ | 虚部取反 |
| **逆 (Inverse)** | $q^{-1} = q^* / \|q\|^2$ | 通用公式 |
| **单位四元数的逆** | $q^{-1} = q^*$ | **对单位四元数，逆 = 共轭**（极大简化计算！） |

> [!tip] 单位四元数求逆的高效性
> 矩阵求逆计算复杂；而对单位四元数，求逆只需对虚部取反——几次乘以 -1 即可完成。这是四元数在动画系统中高性能的重要原因。

### 用四元数表示旋转

#### 轴-角 (Axis-Angle) 到四元数

绕单位向量轴 $\mathbf{v} = (v_x, v_y, v_z)$ 旋转 $\theta$ 角度，对应的四元数：

$$q = \left[\cos\frac{\theta}{2}, \; \mathbf{v} \cdot \sin\frac{\theta}{2}\right]$$

即：

$$a = \cos\frac{\theta}{2}, \quad b = v_x \sin\frac{\theta}{2}, \quad c = v_y \sin\frac{\theta}{2}, \quad d = v_z \sin\frac{\theta}{2}$$

> [!note] 为什么是 θ/2？
> 这是四元数旋转公式 $p' = qpq^{-1}$ 的数学要求——双重乘积结构中每个 $q$ 贡献 $\theta/2$，合计恰好旋转 $\theta$。

#### 执行旋转："三明治乘积"

使用四元数 $q$ 对三维点 $P = (x, y, z)$ 进行旋转：

**步骤 1**：将点 $P$ 表示为**纯四元数 (Pure Quaternion)**（实部为 0）：
$$p = [0, (x, y, z)]$$

**步骤 2**：执行旋转（三明治乘积）：
$$p' = q \cdot p \cdot q^{-1}$$

**步骤 3**：提取结果，$p'$ 的虚部 $(x', y', z')$ 就是旋转后的坐标。

#### 四元数到旋转矩阵

尽管三明治乘积可以直接旋转点，在 GPU 中通常更高效的方式是：先将四元数转换为 $3 \times 3$ 旋转矩阵，再用该矩阵批量变换大量顶点（避免每个顶点都执行两次四元数乘法）。

### 四元数的核心运算

#### 反向旋转（求逆）

对旋转四元数求逆（即反向旋转），只需计算其**共轭**：

$$q^{-1} = q^* = [s, -\mathbf{v}]$$

对比矩阵求逆，计算成本极低。

#### 组合旋转（串联）

将旋转 $Q_1$ 和 $Q_2$ 依次作用，等于将对应四元数相乘：

$$Q_{total} = Q_2 \cdot Q_1$$

（注意：乘法顺序与旋转顺序相反；乘法不满足交换律）

> [!tip] 对比欧拉角
> 欧拉角组合旋转需要推导复杂三角函数公式，而四元数乘法提供了一个统一、无歧义的框架来叠加任意数量的旋转。

#### 构造"从 U 到 V 的旋转"

给定两个方向向量 $\mathbf{U}$ 和 $\mathbf{V}$，构造代表该旋转的四元数：

$$\text{旋转轴}\ \mathbf{W} = \mathbf{U} \times \mathbf{V}$$
$$\text{实部}\ w = 1 + \mathbf{U} \cdot \mathbf{V}$$

将 $(w, \mathbf{W})$ 归一化即得最终单位四元数。

### 四元数的核心优势总结

| 优势 | 描述 |
|------|------|
| **避免奇异点** | 彻底解决欧拉角的万向节死锁问题，旋转平滑稳定 |
| **无歧义性** | 对于确定的空间姿态，单位四元数表示唯一（$q$ 和 $-q$ 代表相同旋转） |
| **高效组合旋转** | 多个旋转叠加只需四元数连乘，比矩阵链乘更简洁 |
| **高效求逆** | 单位四元数的逆 = 共轭（只需虚部取反） |
| **高效插值 (Slerp)** | 在两个旋转之间进行球面线性插值，得到最短路径上的均匀过渡 |
| **数学简洁性** | 将旋转问题从三角函数领域转化为线性代数，结构更清晰 |

> [!important] 为什么四元数是动画系统的基石
> 旋转是游戏动画最核心的操作。四元数解决了欧拉角在插值、组合和奇异点方面的全部问题，以4个浮点数（比 $3\times3$ 矩阵的9个更紧凑）高效表示任意三维旋转。它是现代游戏引擎、机器人学、航天工程中处理旋转问题的标准工具。

## 关节姿态与仿射矩阵

### 关节姿态 (Joint Pose) 的三大核心元素

描述一个关节在任意时刻的状态称为**姿态 (Pose)**，由旋转、平移、缩放三种基本变换组成。

#### 旋转 (Rotation / Orientation)

旋转是骨骼动画中**最核心、最基本的变换**。绝大多数关节间的相对运动都只涉及旋转。

- **Orientation（朝向）**：更专业的术语，特指关节在三维空间中的朝向
- **四元数 (Quaternion)**：引擎中表示旋转的标准工具——避免 Gimbal Lock，便于 Slerp 球面插值

#### 平移 (Translation / Position)

大多数情况下，子关节相对于父关节的平移是**固定的**（骨骼长度不变）。但在特定场景下至关重要：

| 应用场景 | 说明 |
|----------|------|
| **根骨骼移动** | 角色蹲下/站起时，Pelvis 相对 Root 的位置发生平移变化 |
| **面部动画** | 嘴唇、眉毛等部位的细微动作包含大量平移 |
| **特殊机械结构** | 如弩箭发射时弓弦骨骼的显著平移 |

#### 缩放 (Scale)

缩放通常**非动画**，默认值恒为 (1, 1, 1)。特定艺术效果中有用：

| 应用场景 | 说明 |
|----------|------|
| **面部塑形** | "大眼睛"、"高鼻梁"等效果，通过**非均匀缩放 (Non-uniform Scale)** 实现 |
| **卡通弹性** | Squash and Stretch 效果、呼吸时胸腔的轻微缩放 |

### 关节姿态的数学表达：仿射矩阵 (Affine Matrix)

将旋转、平移、缩放统一为一个矩阵，是引擎对顶点进行骨骼动画计算的核心数据结构。

**矩阵形式**（$3 \times 4$ 格式）：

$$\begin{bmatrix} R'_{xx} & R'_{xy} & R'_{xz} & T_x \\ R'_{yx} & R'_{yy} & R'_{yz} & T_y \\ R'_{zx} & R'_{zy} & R'_{zz} & T_z \end{bmatrix}$$

其中 $R' = R \cdot S$（旋转矩阵与缩放矩阵的乘积）。

> [!tip] 仿射矩阵 vs. 投影矩阵
>
> | 类型 | 用途 | 特点 |
> |------|------|------|
> | **仿射矩阵 (Affine)** | 骨骼变换 | 保持线条平行性；最后一行是 $[0,0,0,1]$，无需透视除法 |
> | **投影矩阵 (Projection)** | 相机渲染 | 产生透视效果；最后一行非 $[0,0,0,1]$，需要除以 $w$ |

### 局部空间存储与插值的必要性

> [!important] 核心原则
> 动画数据（每帧每关节的 Pose）**总是存储和计算在局部空间 (Local Space)** 中——每个关节的变换是相对于其父关节的。

**计算流程**（正向动力学 FK）：

$$M_{model} = M_{parent\_model} \times M_{child\_local}$$

从根节点开始，自顶向下逐级累乘，得到每个关节在模型空间的最终姿态。

**为什么不能在模型空间插值？**

| 方式 | 描述 | 结果 |
|------|------|------|
| **模型空间位置插值**（错误） | 直接对手腕的模型空间坐标线性插值 | 手腕走直线，骨骼被拉伸/压缩（橡皮筋效果）❌ |
| **局部空间旋转插值**（正确） | 对局部旋转四元数进行 Slerp 插值 | 手腕绕手肘做圆弧运动，骨骼长度不变 ✅ |

## 蒙皮矩阵 (Skinning Matrix) 推导

### 核心不变性原则

**蒙皮的本质**：维持顶点与骨骼之间的相对关系不变。

> [!quote] 不变性恒等式
> 顶点在骨骼局部空间中的位置（绑定时） = 顶点在骨骼局部空间中的位置（任意动画帧）

### 单骨骼影响的数学推导

**定义变量**：

| 变量 | 含义 |
|------|------|
| $V_{bind}$ | 顶点在绑定姿态下，在**模型空间**的原始位置 |
| $M_{bind}$ | 骨骼在绑定姿态时，**模型空间**变换矩阵 |
| $V_{local}$ | 顶点在骨骼**局部空间**的不变坐标 |
| $V_{anim}$ | 顶点在当前动画帧，在**模型空间**的新位置 |
| $M_{anim}$ | 骨骼在当前动画帧，**模型空间**变换矩阵 |

**绑定时的关系**：

$$V_{bind} = M_{bind} \cdot V_{local}$$

$$\Rightarrow V_{local} = (M_{bind})^{-1} \cdot V_{bind}$$

$(M_{bind})^{-1}$ 即**反向绑定矩阵 (Inverse Bind Pose Matrix)**——将模型空间顶点变换到骨骼局部空间。

**任意动画帧**（将 $V_{local}$ 代入）：

$$V_{anim} = M_{anim} \cdot V_{local} = M_{anim} \cdot (M_{bind})^{-1} \cdot V_{bind}$$

> [!important] 蒙皮计算基础公式
> $$V_{anim} = \underbrace{M_{anim} \cdot (M_{bind})^{-1}}_{\text{蒙皮矩阵}} \cdot V_{bind}$$
> 这是驱动所有骨骼动画顶点变形的**最底层数学原理**。

### 蒙皮矩阵 (Skinning Matrix)

将公式中与顶点无关、仅与骨骼当前状态相关的部分提炼出来：

$$\text{SkinningMatrix}_J = M_{anim\_J} \cdot (M_{bind\_J})^{-1}$$

有了蒙皮矩阵，顶点位置的计算变为：

$$V_{anim} = \text{SkinningMatrix}_J \cdot V_{bind}$$

**关键优化**：$(M_{bind})^{-1}$ 是**不变量**，在模型美术制作导出后就固定了。应在**加载模型资源时预计算**并存储，运行时直接使用。

### 矩阵调色板 (Matrix Palette)

> [!tip] 避免在着色器中重复计算蒙皮矩阵
> 如果在 Vertex Shader 中为每个顶点都重新计算蒙皮矩阵，将是巨大的性能浪费。

**工作流程**：

```
CPU（每帧）
  └── 遍历所有骨骼 → 计算每根骨骼的 SkinningMatrix
  └── 所有矩阵组成数组（Matrix Palette）→ 一次性上传到 GPU

GPU（Vertex Shader）
  └── 每个顶点根据 BoneIndex → 从 Palette 中取对应矩阵
  └── 与原始位置 V_bind 相乘 → 得到最终位置
```

### 扩展到世界空间

引擎最终需要顶点在**世界空间 (World Space)** 的位置：

$$\text{FinalSkinningMatrix} = M_{World} \cdot M_{anim} \cdot (M_{bind})^{-1}$$

其中 $M_{World}$ 是模型的 Model-to-World 变换矩阵。这个 `FinalSkinningMatrix` 就是传入 Shader 的矩阵调色板内容。

### 平滑蒙皮 (Smooth Skinning / Linear Blend Skinning, LBS)

现实中，关节处的顶点受**多根骨骼共同影响**，各骨骼的影响力由权重决定。

**公式**：

$$V_{anim} = \sum_{i=1}^{n} w_i \cdot \text{SkinningMatrix}_i \cdot V_{bind}$$

**关键约束与限制**：

| 约束 | 说明 |
|------|------|
| **权重和为 1**（$\sum w_i = 1$） | 违反此约束会导致模型非预期缩放、拉伸或撕裂 |
| **每顶点最多 4 根骨骼影响** | 引擎实践中的性能/效果权衡（存储、计算的经典上限） |

> [!important] 必须在模型空间进行混合
> **绝对不能**在各骨骼的局部空间中插值混合——每个骨骼的局部空间坐标系不同，在不同坐标系下加权平均毫无数学意义，会产生完全错误的结果。正确做法：先将顶点变换到统一的**模型空间**，再执行加权混合。

## 动画插值 (Animation Interpolation)

动画数据由离散关键帧组成，需在关键帧之间插值，以在任意时刻生成平滑姿态。

**动画片段 (Animation Clip)**：一组描述特定动作（行走/跑步/跳跃）的连续姿态序列，是完整的动画资产。

**不同分量的插值策略**：

| 分量 | 推荐方法 | 原因 |
|------|----------|------|
| **平移 (Translation)** | LERP 线性插值 | 计算开销小，效果良好 |
| **缩放 (Scale)** | LERP 线性插值 | 同上 |
| **旋转 (Rotation)** | 四元数插值（NLERP / SLERP） | 直接对欧拉角或矩阵 LERP 会产生严重问题 |

### NLERP（标准化线性插值）

$$q_{result} = \text{normalize}((1-t) \cdot q_1 + t \cdot q_2)$$

先对两个四元数线性插值，再**标准化 (Normalize)** 确保结果仍是单位四元数。

| 优点 | 缺点 |
|------|------|
| 计算速度非常快 | 旋转**不匀速**（角速度先快后慢或先慢后快） |

### SLERP（球面线性插值）

$$q_{result} = \frac{\sin((1-t)\Omega)}{\sin\Omega} q_1 + \frac{\sin(t\Omega)}{\sin\Omega} q_2$$

其中 $\Omega$ 是两个四元数之间的夹角（$\cos\Omega = q_1 \cdot q_2$）。

沿 4D 超球面上的**最短大圆弧**插值，保证**恒定角速度**。

| 优点 | 缺点 |
|------|------|
| 旋转匀速自然，动画质量高 | 包含 $\arccos$ 和 $\sin$，计算昂贵 |
| | $\Omega \to 0$ 时出现除零数值不稳定 |

### 旋转插值的"最短路径"问题

四元数中 $q$ 和 $-q$ 代表**相同的旋转**，但从 $q_1$ 插值到 $q_2$ 与插值到 $-q_2$ 路径不同（一短一长），会导致关节非预期翻转。

**解决方案**：插值前检查点积，选择最短路径：

```cpp
if (dot(q1, q2) < 0) {
    q2 = -q2;  // 切换到最短路径
}
// 然后再执行 SLERP 或 NLERP
```

### 工业界实用混合方案

```
计算 dot(q1, q2)
  ├── dot > 0.999（夹角极小）→ 使用 NLERP（快速，误差可忽略）
  └── 否则                   → 使用 SLERP（质量优先）
```

既避免了不必要的性能开销，又规避了 SLERP 在近似相等时的数值不稳定问题。

## 实时动画渲染管线 (Runtime Animation Pipeline)

```
[CPU] 1. 数据准备
         └── 从 Animation Clip 库中加载当前动画数据

[CPU] 2. 姿态计算
         ├── 根据当前时间，找前后两个关键帧 (Keyframes)
         ├── LERP/NLERP/SLERP 计算当前帧的骨骼局部姿态 (Local Pose)
         └── FK 正向动力学：遍历骨骼层级 → 计算模型空间姿态 (Model Space Pose)

[CPU] 3. 蒙皮矩阵调色板生成
         └── 对每根骨骼：SkinningMatrix = M_World * M_anim * (M_bind)^-1
         └── 组合成数组（Palette）→ 上传 GPU

[GPU] 4. 顶点着色与蒙皮 (Vertex Shader)
         └── 每顶点根据 BoneIndex + Weight → 从 Palette 取矩阵 → 加权变换
```

> [!tip] 发展趋势：GPU Driven
>
> | 方式 | 描述 |
> |------|------|
> | **传统做法** | 步骤 1-3 在 CPU 完成，步骤 4 在 GPU |
> | **现代3A引擎** | 整个动画更新流程（含姿态计算、矩阵生成）都移到 GPU（Compute Shader） |
>
> GPU Driven 极大减轻 CPU 负担，使其专注于游戏逻辑和 AI，是当前的主流发展方向。

## 动画压缩 (Animation Compression)

### 压缩的必要性

未经压缩的原始动画数据量极其庞大。**粗略估算（以 LOL 规模为例）**：

$$150\ \text{英雄} \times 10\ \text{动画} \times 5\ \text{秒} \times 30\ \text{fps} \times 70\ \text{关节} \times 9\ \text{DOF/关节} \approx \mathbf{2\text{-}3\ GB}$$

> [!important] 动画压缩不是可选项
> 对于任何商业级游戏，动画压缩是**必须攻克的难关**，而非锦上添花的优化。

### 动画数据特性分析

| 数据类型 | 特性 | 压缩策略 |
|----------|------|----------|
| **缩放 (Scale)** | 绝大多数骨骼整个动画中恒为 (1,1,1) | 直接剔除轨道，存储常量 |
| **平移 (Translation)** | 局部空间下，大多数子骨骼平移固定（骨骼长度不变） | 直接剔除轨道，存储常量 |
| **旋转 (Rotation)** | 动画绝大部分动态信息体现于此 | **重点压缩对象** |

### 核心压缩技术一：轨道剔除与关键帧

#### 轨道剔除 (Track Removal)

移除整个动画片段中保持不变的数据轨道（大部分骨骼的 Scale 和 Translation），只存储一个常量值。效果立竿见影。

#### 关键帧 (Keyframing)

原始数据按固定频率（30Hz）采样，包含大量冗余中间帧。只保留"关键"帧，运行时通过插值还原中间帧。

**Marching 算法（关键帧选取）**：

```
1. 第一帧作为第一个关键帧
2. 向前遍历：用当前关键帧与前方采样点做线性插值
3. 计算插值结果与原始数据的误差
4. 误差 > 阈值 → 将前一个采样点设为新关键帧，从此处重新开始
5. 重复直至末帧
```

结果：运动剧烈处关键帧密集，运动平缓处关键帧稀疏（非均匀分布）。

### 核心压缩技术二：Catmull-Rom 样条插值

旋转数据是平滑曲线，简单线性插值效果不佳、压缩率低。

**Catmull-Rom 样条**是三阶多项式曲线 (Cubic Polynomial)，用**更少控制点（关键帧）**平滑拟合原始曲线：

| 特性 | 描述 |
|------|------|
| **定义** | 从 $P_1$ 到 $P_2$ 的曲线段，需前后两个额外控制点 $P_0$ 和 $P_3$ |
| **连续性** | 保证 $C^1$ 连续（切线连续），动画角速度变化平滑，无突兀停顿 |
| **张力参数 $\alpha$** | 调整曲线"锐度"，通常取 $\alpha = 0.5$ 得到标准 Catmull-Rom |
| **运行时高效** | 插值时只需多项式求值，所有曲线拟合离线完成 |

> [!tip] 对比线性插值
> 线性插值：为控制误差需大量关键帧 → 压缩率低
> Catmull-Rom：用更少关键帧达到同等甚至更高精度 → **高压缩率 + 高质量**

### 核心压缩技术三：数值量化 (Numerical Quantization)

放弃 32-bit 浮点数，改用位数更少的整数近似表示。

#### 定点数 (Fixed-Point)

将浮点数线性映射到整数范围：

```cpp
// 编码（32-bit float → 16-bit int）
uint16_t quantized = round(((value - min) / (max - min)) * 65535);

// 解码
float value = (quantized / 65535.0f) * (max - min) + min;
```

#### 四元数压缩：Biggest Three 技巧

**关键观察**：单位四元数满足 $w^2 + x^2 + y^2 + z^2 = 1$，只需知道任意三个分量就能还原第四个。

**压缩流程**：

```
1. 找出 w, x, y, z 中绝对值最大的分量
2. 存储该分量的 2-bit 索引（w=0, x=1, y=2, z=3）
3. 最大分量不存储！其余三个分量绝对值 ≤ 1/√2 ≈ 0.707
4. 利用更小范围，将三个分量各用 15-bit 定点化

解码：根据 2-bit 索引和三个量化值 → 利用约束关系还原最大分量
```

**压缩率**：

| 方式 | 存储 | 位数 |
|------|------|------|
| 原始四元数 | 4 × 32-bit float | 128 bits |
| Biggest Three 压缩 | 2 bits + 3 × 15 bits | **47 bits**（对齐后 48 bits / 6 bytes） |
| **压缩率** | — | **超过 60%** |

### 压缩的代价：误差累积 (Error Accumulation)

> [!important] 压缩是有损的，误差会沿骨骼链放大
> 骨骼动画是层级变换。子关节的最终变换 = 所有祖先关节变换的累乘结果。根骨骼的微小误差会逐级传递，在末端骨骼处被显著放大。

**视觉表现**：最常见的是**抖动 (Jittering)**，在**末端效应器 (End Effector)** 处最明显（如手中武器的尖端在角色大幅动作时剧烈、不自然地抖动）。

## 动画制作管线 (Animation Production Pipeline)

### 误差的感知差异与度量

不同骨骼对误差的**敏感度 (Sensitivity)** 天差地别：

| 区域                  | 敏感度 | 原因                        |
| ------------------- | --- | ------------------------- |
| **手持武器、手腕、脚踝等末端骨骼** | 高   | 微小误差容易被察觉；可能导致手与武器分离等穿模问题 |
| **躯干、上臂等中间骨骼**      | 低   | 视觉上不敏感                    |

**视觉误差度量方法**：

| 方法 | 描述 | 评价 |
|------|------|------|
| **暴力法** | 比较所有顶点压缩前后的三维空间位置差 | 准确但计算量巨大，不可行 |
| **业界实用法** | 在每根骨骼上定义两个带偏移的虚拟点，比较压缩前后位置变化 | 高效；可为高敏感骨骼设置大偏移以提升权重 |

### 误差补偿的悖论

> [!note] 反直觉的结论
> 让子骨骼去"补偿"父骨骼传递下来的误差，往往会产生**更糟糕**的结果。

**原因**：骨骼链各节产生不同频率的误差，末端骨骼为补偿所有上游误差，其运动数据从原本平滑的低频曲线被迫变成充满噪声的**高频曲线**——平均位置更准了，但会产生极不自然的高频抖动。

### 完整的动画制作流程

#### 1. 模型准备 (Mesh Preparation)

- 使用**低多边形模型 (Low-Poly Mesh)** 进行绑定和动画制作
- 在关节处（手肘、膝盖）有意增加**环线 (Edge Loops)**，确保弯曲时平滑过渡

#### 2. 骨架创建 (Skeleton Creation / Rigging)

- 在 DCC 工具（3ds Max / Maya）中，为 A-Pose 或 T-Pose 的角色匹配骨架（现代工具提供 Biped 模板）
- 添加**游戏性骨骼 (Gameplay Joints)**（如武器挂点）
- 添加用于 IK 解算器的辅助骨骼

#### 3. 蒙皮 / 权重绘制 (Skinning / Weight Painting)

- **自动蒙皮 (Auto-Skinning)**：工具自动计算初始权重（效果往往过于柔软，似"橡皮糖"）
- **手动校正 (Weight Painting)**：美术师像画画一样，手动为不同区域的顶点"涂"上各骨骼的影响权重，达到理想变形效果

#### 4. 动画制作 (Keyframe Animation)

- 动画师**不逐帧**调整姿态，而是在关键时刻设置**关键帧 (Keyframes)**
- 计算机自动在关键帧之间进行**插值 (Interpolation)**，生成平滑过渡

#### 5. 导出与引擎集成 (Export & Engine Integration)

引擎工程师编写导出插件，将 DCC 数据转换为引擎可识别格式（如 FBX）。

> [!important] 根骨骼位移 (Root Motion) 的正确处理
>
> **问题**：对于跳跃、前冲等改变角色世界位置的动画，根骨骼本身也会移动。
>
> **错误做法**：将根骨骼位移动画直接烘焙进动画序列。
>
> **正确做法**：将根骨骼位移信息**单独导出为位移曲线 (Displacement Curve)**。
>
> **原因**：角色实际移动由游戏逻辑（Character Controller）控制；通过应用位移曲线，确保动画步幅与角色实际移动速度完美匹配，彻底解决**脚底打滑 (Foot Sliding)** 问题。

## 高级动画技术

### 动画混合 (Animation Blending)

#### 核心问题与动机

游戏角色拥有成百上千个独立的动画片段（站立、行走、奔跑、跳跃……），若简单地在它们之间切换，会产生明显的**跳变 (Popping)** 和不连贯感。

**核心目标**：根据游戏逻辑将多个动画素材按特定规则**混合 (Blend)** 在一起，实现**无极变速 (Stepless Transition)**。

**与关键帧插值的本质区别**：

| 技术 | 插值范围 | 目的 |
|------|----------|------|
| **关键帧插值** | 单个 Clip 内部，不同时间点的帧 | 生成 Clip 内的中间帧 |
| **动画混合** | 多个不同 Clip 之间，同一时间点的姿势 | 生成不同动画之间的过渡 |

#### 权重计算

以速度驱动走→跑过渡为例：

```cpp
// 1. 归一化当前参数到 [0, 1]
float t = (current_speed - speed_walk) / (speed_run - speed_walk);
t = clamp(t, 0.0f, 1.0f);

// 2. 各动画权重
float weight_walk = 1.0f - t;
float weight_run  = t;

// 3. 最终姿势（对每个关节的旋转执行 Slerp）
FinalPose = Lerp(Pose_Walk, Pose_Run, t);
```

**关键约束**：所有参与混合的动画权重之和必须为 1。

#### 时间对齐问题 (Time Alignment)

> [!important] 时间对齐是混合正确性的前提
> 行走和奔跑的步频不同。若在任意时刻直接取两动画同一帧号混合，可能出现一个左脚在前、另一个右脚在前的情况，产生扭曲"瘸腿"效果。

**解决方案——相位归一化 (Phase Normalization)**：
- 要求动画师保证语义一致性（一个完整循环包含左右脚各迈出一次）
- 将每个循环动画的时间轴映射到 $[0, 1]$ 的**相位 (Phase)**
- 混合系统基于归一化相位采样，而非绝对时间

**不对齐的代价**：**滑步 (Ice Skating / Foot Sliding)**——脚在地面上滑动，是游戏动画中需要极力避免的问题。

### 混合空间 (Blend Space)

#### 一维混合空间 (1D Blend Space)

沿单一控制参数轴在多个动画采样点之间插值：

```
速度轴：[慢走] ---- [正常走] ---- [慢跑] ---- [快跑] ---- [冲刺]
方向轴：[左平移] ------------- [前走] ------------- [右平移]
```

- **采样点可任意数量**，且**可非均匀分布**——动作变化剧烈处密集，平缓处稀疏

#### 二维混合空间 (2D Blend Space)

两个独立控制参数定义平面，动画片段作为平面上的采样点：

```
Y轴（速度）
  ↑  [左跑] [前跑] [右跑]
  |  [左走] [前走] [右走]
  |  [左站] [前站] [右站]
  +--------------------→ X轴（方向）
```

根据当前两参数值，找到对应点所在三角形，用**重心坐标插值**计算最终姿势。

> [!note] 使用前提
> 混合空间中所有参与混合的动画片段，**循环属性必须一致**（要么全循环，要么全一次性），否则产生逻辑和视觉混乱。

#### Delaunay 三角剖分 + 重心坐标插值

**问题**：动画采样点在参数空间中**分布不均匀**；若同时混合 7-8 个动画，实时计算开销难以接受。

**解决方案**：

1. **Delaunay 三角剖分 (Delaunay Triangulation)**：将离散采样点构建成三角网格（最大化最小角，避免狭长三角形）
2. **重心坐标插值 (Barycentric Interpolation)**：在当前参数值所在的三角形内，计算三个顶点的重心权重 $(w_1, w_2, w_3)$，满足 $w_1 + w_2 + w_3 = 1$

**核心优势**：无论参数空间有多少动画片段，每次混合**最多只涉及 3 个动画片段**——极大降低实时计算复杂度。

### 高级混合技术

#### 骨骼蒙版混合 (Skeleton Mask Blending)

通过创建**蒙版 (Mask)**，指定某个动画片段只影响骨骼的特定部分：

| 典型应用 | 说明 |
|----------|------|
| 下半身播放"蹲下"，上半身同时播放"鼓掌" | 上下身完全独立控制 |
| 行走时上半身叠加"瞄准"或"挥手" | 移动与交互解耦 |

**优势**：动画组合自由度高；每个动画只更新部分骨骼，减少数据量和计算量。

#### 增量混合 (Additive Blending)

动画片段不存储**绝对骨骼姿态**，而是存储相对于参考姿态的**变化量 (Delta)**，在混合时叠加到基础动画之上。

**应用场景**：
- 在任何基础姿态（站/坐/走）上叠加"点头示意"
- 实现呼吸、持枪晃动等持续存在的细微动作

> [!note] 使用需谨慎
> **"破损"风险**：若基础动画已经是"扭头到极限"，再叠加同方向的增量动画，会导致脖子超出生理极限，表现极其怪异。需严格限制影响范围和幅度。

#### 动画混合技术工具箱总结

| 技术 | 作用 |
|------|------|
| **Blend Space** | 定义动画参数空间，实现平滑运动的基础框架 |
| **Barycentric / Bilinear 插值** | Blend Space 的核心计算方法 |
| **骨骼蒙版混合** | 实现身体局部的独立动画控制 |
| **增量混合** | 通过叠加"变化量"实现动画修饰和微调 |

### 动画状态机 (Animation State Machine, ASM)

#### 为什么需要状态机

纯粹的混合算法无法处理具有**明确先后顺序和逻辑条件**的动画序列。

**经典案例——跳跃动画的三段式**：

```
起跳 (Jump Start) ──→ 空中循环 (Jump Loop) ──→ 落地 (Landing)
    [离地瞬间]      [持续直到即将落地]      [落地缓冲]
```

这三个状态之间是有条件的单向切换，不是简单的混合关系。

#### ASM 的核心构成

**状态 (State / Node)**：动画系统的基本单元，持续输出一个动画姿势 (Pose)。

一个状态可以是：
- 单一的 Animation Clip（如 Idle、Run）
- 一个复杂的 Blend Space
- 嵌套的子状态机 (Sub-State Machine)

**转换 (Transition)**：连接两个状态的"桥梁"，定义切换规则。

| 属性 | 说明 |
|------|------|
| 起点/终点状态 | Source State → Target State |
| **触发条件 (Trigger Condition)** | "玩家按下跳跃键"、"速度 > 0"、"当前动画播放完毕"等 |
| 过渡方式 (Blending) | 平滑淡入淡出或冻结过渡 |

> [!tip] ASM 最复杂的部分
> 状态机中最复杂、最关键的往往是**转换的触发条件**——这些条件与游戏逻辑紧密耦合（玩家输入、物理状态、游戏事件），是实现复杂角色行为的关键。

#### 状态间过渡 (Fade) 方式

| 方式 | 描述 | 公式/特点 |
|------|------|----------|
| **平滑过渡 (Smooth Transition)** | 标准交叉淡化 (Cross-fade)，源权重 1→0，目标权重 0→1 | $FinalPose = (1-\alpha) \cdot Pose_A + \alpha \cdot Pose_B$ |
| **冻结过渡 (Frozen Transition)** | 源动画在过渡开始时"冻结"在当前帧，目标从此冻结姿势渐入 | 避免过渡期间源动画继续播放导致的不自然混合 |

**过渡曲线 (Transition Curve)**：

| 曲线类型 | 特点 |
|----------|------|
| **线性 (Linear)** | 权重均匀变化，效果生硬 |
| **缓入缓出 (Ease-In/Out)** | 三次函数或贝塞尔曲线，开始慢→中间加速→结束慢，最常用 |

*经验参考：常用过渡时长为 **0.2 秒***

### 动画树 (Animation Tree)

#### 从分层 ASM 到动画树

**分层动画状态机 (Layered ASM)** 是动画树的前身，将角色骨骼分为不同层（经典：上半身 / 下半身），各层独立维护一套状态机，结果叠加：

```
下半身 ASM → [移动动画：走/跑/跳]  ─┐
                                    ├─→ 叠加混合 → 最终输出
上半身 ASM → [攻击/受击/施法动画]  ─┘
```

*实例：《鬼泣5》玩家一边做复杂移动（下半身），一边流畅施展攻击连招（上半身）*

**动画树 (Animation Tree)** 是 Layered ASM 的超集，将混合过程抽象为**表达式树 (Expression Tree)**：

```
动画混合 ≈ (动画A × 权重A + 动画B × 权重B) + 加性动画C
                 ↕
          树状结构自然表达
```

> [!tip] Unreal Engine 动画蓝图
> UE 动画蓝图是业界公认的优秀实现，其核心优势是**自由嵌套**——状态机中的任何一个 State 都可以是一个 Blend Space 甚至另一个完整的 ASM，像搭积木一样自由组合。

#### 动画树的节点类型

**叶节点 (Leaf Nodes)**——动画数据来源：

| 节点 | 说明 |
|------|------|
| Animation Clip | 最基础的动画素材 |
| Blend Space | 1D 或 2D 混合空间 |
| ASM | 一个完整的状态机作为输入节点（体现递归嵌套能力） |

**中间计算节点 (Intermediate Nodes)**——对输入姿势进行处理：

| 节点 | 作用 |
|------|------|
| **Lerp / Blend Node** | 根据权重 Alpha 在两个输入姿势间插值 |
| **Additive Blending Node** | 将差量动画叠加到基础动画上 |
| **Masking Node** | 仅将输入动画应用到指定骨骼（如只影响上半身） |

#### 控制变量 (Control Variables)——动画树的"灵魂"

动画树的动态表现力来自外部游戏逻辑对其内部**控制变量**的实时驱动，如同"管道上的阀门"。

**水管类比**：
```
动画数据（叶节点）= 不同颜色的水源
动画树的节点与连线  = 复杂管道系统
混合节点           = 管道汇合处
控制变量           = 每个汇合处的阀门（决定各水源流量）
最终输出姿势        = 管道末端混合后的最终颜色
```

**控制变量的两大类型**：

| 类型 | 定义 | 示例 |
|------|------|------|
| **环境参数 (Environmental Parameters)** | 持续变化的游戏状态值，由 Gameplay 实时传入 | 移动速度、朝向方向、生命值百分比 |
| **事件 (Events)** | 离散的、瞬间发生的指令，触发动画树内部状态改变 | 玩家按"切换武器"→内部 WeaponType 从 Rifle→RocketLauncher |

### 反向动力学 (Inverse Kinematics, IK)

#### 正向动力学 vs. 反向动力学

| | 正向动力学 (FK) | 反向动力学 (IK) |
|--|-----------------|-----------------|
| **思路** | 从根到末端：给定各关节旋转 → 计算末端位置 | 从结果到原因：给定末端目标位置 → 反推各关节旋转 |
| **类比** | 按顺序移动肩膀→肘→手，决定手的位置 | 预先确定手要抓住的杯子，大脑自动计算各关节角度 |
| **局限** | 动画在"真空"中制作，无法自动适应复杂环境 | 计算复杂，需处理歧义性和关节约束 |

**末端效应器 (End Effector)**：施加目标约束的末端骨骼。

IK 在动画管线中作为**后处理 (Post-Process)** 存在：

```
动画混合（FK 基础姿态）
  → 转换到世界坐标系
  → IK 解算（根据环境约束调整骨骼链）
  → 最终姿态提交渲染器
```

#### Two-Bone IK：最简实用的解法

**核心原理**：三角形解法——大腿骨、小腿骨为三角形两边，髋关节到目标落脚点为第三边，三边长度已知，用余弦定理解出各关节角度。

**解的歧义性问题**：数学上存在无限多解（膝盖可以朝前、朝内、朝外）。

**解决方案——参考向量 (Pole Vector)**：

```
额外输入一个由美术师指定（或根据角色朝向计算）的参考向量
在解空间的圆环上，找距离参考向量最近的解
实现方式：向量点积 (Dot Product)
```

#### 关节约束 (Joint Constraints)

真实骨骼的运动范围有限，IK 求解必须尊重这些约束，否则会产生物理 Bug（肢体扭曲、关节超限旋转 360°等）：

| 关节类型 | 示例 | 自由度 |
|----------|------|--------|
| **球状关节 (Ball-and-socket)** | 髋关节、肩关节 | 多轴旋转，范围较大 |
| **铰链关节 (Hinge/Planar)** | 膝关节、肘关节、踝关节 | 通常只在 1-2 个轴向有限旋转 |
| **枢纽关节 (Pivot)** | 颈椎 | 主要绕单轴旋转 |
| **马鞍关节 (Saddle)** | 大拇指根部 | 两方向弯曲，侧向旋转受限 |

#### CCD 算法 (Cyclic Coordinate Descent)

**核心思路**：从骨骼链末端向根逐关节迭代，每个关节直接朝向目标旋转，循环直到收敛。

**算法流程**：
```
FOR 迭代次数:
    FOR 关节 j FROM 末端 TO 根:
        V_current = (末端效应器 → 当前关节 j) 的向量
        V_target  = (目标点 → 当前关节 j) 的向量
        旋转当前关节 j，使 V_current 对齐 V_target
    IF 末端效应器 足够接近目标: BREAK
```

**优化 Hacks**（避免末端关节旋转过大、姿态不自然）：
- 限制每关节单步最大旋转角度
- 越靠近根节点，旋转幅度越小（权重分配）
- 初始迭代允许较大误差范围，逐步收紧

#### FABRIK 算法 (Forward And Backward Reaching IK)

**核心思路**：不直接操作旋转，通过调整关节位置来满足骨骼长度约束，交替执行前向（末端→根）和后向（根→末端）两个阶段。

**算法流程**：

```
// 前向阶段（从末端到根）
末端效应器位置 ← 目标点
FOR 关节 j FROM 末端-1 TO 根:
    沿 j 与其子关节的连线方向，移动 j 到距子关节一个骨骼长度处

// 后向阶段（从根到末端）
根关节 ← 原始固定位置
FOR 关节 j FROM 根+1 TO 末端:
    沿 j 与其父关节的连线方向，移动 j 到距父关节一个骨骼长度处

// 循环直到末端效应器足够接近目标
```

**CCD vs. FABRIK 对比**：

| | CCD | FABRIK |
|--|-----|--------|
| **操作对象** | 旋转 | 位置 |
| **直觉** | 逐关节对齐目标 | 前后拉伸链条满足长度约束 |
| **关节约束处理** | 直接 Clamp 旋转角度 | 将超限位置投影回约束范围 |
| **实践应用** | 广泛使用 | 广泛使用，独立游戏推荐首选 |

#### 可达性判断 (Reachability Check)

在启动复杂迭代求解前，快速判断目标是否可达，避免无效计算：

```
1. 将骨骼链完全拉直 → 总长度 = Σ(各骨骼长度)
   IF 总长度 < 到目标的距离 → 不可达

2. 盲区检测（常被忽略）：
   IF 某骨骼长度 L_max > 其余所有骨骼长度之和 ΣL_others
   → 根关节附近存在无法触及的"盲区"
```

#### 雅克比矩阵 (Jacobian Matrix) 简介

当场景需要**同时控制多个末端效应器**（如攀岩时四肢都需固定在特定位置），CCD/FABRIK 会遇到"按下葫芦浮起瓢"的困境。

**雅克比矩阵**：建立"原因（关节角度变化 $\Delta\theta$）"和"结果（末端位置变化 $\Delta p$）"之间的线性关系：

$$\Delta p = J \cdot \Delta\theta$$

其中 $J$ 是末端点位置关于关节角度的偏导数矩阵（Jacobian），描述"当前姿态下，每个关节微小旋转对每个末端点位置的影响"。

**求解过程**（迭代逼近）：
```
1. 计算误差：所有末端点与各自目标的位置差距 Δp
2. 构建当前姿态下的 Jacobian 矩阵 J
3. 反向求解：Δθ = J⁻¹ · Δp（或用伪逆）
4. 应用 Δθ，更新骨骼姿态
5. 循环直到所有末端点足够接近目标
```

| 优点 | 缺点 |
|------|------|
| 能系统性处理复杂多点约束 | 构建和求解矩阵（特别是求逆）计算量巨大 |

#### IK 前沿挑战

| 挑战 | 描述 |
|------|------|
| **自相交 (Self-Intersection)** | 传统 IK 将骨骼视为无体积线段，解出的姿态可能导致肢体穿透自身 |
| **缺乏预知性 (Lack of Anticipation)** | 角色只能被动响应约束，无法像真人一样提前弯腰过低矮通道 |
| **平衡与动力学** | 传统 IK 不考虑重心，缺乏重量感，解出的姿态可能不符合物理平衡 |

**未来方向**：IK 与 AI、环境感知、物理动力学深度结合，是近十年 IK 研究论文激增的主要驱动力。

### 表情动画 (Facial Animation)

#### 核心挑战

人类面部有 **43 块肌肉**协同工作，产生极其丰富细腻的表情。**微表情 (Subtle Expressions)** 的捕捉与再现是核心难点——极其细微的肌肉牵动就能传递情感，任何不自然都会被察觉。

#### FACS 工业标准

**FACS (Facial Action Coding System)**：面部行为编码系统，将所有人类表情分解为一组有限的标准化面部肌肉动作。

**AU (Action Unit)**：动作单元，FACS 定义了 **46 个基础 AU**。

任何复杂表情 = 多个 AU 的线性组合。例如：

$$\text{惊讶} = \text{AU}_{眉毛上扬} + \text{AU}_{眼睛睁大} + \text{AU}_{嘴巴张开}$$

> [!tip] FACS 的工程意义
> FACS 将复杂的表情艺术**工程化和定量化**，是计算机生成和控制逼真面部表情的理论基础和行业标准。苹果在实践中将 46 个 AU 提炼为约 28 个核心 AU，并利用人脸对称性进一步优化。

#### Morph Target 动画（主流方案）

**核心思想**：存储每个 AU 相对于**中性面孔 (Neutral Face)** 的**顶点位移 (Vertex Offset / Delta)**，通过加权叠加生成任意表情。

**最终顶点位置公式**：

$$V_{final} = V_{neutral} + \sum_i w_i \cdot \Delta V_i$$

其中 $w_i$ 是第 $i$ 个 Morph Target 的权重，$\Delta V_i$ 是其顶点位移向量。

**解决局部控制问题**：若 AU"闭眼"只影响眼睛周围顶点，其在嘴巴区域的 $\Delta V = 0$，多个 AU 叠加时各区域互不"污染"。

#### 骨骼 + Morph Target 混合方案（3A 游戏标配）

| 技术 | 擅长场景 |
|------|----------|
| **骨骼动画** | 眼球转动、下巴开合（大幅度刚体运动）；程序化/IK 控制（视线追踪）；捏脸系统的面部结构调整 |
| **Morph Target** | 嘴唇撅起、酒窝、皱眉等柔性肌肉形变（骨骼难以精确模拟） |

两者结合：**骨骼负责大范围结构运动，Morph Target 负责表层肌肉细腻变化**。

#### 其他面部动画技术

| 技术 | 原理 | 适用场景 |
|------|------|----------|
| **纹理动画** | 将表情预渲染/绘制成纹理序列，运行时切换/混合 | 卡通渲染、风格化游戏，效率高且美术风格可控 |
| **肌肉物理模拟** | 真正模拟 43 块面部肌肉的收缩/舒张来牵动皮肤 | 目前主要用于影视特效，实时游戏尚少；未来可能替代 Morph Target |

#### 行业标杆与表情捕捉

UE MetaHuman 代表当前实时角色动画的最高水平。最大挑战是**表情捕捉 (Facial Capture)**：
- 依赖高清摄像机（不像身体动捕可绑定标记点）
- 从视频序列中解构细微的面部变化（哪块肌肉在动？），映射到 Blend Shape 权重或骨骼驱动参数
- 这是一个极其复杂的计算机视觉问题

### 动画重定向 (Animation Retargeting)

#### 核心需求

为游戏中每个体型各异的角色都制作独立动画成本极高，需要**一套动画，多个角色复用**。

**关键术语**：

| 术语 | 定义 |
|------|------|
| **源角色 (Source Character)** | 提供原始动画的角色 |
| **目标角色 (Target Character)** | 需要应用这套动画的角色 |
| **绑定姿势 (Bind Pose)** | 角色建模绑定时的初始中立姿态 |
| **相对变换 (Relative Transformation)** | 动画当前帧的姿态相对于绑定姿势的**变化量** |

#### 核心原理：传递相对旋转

> [!important] 为何不能直接应用绝对变换
> **错误示例**：驼背怪物（绑定时脖子前倾 15°），直接把女孩脖子 30° 的绝对旋转赋给怪物，怪物的脖子会"啪"地从 15° 变成 30°，丢失驼背特征。
>
> **正确做法**：
> $$\theta_{target} = \theta_{target\_bind} + (\theta_{source\_anim} - \theta_{source\_bind})$$
>
> 女孩从 0° 转到 30°，变化量 = +30°；怪物绑定 15° + 30° = 45°——保持驼背同时完成点头动作。

**实现步骤**：
1. **骨骼映射**：建立源骨骼与目标骨骼的一对一对应关系
2. **忽略绝对位置差异**：不同角色的骨骼长度、身高各异，只传递旋转变化量
3. **传递相对旋转**：将"变化量"应用到目标角色的绑定姿势上

#### 处理不同身体比例

**问题**：身高/腿长比例不同 → 脚部悬空 (Floating) 或滑步 (Foot Skating)

**启发式解决方案**：

```
// 垂直位移校正（防止悬空）
Target_Y = Animation_Y × (Target_Hip_Height / Source_Hip_Height)

// 移动速度校正（防止滑步）
Target_Speed = Source_Speed × (Target_Hip_Height / Source_Hip_Height)
```

**复杂姿态下的升级方案**：使用 **IK** 强制将脚踝锁在地面上，让 IK 解算器自动计算膝盖和臀部的弯曲角度，适配下蹲等大幅度动作。

#### 处理不同骨骼拓扑

当骨骼链中骨骼数量不一致时（如一个角色 3 根脊椎骨，另一个只有 1 根），无法简单一对一映射。

**参数化骨骼链方案（NVIDIA Omniverse 思路）**：

```
1. 找到两条骨骼链的共同起始/结束锚点（如 Pelvis → Chest）
2. 将整条链长度归一化到 [0, 1]
3. 计算源/目标骨骼链上每根骨骼对应的参数值 t
4. 对目标骨骼的每个 t 值，在源骨骼链上 t 处插值得到虚拟旋转
5. 将插值旋转应用到目标骨骼上
```

**效果**：目标骨骼链大致模拟源骨骼链的弯曲形态，保持动画整体感觉。

#### 面部动画重定向：语义约束处理

捏脸后角色面部基础网格改变，原始 Morph Target 可能无法再现语义：

| 问题 | 现象 |
|------|------|
| **眼睛闭合** | 为标准眼睛制作的"闭眼"动画应用到大眼睛角色上，顶点位移不足，眼睛无法完全闭合（似翻白眼） |
| **嘴巴紧闭** | 嘴唇厚度改变，"闭嘴"动画无法让上下嘴唇正确接触 |

**解决方案：约束点 + 拉普拉斯平滑**：

```
1. 在强语义约束区域定义成对的约束点（如上下眼睑边缘需重合的点）
2. 应用基础 Morph Target 动画
3. 强制移动约束点使其满足约束（上眼睑→下眼睑位置）
4. 对约束点周围的顶点进行拉普拉斯平滑，将突兀变化扩散为自然过渡
```

**拉普拉斯算子 (Laplacian Operator)**：局部平滑滤波器，效果如同弹性橡皮膜——拉动几个点时，周围区域随之产生平滑的连续形变。

#### 重定向的开放性挑战

| 挑战 | 描述 |
|------|------|
| **自穿插** | 瘦角色动画应用到胖角色时，手臂可能穿过身体 |
| **语义丢失** | "鼓掌"重定向到肩宽差异巨大的角色，双手可能无法合拢 |
| **物理平衡** | 重定向后可能破坏角色的重心平衡，跑/跳/推时缺乏稳定感 |

### 高级动画系统全景

| 模块 | 核心功能 | 主要技术 | 挑战深度 |
|------|----------|----------|---------|
| **混合系统** | 连接 Gameplay 与动画表现的桥梁 | ASM / Blend Tree / Blend Space | 架构设计水很深，需大量工程实践 |
| **IK** | 解决角色与环境的交互，让角色真实"存在"于世界中 | Two-Bone IK / CCD / FABRIK / Jacobian | 数学门槛高，深入需大量线性代数 |
| **表情动画** | 角色面部精细区域的表现 | Morph Target + 骨骼动画混合 | 技术实现不难，美术制作成本高 |
| **动画重定向** | "动画资产放大器"，一套动画复用到众多不同角色 | 相对旋转传递 + 比例校正 + IK | 基础实现不难，做到无瑕疵极其困难 |

> [!note] 学习路径建议
> 对于大部分项目，**FABRIK + Blend Space + 简单 ASM** 足以应对多数场景。深入研究 Jacobian Matrix 和 Full-Body IK 是进入 3A 级动画系统开发的必要台阶。Unreal Engine 的动画蓝图是目前最值得深入学习的参考实现。
