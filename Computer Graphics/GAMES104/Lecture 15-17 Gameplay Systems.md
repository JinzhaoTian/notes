Gameplay 系统（玩法系统）是游戏引擎中边界最模糊、也最直接决定玩家体验的模块。它几乎涵盖了除底层渲染、物理之外的所有上层逻辑，是连接玩家操作与游戏世界的核心枢纽。

## 玩法系统概述

### 定义与范围

**Gameplay 系统**是一个极其庞杂的系统，其边界与渲染、物理、动画等模块深度交织，共同构成完整游戏体验。

**本讲座内容规划**：

| 模块 | 目标 |
|------|------|
| **事件系统 (Event System)** | 游戏对象如何互相通信和驱动，这是一切互动玩法的基础 |
| **脚本系统 (Scripting System)** | 如何用脚本编写游戏规则和逻辑 |
| **可视化脚本 (Visual Scripting)** | 以 Unreal Engine 蓝图 (Blueprint) 为代表的图形化编程方案 |
| **3C 系统** | Character、Control、Camera，构建优秀角色操控体验的基础 |
| **游戏 AI** | 寻路、决策算法、机器学习 |

### 三大核心挑战

#### 挑战一：高度的系统耦合性 (System Interconnectivity)

玩法工程师 (Gameplay Engineer) 的角色更像是"指挥家"，需要协调各系统专家。

**经典案例：实现"打击感" (Hit-Feel)**

实现一次有力的劈砍，需要调用和协调：

```
动画系统 (Animation)  → 播放攻击动画和受击动画
特效系统 (VFX)        → 刀光、击中火花、流血
音效系统 (Sound FX)   → 挥砍声、击中声、惨叫声
控制系统 (Control)    → 响应玩家输入、手柄震动
UI 系统 (UI)          → 伤害数字、"暴击"、"Double Kill" 提示
渲染系统 (Rendering)  → 卡帧 (Hit-Stop)：击中瞬间短暂冻结画面
```

#### 挑战二：玩法的多样性与可扩展性 (Variety and Extensibility)

一个统一的世界观下往往融合了多种截然不同的玩法。

*示例：《巫师3》核心 ARPG 战斗 + 内置昆特牌卡牌游戏；大型 MMO 包含战斗、踢足球、科举、家园建造等无数玩法*

架构要求：底层设计必须通用且灵活，能够低成本添加全新的逻辑模块，而不影响现有系统。

#### 挑战三：极速的迭代需求 (Rapid Iteration)

| 对比维度 | 渲染功能 | 玩法功能 |
|----------|----------|----------|
| **开发周期** | 半年到一年以上 | 几天到几周 |
| **稳定性** | 相对稳定和专注 | 经常在开发中被推翻重来 |
| **开发模式** | 大型迭代 | 短小精悍的冲刺 (Sprint) |

**震撼案例**：《堡垒之夜》(Fortnite) 在发现吃鸡模式潜力后，仅用**两个月**就完成了从 PVE 到 Battle Royale 的核心玩法转型。

## 事件系统 (Event System)

### 发布-订阅模式 (Publish-Subscribe Pattern)

核心思想：与其让一个对象直接调用另一个对象的方法（强耦合），不如通过一个中立的"信息中心"进行通信。

**生动比喻**：
- 发布者：校园社团，定期出版自己的"小报"（发布事件）
- 订阅者：对特定内容感兴趣的学生（注册对某类事件的关注）
- 信息中心：学校收发室，准确投递小报给订阅者

### 事件系统的三大核心组件

| 组件 | 定义 | 类比 |
|------|------|------|
| **事件 (Event/Message)** | 对游戏中发生事情的封装，是承载信息的载体 | 包裹本身 |
| **事件分发器 (Event Dispatcher)** | 接收所有发布的事件，准确派送给订阅者 | 高效的物流公司 |
| **回调函数 (Callback)** | 订阅者预先注册的函数，事件触发时自动调用 | 收到包裹后的处理动作 |

### 事件的定义与扩展

**事件的基本构成**：

```
事件类型 (Event Type)：唯一标识符，如 enum 或字符串哈希
事件参数 (Payload)：携带的具体数据

示例 - 爆炸事件：
{
  type: "OnExplosion",
  center: (x, y, z),
  damageAmount: 100,
  damageType: "Fire"
}
```

**从静态定义到动态扩展的演进**：

| 方案 | 特点 | 适用场景 |
|------|------|----------|
| **静态 C++ 继承** | 类型安全，编译期检查，每次新增需程序员修改代码 | 早期简单游戏 |
| **数据驱动 + 代码生成** | 设计师在配置文件中定义，工具链自动生成代码 | 常见方案，需编译步骤 |
| **运行时注入 (DLL 热加载)** | 引擎运行时加载新 DLL，无需重启主程序 | UE 的 Hot Reload，实现复杂 |
| **脚本语言** | 在脚本中直接定义，天然动态性 | 最主流、最平衡的方案 |

### 回调函数与生命周期安全

**核心问题**：回调的注册和执行在时间上分离——注册时对象存在，执行时对象可能已销毁。

**野指针场景**：
```
1. EnemyA 注册了 OnExplosionDamage 回调
2. 下一帧，EnemyA 因其他原因被销毁（内存释放）
3. 手雷爆炸，系统尝试调用 EnemyA 的回调
4. 访问无效内存 → 程序崩溃 (Dangling Pointer)
```

**解决方案：智能指针 + 引用计数**

| 引用类型 | 核心观点 | 优点 | 缺点 | 典型用例 |
|----------|----------|------|------|----------|
| **强引用 (Strong Reference)** | "我引用了你，你就不能被销毁" | 绝对安全，无需检查 | 可能导致内存泄漏（循环引用） | 父子关系 |
| **弱引用 (Weak Reference)** | "我引用了你，但你随时可能消失" | 灵活，避免内存泄漏 | 每次使用前需检查有效性 | 回调函数、临时引用 |

```cpp
// 弱引用使用示例
weak_ptr<GameObject> weakEnemyRef = targetEnemy;

if (shared_ptr<GameObject> lockedEnemy = weakEnemyRef.lock()) {
    // 锁定成功，对象仍然存在，可以安全使用
    lockedEnemy->TakeDamage(10);
} else {
    // 锁定失败，对象已被销毁，什么都不做
}
```

### 即时派发 vs 事件队列

#### 即时派发 (Immediate Dispatch) 的问题

| 问题 | 说明 |
|------|------|
| **性能低下** | O(N × M × ...) 复杂度，暴力遍历 |
| **调用栈过深** | 链式反应导致递归调用，调试噩梦 |
| **阻塞帧率** | 耗时回调会阻塞主线程，导致卡顿 |
| **难以并行化** | 天生串行，无法利用多核优势 |

#### 现代架构：事件队列 (Event Queue)

**核心思想**：延迟处理——将当前帧产生的所有事件存入队列，在下一帧特定阶段统一处理。

**关键实现技术**：

**事件存储与序列化**：通过反射系统动态获取事件类型的元数据，将事件对象"拍平"成二进制数据存入内存块，再按需反序列化。

**环形缓冲区 (Ring Buffer)**：
```
预分配固定内存块
↓ 通过 head/tail 指针追踪入队/出队
↓ 已处理事件的空间可被后续事件复用
↓ overflow 时丢弃新事件（防止崩溃，保留几帧错误好过引擎崩溃）
```

**事件分类（分而治之）**：将事件按系统分类，使用多个独立队列：

```
网络事件队列 (Network Event Queue)
战斗事件队列 (Combat Event Queue)
动画事件队列 (Animation Event Queue)
UI 事件队列 (UI Event Queue)
```

优点：各子系统只处理自己的队列，大幅减少不必要的遍历；出问题时可直接检查对应队列。

#### 三种处理时机

| 模式 | 处理时机 | 适用场景 |
|------|----------|----------|
| **立即处理 (Immediate)** | 事件发出的那一刻 | 打击感反馈等对延迟极度敏感的逻辑 |
| **下一帧开始前 (Pre-Tick)** | 下一帧所有系统 Tick 之前 | 最常见的延迟处理模式 |
| **本帧结束后 (Post-Tick)** | 本帧所有系统 Tick 完成后 | — |

> [!warning] 关于事件优先级
> **强烈建议不要为游戏逻辑事件设置优先级**。优先级会破坏发布-订阅模式的解耦原则，引入隐式的执行顺序假设，与现代引擎的并行化架构冲突，并增加系统脆弱性。设计的黄金法则是**顺序无关性 (Order Independence)**。

#### 帧延迟与打击感问题

事件队列引入的延迟在延迟敏感场景中不可忽视：

```
N 帧   → 玩家输入"攻击"→ 碰撞检测 → 产生"击中"事件 → 进入队列
N+1 帧 → 处理"击中"事件 → 触发伤害计算 → 产生"死亡"事件 → 进入队列
N+2 帧 → 处理"死亡"事件 → 播放死亡动画、特效、音效
```

在 60FPS 下，N→N+2 的延迟已超过 **30ms**。对于"打击感"这种对延迟极敏感的反馈，必须使用**立即处理 (Immediate)** 模式，而不是入队等待。

> [!tip] 实践原则
> 将事件分为两类：**时间敏感**（打击反馈、UI 即时更新）→ 立即处理；**非时间敏感**（伤害结算、任务进度）→ 入队延迟处理。合理分类是事件系统性能调优的关键。

## 脚本系统 (Scripting System)

### 为什么需要脚本语言

**C++ 的三大痛点**：

| 痛点 | 说明 |
|------|------|
| **开发效率低** | 每次微小改动都需重新编译，耗时从几分钟到半小时 |
| **难以热更新** | 编译型二进制代码静态，实现热更新需要复杂的底层 Hack |
| **对非程序员不友好** | 要求策划和美术直接修改 C++ 代码既不现实也风险极大 |

**脚本语言的优势**：

```
简单易学    → 策划、技术美术也能参与玩法逻辑编写
热更新      → 解释执行，替换脚本文件即可，无需重启
沙箱化运行  → 运行在虚拟机 (VM) 上，脚本崩溃不影响引擎进程
```

> [!important] 热更新的核心挑战
> 热更新只替换了"逻辑"（函数），不处理"数据"（变量）。如果新代码依赖的状态与旧代码不一致，或未能正确重置全局变量，极易导致崩溃或逻辑错乱。在百万级玩家在线的商业游戏中，保证热更新的**鲁棒性 (Robustness)** 是工程上的重中之重。

### 脚本语言工作原理

```
脚本代码 (Script Code, 文本文件)
    ↓ 编译器 (Compiler)
字节码 (Bytecode, 平台无关中间指令)
    ↓ 虚拟机 (Virtual Machine)
执行结果
```

代价：间接执行通常比原生 C++ 慢，但带来了鲁棒性和热更新能力。

### 主流脚本语言对比

| 特性 | Lua | Python | C# |
|------|-----|--------|-----|
| **核心优势** | 极致轻量，嵌入方便 | 库强大丰富 | 性能与内存的良好平衡 |
| **内存占用** | 极低 | 非常大（数百 MB） | 中等 |
| **与 C++ 交互** | 效率极高 | 尚可 | 良好 |
| **面向对象** | 通过 metatable 模拟 | 原生支持 | 原生支持 |
| **知名应用** | 《魔兽世界》插件系统 | 数据科学、Web 后端 | Unity 引擎 |

> [!warning] 反面教材
> 强行将 Lua 改造为面向对象风格会破坏其原生设计哲学，导致 GC 效率急剧下降，且无法从 LuaJIT 中获益。**尊重语言自身的设计**，是技术选型的重要原则。

**执行性能**：C# > Python ≈ Lua  
**内存占用**：Lua < C# < Python

**JIT 编译 (Just-In-Time)**：LuaJIT 等技术在运行时将热点代码编译为本地机器码，性能可比原生 Lua 高出一个数量级。

### 引擎与脚本的两种协作模式

#### 引擎驱动脚本 (Engine-Driven) — 最常见

```
引擎 Main Loop 驱动
    ↓ 在固定阶段 Tick Animation
    ↓ 在固定阶段 Tick Physics
    ↓ 在固定阶段调用脚本逻辑
脚本是"员工"，引擎是"老板"
```

*代表：Unity 中 C# 脚本的 Update() 由引擎在每帧调用*

#### 脚本驱动引擎 (Script-Driven) — 更灵活

```
脚本层控制主循环
    ↓ 脚本决定何时调用 Engine.TickAnimation()
    ↓ 脚本决定何时调用 Engine.RenderScene()
引擎是"职能部门"，脚本是"总指挥"
```

### 游戏对象生命周期管理

| 流派 | 管理者 | 优点 | 缺点 | 适用场景 |
|------|--------|------|------|----------|
| **C++ 引擎管理** | 引擎内核 | 性能可控，安全性高 | 灵活性差，频繁创建对象流程繁琐 | 对象数量相对固定的单机大作 |
| **脚本系统管理** | 脚本层 + GC | 高度灵活，代码简单 | GC 开销巨大，可能成为性能瓶颈 | 玩法极其复杂、对象动态变化的 MMO |

**GC 的双刃剑**：
- 优点：无需手动管理内存，避免野指针和内存泄漏
- 缺点：执行时机不确定，可能在激烈战斗中触发，导致游戏卡顿（性能抖动 Stutter）

## 可视化脚本 (Visual Scripting)

### 为什么需要可视化脚本

**目标用户**：设计师 (Designers) 和 艺术家 (Artists)

**核心优势**：
- 降低编程门槛，无需关心变量声明、生命周期、编译错误等概念
- 类型安全连接：系统在编辑阶段就阻止不兼容类型的连接（蓝色接口只能连蓝色线）
- 直观易懂，逻辑流程一目了然，调试友好

### 可视化脚本的基本构成

可视化脚本是对传统编程语言基本要素的图形化映射：

#### 变量 (Variables)

用不同**形状或颜色的引脚 (Pins)** 代表不同数据类型（bool、int、Color、Vector 等），从物理上阻止不兼容类型的连接。

#### 执行流：语句与控制流

| 类型 | 定义 | 可视化特征 |
|------|------|------------|
| **表达式 (Expressions)** | 负责数据处理和计算（加减乘除、比较等），瞬时完成 | 无执行引脚，只有数据输入/输出 |
| **语句 (Statements)** | 执行具体动作，改变游戏世界状态，需要时间 | 有白色三角形**执行引脚 (Execution Pin)** |
| **控制流 (Control Flow)** | 条件判断、循环分支（if/else、for、switch 等） | 多个输出执行引脚，根据条件决定走向 |

**执行流 (Execution Flow)**：程序的执行顺序由白色执行引脚的连线决定。

#### 高级抽象

| 概念 | 对应编程概念 | 说明 |
|------|------------|------|
| **函数 (Functions)** | 函数/方法 | 将一系列操作封装为可复用单元，有明确的输入和输出 |
| **类 (Classes)** | 类 | UE 的 Blueprint 就是一个类，包含成员变量和事件图表 |

### 上下文感知建议 (Contextual Suggestions)

可视化脚本编辑器的核心用户体验功能：

```
从执行引脚拖拽连线后松开 → 弹出候选节点列表
系统根据：
  · 当前引脚的数据类型（过滤不兼容节点）
  · 当前上下文（玩家角色 vs 敌人 vs 物件）
  · 使用频率（高频节点排在前面）
自动推荐最相关的可连接节点
```

这一功能大幅降低使用门槛——设计师无需记忆所有节点名称，系统会在合适时机"告诉"你有什么可以用。

### 可视化调试 (Visual Debugging)

运行时可直接在蓝图编辑器中观察执行过程：

| 调试特性 | 说明 |
|----------|------|
| **高亮执行路径** | 正在执行的节点和连线实时高亮，清晰展示当前程序走的是哪条分支 |
| **悬停查看数值** | 鼠标悬停在数据引脚上，弹出当前帧该引脚的实时数值 |
| **断点支持** | 在节点上设置断点，暂停执行以检查状态 |

这是纯文本代码调试器难以提供的直观体验，也是可视化脚本在教学和原型迭代阶段被广泛青睐的重要原因。

### 工程实践挑战

| 挑战 | 说明 |
|------|------|
| **版本控制与合并冲突** | 图形化节点的语义难以追踪，二进制文件合并风险高 |
| **可读性下降** | 复杂蓝图包含成百上千节点，可读性急剧下降，交接困难 |
| **生产阶段演变** | 业界趋势："原型用蓝图，量产用代码"，复杂系统最终重构为代码 |

### 可视化脚本的本质

> [!important] 核心揭秘
> 可视化脚本本质上是**脚本语言的图形化前端表示 (A graphical front-end for a scripting language)**。
>
> Visual Graph → 编译 → 字节码 / 机器码（现代引擎为追求性能直接跳过中间文本脚本）
>
> 虽然入门简单，但实现一个商业级的可视化编程系统极其复杂（如 UE 的 Blueprint 需要团队投入数年持续开发）。

## 3C 系统：操控体验的核心

**3C** = **C**haracter（角色）+ **C**ontrol（控制）+ **C**amera（相机）

这三者共同协作，构成玩家与游戏世界交互的基础体验，直接决定游戏的"手感"和沉浸感。

> [!note] 学习标杆
> 《双人成行》(It Takes Two) 在 3C 设计上的打磨甚至超越了许多 3A 大作，是学习 3C 系统的绝佳案例。

### C1 - Character（角色）系统

这里的"角色"不是指模型，而是指**角色行为逻辑的集合**。

**关键组成部分**：

| 方面 | 说明 |
|------|------|
| **精细化移动** | 远超"前后左右"：处理上下坡、越过小障碍、不同表面表现（冰面/沙地）、与障碍物交互 |
| **丰富的环境互动** | 物理行为（抓取、攀爬、滑翔、游泳）；视觉/音效反馈（雪地脚印、不同材质脚步声） |

**实现策略**：以**动画状态机 (Animation State Machine)** 为基础，状态节点不仅控制动画播放，还挂载逻辑脚本。角色在不同动画状态（跑、跳、游泳）间切换时，相应游戏逻辑也会被触发。

**对引擎架构的要求**：引擎不负责写死具体角色行为，而是提供能够互相通信的底层系统，并将定义系统间交互的接口和工具开放给策划和设计师。

### C2 - Control（控制）系统

控制系统是连接玩家意图和角色行为的"翻译官"，是"游戏手感" (Game Feel) 的直接来源。

#### 核心挑战：延迟与辅助瞄准

从玩家"看到-反应-操作-信号传输-引擎处理"的链路，延迟可高达 100-200ms。在快节奏游戏中，这足以让玩家感觉"准星划过了目标"。

**辅助瞄准 (Aim Assist)** — 必要的延迟补偿机制：

```
玩家按下瞄准键 → 触发 Aim 事件
    ↓
相机变化：FOV 缩小（模拟望远镜）+ 相机位置前移
UI 变化：准星样式改变
    ↓
吸附效果 (Snapping Effect)：
  当准星靠近预设可瞄准目标时，自动平滑"吸"向目标
  引擎提供工具定义可瞄准目标
  脚本实时计算准星与目标夹角
  夹角小于阈值时触发吸附
  吸附过程为平滑插值（保证手感自然）
```

#### 反馈 (Feedback)

反馈是控制循环中至关重要的一环，是主动媒体（游戏）与被动媒体（电影）的核心区别。

| 反馈类型 | 示例 |
|----------|------|
| **力反馈 (Haptics)** | 手柄震动模拟工具手感；专业方向盘模拟路感阻力 |
| **视觉反馈** | RGB 灯效随游戏状态变化（残血时变红） |
| **听觉反馈** | PS5 手柄内置喇叭在特定场景发出声音 |

#### 控制系统的复杂性

同一个按键在不同状态下（站立、奔跑、游泳）触发完全不同的行为；格斗游戏的"搓招"（特定输入序列）也需要控制系统来识别。这些复杂逻辑**必须通过可视化脚本等工具交给设计师定义**。

### C3 - Camera（相机）系统

相机系统是一种强大的**叙事工具**，是塑造玩家**主观感受 (Subjective Experience)** 的核心，远不止定义一个 POV 和 FOV。

#### 动态相机设计

- 相机的距离、角度、偏移根据角色状态（走、跑、冲刺）和环境**动态变化**
- **穿墙问题解决方案**：
  - **弹簧臂 (Spring Arm)**：检测到与环境碰撞时自动缩短，将相机拉近角色
  - **遮挡物透明化**：遮挡相机视线的物体变为半透明

#### 相机与主观感受

| 情绪 | 相机表现 |
|------|----------|
| **恐惧/紧张** | FOV 变窄，模拟瞳孔放大后视野聚焦的效果 |
| **放松/探索** | FOV 变宽，让玩家看到更广阔的场景 |

**Camera Cage / Camera Track**：设计师定义的空间区域或规则集，在此区域内相机各种参数被精确控制和插值，像电影导演一样编排玩家的观看体验。

#### 多相机系统的无缝切换

一个典型游戏的相机切换序列：

```
常规移动        → 标准第三人称相机
举枪瞄准        → 越肩视角 / 第一人称相机 (ADS Camera)
拾取重机枪      → 视野更远、偏移更大的第三人称相机
进入载具        → 载具专用相机（车内/车外）
使用狙击镜      → 高倍率瞄准镜相机 (Scope Camera)
```

**相机管理器 (Camera Manager)**：管理所有不同状态下的相机，并在不同状态间实现平滑的**插值 (Interpolation)**，避免生硬的视角切换。

#### 相机特效

| 特效 | 作用 |
|------|------|
| **抖屏 (Screen Shake)** | 增强打击感，是最有效的方式之一 |
| **运动模糊 (Motion Blur)** | 模拟速度感 |
| **FOV 变化** | 配合运动状态增强冲刺、速度感 |
| **相机惯性 (Inertia)** | 相机"不完全跟随"角色，使动作更自然生动 |

## 基础 AI：导航系统 (Navigation System)

AI 的第一个基础是导航系统——解决 AI 角色**如何在游戏世界中移动**的问题。

### 导航系统的三个核心步骤

```
1. 世界表达 (World Representation)   → 将场景转换成 AI 可理解的数据结构
2. 路径寻找 (Pathfinding)            → 在世界表达上运行算法找到路径
3. 路径平滑 (Path Smoothing)         → 将折线路径优化为自然平滑的曲线
```

### 可行走区域 (Workable Area) 的定义

世界表达的第一步，是确定哪些区域是 AI **可以通行**的。这不是简单的物理碰撞查询，而是一个综合多方面信息的判断：

| 信息来源 | 说明 |
|----------|------|
| **物理碰撞** | 场景几何体的碰撞层（最基础的输入） |
| **角色能力** | 角色能跨越的最大台阶高度、能跳跃的最大间距、能通过的最窄通道 |
| **坡度限制** | 超过某角度的斜面标记为不可通行（防止 AI 试图爬上峭壁） |
| **区域类型** | 不同 AI 类型有不同规则：步兵不能走水域，飞行单位不受地面限制 |
| **设计师覆盖** | 手动放置**隐形墙 (Air Wall)**，将物理上可通行但剧情/设计上不允许的区域封闭 |

> [!note] 可行走区域是 NavMesh 生成的输入
> Recast 等工具的体素化阶段，本质上就是在将上述综合规则转换为离散的"可行走/不可行走"标记，最终生成 NavMesh。

### 世界表达方式对比

| 方式 | 抽象层级 | AI 行为 | 内存占用 | 动态更新 | 3D 结构 | 现代应用 |
|------|----------|---------|---------|---------|---------|---------|
| **路点网络 (Waypoint)** | 点 | 机械、不自然 | 低 | 困难，需手动 | 有限 | 简单/老式游戏 |
| **网格法 (Grid)** | 单元 | 较生硬 | 非常高 | 非常简单 | 几乎不支持 | 特定场景、原型 |
| **导航网格 (NavMesh)** | 面 | 灵活、自然 | 相对较低 | 较复杂 | 完美支持 | **业界标准** |
| **稀疏体素八叉树** | 体 | 三维自由 | 大 | 复杂 | 完美支持 | 飞行/太空游戏 |

#### Waypoint Network（路点网络）

经典地铁类比：路点 = 地铁站，路径 = 地铁线路。AI 走到最近路点 → 网络内寻路 → 从终点走到目标。

**缺点**：严重依赖设计师手动放置路点，地图修改时需手动同步更新；AI 倾向于沿网络中心线移动，行为不自然。

#### Grid（网格法）

将地图均匀划分为二维格子，每格标记为可通行或不可通行。

> [!warning] 缓存缺失问题 (Cache Miss)
> 二维数组在内存中以**行优先 (Row-Major)** 方式存储。寻路算法需要频繁访问节点的上下左右邻居，访问"右邻居"（同行下一列）在内存中连续，但访问"下邻居"（下一行同列）需要跳过整行的内存距离。
>
> 对于 1024×1024 的大地图，每次访问"列方向邻居"都是一次大跨度内存跳跃，导致 CPU 缓存命中率极低，大幅降低寻路性能。
>
> **这是大世界游戏很少使用网格法做主要寻路表达的工程原因之一。**

#### NavMesh（导航网格）

用一组连续互相连接的**凸多边形 (Convex Polygons)** 精确覆盖所有可通行地面。

**为什么必须是凸多边形**？

```
凸多边形关键性质：内部任意两点连线完全包含在多边形内
→ 保证从A到B的直线路径在多边形内部有效
凹多边形问题：A到B的直线可能穿过不可通行区域（障碍物）
```

**非流形结构 (Non-Manifold Structure)**：

现实关卡中常出现立交式结构——道路从桥下穿过，桥面和桥下地面在垂直方向上重叠。在二维网格中无法同时表达两层地面，但 NavMesh 可以通过将桥面和桥下生成为**不相连的独立多边形集合**来处理：

```
桥面 NavMesh：y=5.0m 的独立多边形集合
桥下 NavMesh：y=0.0m 的独立多边形集合

通过"离网链接 (Off-Mesh Link)"将两个网格的入口/出口点手动相连
```

这种在同一水平坐标下存在多个垂直层级的结构，称为**非流形 (Non-Manifold)**——NavMesh 天然支持，而网格法几乎无法处理。

**多边形走廊 (Polygon Corridor) 与传送门 (Portal)**：

A* 在 NavMesh 上找到的路径是一系列相邻多边形序列。两个相邻多边形共享的那条边称为**传送门 (Portal)**——是后续路径平滑算法的基础。

#### NavMesh 自动生成：Recast Navigation

```
第一步：体素化 (Voxelization)
  将三维场景离散化为体素（类似《我的世界》风格）

第二步：标记可行走区域
  根据角色高度、半径、坡度等参数，标记可通行体素

第三步：区域划分（距离场 + 洪水算法）
  计算每个体素到最近边缘的距离 → 以距离最大的点为"种子"
  洪水填充算法扩张 → 分割出近似凸多边形区域

第四步：多边形化
  将体素区域转换为最终的三角形 NavMesh
```

### NavMesh 的高级应用

#### 区域标记 (Polygon Flags)

为 NavMesh 上不同多边形打标签：

```
材质区分   → 草地、沙地、河流（触发不同脚步声和粒子特效）
寻路成本   → 沼泽地成本高于公路，AI 优先选择公路
区域禁用   → 特定 AI 类型（如步兵）将水域标记为不可通行
```

#### 分块更新 (Tiled NavMesh)

将大世界切分为固定大小的 Tile（如 64×64 米），动态障碍物出现时只重新计算受影响的少数 Tile。技术难点：确保相邻 Tile 边界处顶点完美对齐缝合。

#### 离网链接 (Off-Mesh Links)

设计师手动在两个 NavMesh 多边形间创建特殊连接，代表需要特殊动作才能通过的路径：

```
攀爬点      → 连接地面和高台
传送门      → 连接两个不相邻区域
滑索        → 如《死亡搁浅》从电线杆滑下
跳跃点      → 标记可跳过的小间隙
```

### 路径寻找算法

#### 图搜索的本质

无论 Waypoint、Grid 还是 NavMesh，用于寻路时都可抽象为图：

```
Waypoint: 路点 = 节点，连接 = 边
Grid:     格子中心 = 节点，相邻格子连接 = 边
NavMesh:  多边形中心 = 节点，公共边（Portal）= 边
```

#### Dijkstra 算法

从单个源点计算到图中所有其他节点的最短路径。采用贪心策略，总是从未访问节点中选择当前已知距离最小的节点进行探索（**松弛操作 Relaxation**）。

**游戏中的局限**：发散式搜索，探索所有方向，计算量较大。

#### A* 算法（游戏寻路事实标准）

在 Dijkstra 基础上引入**启发函数 (Heuristic Function)**：

$$f(n) = g(n) + h(n)$$

| 项 | 含义 |
|----|------|
| $g(n)$ | 从起点到当前节点 n 的**实际**路径成本 |
| $h(n)$ | 从当前节点 n 到终点的**预估**成本（启发函数） |
| $f(n)$ | 对总成本的估计，始终选择 $f(n)$ 最小的节点 |

**启发函数设计**：

| 世界类型 | 启发函数 | 原因 |
|----------|----------|------|
| 网格世界 | 曼哈顿距离 `\|x1-x2\| + \|y1-y2\|` | 符合网格移动规则 |
| NavMesh 世界 | 欧氏距离（两点间直线距离） | 虽忽略障碍，但提供强方向指引，且永不高估实际距离 |

**启发函数精度影响**：

| 情况 | 效果 | 权衡 |
|------|------|------|
| $h(n)$ 偏低（低估） | 探索更多节点，类似 Dijkstra | 路径更可能最优，速度较慢 |
| $h(n)$ 偏高（过估） | 更"功利"地朝向终点 | 速度极快，但不保证找到最优解 |

只要 $h(n)$ 不高估实际最短距离（**可采纳启发式 Admissible Heuristic**），A* 就保证找到最优路径。欧氏距离恰好满足这个条件。

### 路径平滑：漏斗算法 (Funnel Algorithm)

A* 在 NavMesh 上找到的路径是一系列折线（多边形中心点连线），AI 沿此移动会产生**Z字形 (Zig-Zag)** 效果，非常机械。

**漏斗算法核心思想**：从起点开始，试图找到一条尽可能"直"的视线穿过多边形走廊，不断收紧视线范围，直到视线被"墙壁"挡住为止——这个不断收窄的扇形区域形态像"漏斗"。

最终效果：将原本由十几个路点组成的路径简化为只有一两个拐点的平滑路径。

## 基础 AI：转向与群体模拟

### Steering 行为系统

**Pathfinding 与 Steering 的区别**：

| 系统 | 关注点 | 解决的问题 |
|------|--------|------------|
| **寻路 (Pathfinding)** | 宏观，"去哪里" | 找到从 A 到 B 的理想路径 |
| **转向 (Steering)** | 微观，"怎么走" | 如何在物理约束下真实地沿路径移动 |

**物理约束**：加速度/减速度；转弯半径（车辆无法瞬间改变方向）

> [!warning] 常见 Bug
> NPC 卡在墙角不停抖动，往往是 Steering 系统的问题：寻路系统告诉 NPC 可以通过，但由于转弯半径过大，Steering 无法转过狭窄弯角，导致反复尝试失败。

#### 三大基本 Steering 行为

**1. 追逐与逃跑 (Seek and Flee)**

每帧重新评估自身与目标的位置关系，计算并更新加速度向量。

变种：
- **追踪 (Pursuit)**：预测移动目标未来位置
- **方向场跟随 (Flow Field Following)**：预先在空间中定义方向向量场，AI 自然跟随流动，适合鱼群、人群大规模模拟

**2. 速度匹配 (Velocity Matching)**

在接近目标时，平滑地将自身速度调整到与目标一致（通常是减速至零停在目标位置）。

类比：火星探测器入轨——最难的不是加速飞过去，而是精确减速匹配火星公转速度以成功入轨。

**迭代收敛方法**：

```
每帧：
  当前速度差 = 目标速度 - 当前速度
  若 |速度差| > 最大加速度 × Δt：
    施加最大加速度朝向目标速度方向 → 本帧尽量靠近
  否则：
    直接将速度设为目标速度（已在一帧内可达）

关键参数：
  · 减速距离阈值：距目标多远时开始减速
  · 时间常数 τ：控制速度收敛的"松紧度"
    τ 小 → 快速到位（生硬）；τ 大 → 缓慢收敛（柔顺）
```

> [!tip] 工程技巧
> 在实现中常用 **时间常数 τ (Time Constant)** 代替固定加速度：每帧速度误差乘以衰减系数 `(1 - Δt/τ)`，天然避免超调（Overshoot），是实现平滑减停的最简洁方式。

**3. 朝向对齐 (Alignment)**

将自身朝向与目标方向对齐，需要引入**角加速度/角减速度**：

> [!important] 关键细节
> **错误做法**：直接将角度设为目标角度（瞬间转向，极其机械）  
> **正确做法**：施加角加速度，使朝向平滑转向目标角度，接近时施加反向角减速
>
> 缺少平滑角速度变化的 AI 转向会破坏玩家沉浸感，是早期/廉价游戏中常见的 AI 质量问题。

### 群体模拟 (Crowd Simulation)

#### 三种方法

| 方法 | 思路 | 优点 | 缺点 | 应用 |
|------|------|------|------|------|
| **微观 (Microscopic)** | 为每个个体定义简单局部规则，宏观行为自然涌现 | 生动自然，随机感强 | 结果难以精确控制 | 鱼群、鸟群 |
| **宏观 (Macroscopic)** | 预设全局路径或区域规则约束群体 | 高度可控，符合真实行为规范 | 需要额外规则处理特殊情况 | 城市人群、交通 (UE5 MassAI) |
| **混合 (Hybrid)** | 宏观指令 + 微观局部交互 | 兼顾策略感和自主行为 | 复杂度较高 | RTS 游戏 (星际争霸、帝国时代) |

**Boids 算法三原则（微观方法）**：

```
分离 (Separation)：避免与邻近个体挤在一起（斥力）
对齐 (Alignment)：调整方向与邻近个体保持一致
内聚 (Cohesion)：朝着邻近群体中心移动，避免掉队（引力）
```

类比：弹簧系统——靠太近产生斥力推开，离太远产生引力拉回。

#### 碰撞避免方法

| 方法 | 原理 | 优点 | 缺点 |
|------|------|------|------|
| **基于力 (Force-Based)** | 距离越近斥力越大，$F \propto 1/d^2$ | 实现简单，易于调试 | 效果不够优雅，可能抖动 |
| **速度障碍 VO** | 在速度空间计算碰撞区域，调整速度绕开 | 理论优雅 | 单向避让 |
| **相互速度障碍 RVO** | 双方各承担一半避让责任 | 效果平滑 | 多智能体场景可能引发连锁 |
| **ORCA** | 全局优化，为每个个体计算安全速度区域 | 最优解，非常平滑 | 数学复杂，计算量大 |
| **基于距离场** | 预计算静态障碍的距离场，实时查询梯度施加斥力 | 大规模群体效率高 | 需要预计算 |

**RVO 公平性原理**：

VO（速度障碍）的根本问题是**单边避让**——若只有 A 主动避让 B，则 A 总是承担所有代价，导致异常行为（如 A 绕一大圈，而 B 原地不动）。

RVO 的解决方案是**责任共担**：

```
传统 VO：A 完全避开 B 的速度障碍区域
RVO：A 和 B 各承担 50% 的避让责任
  → 两者各自只需调整一半的速度偏移量
  → 双方同时微小调整，合力完成避碰
  → 整体轨迹更平滑，不出现单方绕远路的异常
```

这个"公平性"原则让 RVO 在平滑性和计算效率之间取得了良好平衡，是游戏中使用最广泛的碰撞避免方案之一。

> [!tip] 工程建议
> 对于大多数游戏场景，**基于力的方法**更具工程优势——简单、稳定、易于调试。商业引擎通常两种方案都提供，开发者根据需求选择。

## 基础 AI：感知与决策概览

### AI 感知系统 (Perception System)

#### 空间信息

**静态空间信息**：由关卡设计师预先标注的战术参考：

| 信息类型 | 作用 |
|----------|------|
| **可通行区域 (NavMesh)** | 最基础的空间信息 |
| **战术地图 (Tactical Map)** | 标注具有战术意义的高价值点（如桥头堡） |
| **智能物件 (Smart Objects)** | 标记 AI 知道如何交互的物体（梯子、可破坏的墙） |
| **掩体点 (Cover Points)** | 标记可提供掩护的位置 |

*《战争机器》(Gears of War) 的 AI 出色的掩体使用行为，正是来源于设计师在地图中大量标注的掩体点信息。*

**动态空间信息**：

| 类型 | 说明 |
|------|------|
| **影响力图 (Influence Map)** | 多维度网格数据，量化地图各区域的威胁度等属性；AI 规划路径时查询并避开高威胁区域 |
| **动态寻路** | 场景物体移动或桥梁被摧毁时，实时调整移动路径 |
| **动态视野** | 受移动物体、烟雾等影响的实时视野 |

#### 感知模拟：避免"全知全能"

好的 AI 感知应该像人类一样**受限**，而不是拥有上帝视角：

| 感官 | 特点 |
|------|------|
| **视觉 (Vision)** | 有明确的朝向和视野范围 (FOV)，玩家可从背后偷袭 |
| **听觉 (Hearing)** | 通常 360 度；受障碍物遮挡 (Occlusion) 影响 |
| **嗅觉 (Smell) 等** | 猎犬可以根据气味轨迹追踪玩家 |

**工程优化**：
- 开放控制接口，按不同情况灵活调整感知频率、精度和范围
- **共享感知数据**：位置相近的一组 AI 共用一个感知结果，避免大量重复计算

### AI 即服务架构 (AI as a Service)

随着机器学习模型越来越复杂，一种新兴的工程架构将 AI 决策模块从游戏引擎中**解耦为独立外部服务**：

```
游戏引擎
  │  ① 封装游戏状态（State）
  ↓
HTTP / RPC 请求  ─────────────────────────────────────────►
                                                          AI 服务器
                                                          （Python/PyTorch）
                                                          接收状态 → 推理 → 返回动作
◄─────────────────────────────────────────
  ② 接收动作（Action）
  │
  ↓
引擎执行动作
```

| 维度 | 优点 | 缺点 |
|------|------|------|
| **开发效率** | AI 团队用熟悉的 Python 生态独立开发和迭代 | 引擎-服务通信有网络延迟（本地可 <1ms，但仍有开销） |
| **灵活性** | 可独立升级 AI 模型，无需重新编译引擎 | 状态序列化/反序列化增加了开发和调试复杂度 |
| **资源隔离** | AI 推理在独立进程，不阻塞游戏主线程 | 服务进程管理增加部署成本 |
| **工具链** | 可直接使用 TensorFlow/PyTorch 的全套调试工具 | 跨进程状态同步可能引入一致性问题 |

> [!note] 适用场景
> "AI 即服务"架构更适合**研究原型**和**后端 NPC 服务**（如 MMO 中的 AI 服务器），而非对延迟敏感的本地单机 NPC。在生产环境中，通常将训练好的模型导出并集成进引擎内的 C++ 推理库（如 TensorRT / ONNX Runtime）。

### 决策算法概览

| 算法 | 类型 | 核心特点 |
|------|------|----------|
| 有限状态机 (FSM) | 前向规划 | 基础经典，状态跳转 |
| 行为树 (Behavior Tree) | 前向规划 | 现代主流，树状结构直观 |
| 分层任务网络 (HTN) | 目标导向规划 | 层级分解，适合长期规划 |
| 目标导向行为规划 (GOAP) | 目标导向规划 | 自动规划行为序列，动态适应 |
| 蒙特卡洛树搜索 (MCTS) | 搜索算法 | 适合回合制复杂博弈 |
| 深度强化学习 (DRL) | 机器学习 | 超越设计限制，涌现行为 |

**两大决策思路**：

| 思路 | 特点 | 比喻 | 代表算法 |
|------|------|------|----------|
| **前向规划 (Forward Planning)** | 响应式，根据当前状态一步步决策 | "脚踩西瓜皮，走到哪是哪" | FSM, BT |
| **目标导向规划 (Goal-Oriented)** | 以终为始，反向推导达成目标的行动序列 | "以终为始，制定详细计划" | HTN, GOAP |

## 有限状态机 (Finite State Machine, FSM)

### 核心思想

AI 的所有行为抽象为一系列离散的**状态 (State)**，任意时刻处于且仅处于一个状态，通过满足**条件 (Condition)** 的**转移 (Transition)** 在状态间切换。

**经典案例：吃豆人 AI**

```
    发现幽灵且无敌状态
    ──────────────────────────────────►
闲逛 (Wander)                    追逐幽灵 (Chase Ghost)
    ◄──────────────────────────────────
    无敌时间结束

    ◄────────────────────────────────►
闲逛 (Wander)                    逃离幽灵 (Flee Ghost)
    发现幽灵且非无敌状态        幽灵消失
```

### FSM 的核心问题：状态爆炸

随着游戏逻辑复杂度提升，状态数量急剧增加，连接线像一团乱麻——称为**"意大利面条式代码"**。

**解决方案：分层有限状态机 (HFSM)**

将功能相近的状态组织成子状态机，提升可读性和模块化。缺点：从深层状态快速跳转到另一个子状态机的深层状态，速度较慢。

## 行为树 (Behavior Tree, BT)

行为树从 **Halo 2** 中被大规模商业应用，逐渐成为现代游戏 AI 最主流的决策技术。其思想源泉是商业和军事领域的**决策树 (Decision Tree)**。

### FSM vs BT 的根本区别

- **FSM** 抽象的是"逻辑"：`IF condition THEN state = newState`
- **BT** 抽象的是"**人类思维模式**"：描述"我该做什么"的思考过程

### 基本节点类型

#### 可执行节点（叶节点）

| 类型 | 功能 | 返回状态 | 特点 |
|------|------|----------|------|
| **条件节点 (Condition)** | 进行逻辑判断（如"敌人是否在视野内"） | 成功/失败 | 瞬时完成 |
| **动作节点 (Action)** | 执行具体动作（如"移动到目标点"） | 成功/失败/**运行中** | 需要时间执行，有 Running 状态 |

#### 控制流节点

**顺序节点 (Sequencer/AND节点)**：

```
从左到右依次执行子节点
  子节点返回 Failure → 立即停止，返回 Failure（后续子节点不执行）
  子节点返回 Running → 立即停止，返回 Running
  所有子节点都 Success → 返回 Success
```

*类比*：预设的线性计划（打开门需要"走到门前 → 解锁门 → 推开门"全部完成）

**选择节点 (Selector/OR节点)**：

```
从左到右依次执行子节点
  子节点返回 Success → 立即停止，返回 Success（后续子节点不执行）
  子节点返回 Running → 立即停止，返回 Running
  所有子节点都 Failure → 返回 Failure
```

*类比*：带优先级的决策链（攻击 > 追击 > 巡逻）

**并行节点 (Parallel)**：同时执行所有子节点，允许 AI "一心多用"。

*示例*：一边移动到支援点，一边持续警戒射击——FSM 很难优雅实现这种并发行为。

**装饰器 (Decorator)**：包装一个子节点，修改其行为或结果。常见类型：Loop（循环）、Wait（等待）、Inverter（取反结果）、Cooldown（冷却时间）。

### Ticking 机制：行为抢占的关键

经典 BT 每一帧从**根节点 (Root)** 开始重新遍历：

```
每帧开始
↓
从根节点遍历，根据 Selector/Sequencer 规则选择节点
↓
执行选中的 Action 节点
↓
下一帧重新从根节点开始
```

**为什么每帧从根节点开始**？实现**行为抢占 (Interrupt)**——高优先级事件（如敌人出现）可立即打断低优先级任务（巡逻）。

**性能优化**：事件驱动混合模式——平时只从 Running 节点开始 Tick，重要外部事件发生时强制从根节点重新评估。

### 黑板 (Blackboard)

**黑板**是行为树的全局数据共享中心，使不同节点间能够交换信息。

```
实现方式：键值对 (Key-Value) 存储
使用方式：
  攻击节点击杀敌人后 → 在黑板写入 lastKillTime = now()
  庆祝节点 → 读取 lastKillTime，若最近发生则播放庆祝动画
```

### BT 的核心局限

> [!important] 行为树的根本性缺陷
> 无论是 FSM 还是 BT，本质都是**反应式 AI (Reactive AI)**——AI 只是根据预设规则对当前环境做出反应，没有长远的内在"目标"或"追求"。它是一个没有灵魂的机器人，只是在执行指令。
>
> 这是推动 HTN、GOAP 等**目标导向**算法出现的核心动力。

## 分层任务网络 (Hierarchical Task Network, HTN)

HTN 是一种基于规划 (Planning-based) 的方法，被《地平线》系列、《黑暗之魂》等知名作品所采用。

### 核心组件

#### 世界状态 (World State)

不是客观物理世界的真实描述，而是 **AI 大脑中对世界的主观认知**——AI 的所有决策都基于它"认为"的世界是怎样的。

#### 传感器 (Sensor)

从真实游戏环境中抓取信息，更新 AI 内部的 World State：

```
真实世界 → Sensor（感知）→ World State（更新认知）
```

### 任务类型

#### 原子任务 (Primitive Task)

可以直接执行的具体动作，包含三要素：

```
动作 (Action)：实际执行的逻辑或函数
前置条件 (Precondition)：对 World State 的"读"操作
效果 (Effect)：执行后对 World State 的"写"操作

示例 - 使用解毒剂：
  Action:       UseAntidote()
  Precondition: WorldState.HasAntidote > 0
  Effect:       WorldState.IsPoisoned = false, HasAntidote -= 1
```

#### 复合任务 (Compound Task)

代表一个高层级目标，包含一个或多个按优先级排列的**方法 (Method)**：

```
复合任务 "治好中毒状态"：
  方法1（最高优先级）：制造解药  → [检查材料, 减少材料, 增加解药]
  方法2：购买解药               → [前往商店, 与 NPC 交互, 完成交易]
  方法3（最低优先级）：使用背包里已有的解药
```

**与行为树的类比**：

```
Methods 列表  ≈  BT 的 Selector（依次尝试直到找到可行方案）
Method 内部   ≈  BT 的 Sequencer（必须按顺序完成所有子任务）
```

### HTN 规划过程

规划器在**"草稿纸"（World State 副本）上推演**，而不直接修改真实世界状态：

```
1. 选定最高优先级目标
2. 在 Domain 中搜索可行方法
3. 每加入一个原子任务，将其 Effect 应用到 World State 副本
4. 后续任务的 Precondition 检查基于修改后的副本
5. 循环直到所有前置条件满足，输出原子任务序列
6. 计划交给 Plan Runner 执行

重规划触发条件：
  · 无计划 / 计划执行完毕
  · 执行失败
  · 世界状态发生重大变化（当前计划目标失去意义）
```

**重要假设**：规划阶段默认所有选择的动作都会成功（乐观策略），执行失败时再触发重规划。

**鲁棒的默认任务**：必须设置前置条件极易满足（或无前置条件）的默认任务（如 Wander、Idle），确保 AI 即使"迷茫"时也总有事可做。

### HTN 的工程挑战

#### 行为振荡问题 (Behavior Oscillation)

当两个方法的优先级接近，且世界状态在它们的前置条件临界值附近频繁波动时，AI 会反复在两个计划之间来回切换，产生不自然的抖动行为。

**"勤奋的人"类比**：

```
HTN 规划器制定了详细的今日工作计划。
执行途中，手机收到一条消息 → 世界状态改变 → 触发重规划。
新计划推翻旧计划 → 又执行了一会儿 → 又收到消息 → 再次重规划。

结果：一整天都在不停地"制定新计划"，反而什么正事都没做。
```

**解决方案**：
- 设置**重规划最小间隔**（Cooldown）：即使世界状态改变，也等待一定时间后再触发重规划
- 设置**状态变化阈值**：只有变化量超过阈值才触发重规划，滤除微小波动
- **回退 (Backtracking)**：当高优先级方法执行失败时，不立即重新规划整个计划，而是只回退到上一个 Compound Task，尝试其次优先级方法

### HTN vs BT：效率的飞跃

| 维度 | BT | HTN |
|------|-----|-----|
| **每帧开销** | 每帧从根节点遍历，70-80% 时间在重复计算 | 一次规划，持续执行，只在特定触发条件时重规划 |
| **设计意图** | 隐含在树结构中，不明确 | 目标显式定义，逻辑清晰 |
| **适应性** | 反应式，无长期规划 | 有长期目标，能够规划复杂行为序列 |

## 目标导向行为规划 (GOAP)

GOAP 将目标**显式化、定量化**，被《古墓丽影》系列、《刺客信条：奥德赛》等作品采用。

### 与 BT/HTN 的核心区别

在 BT 和 HTN 中，目标通常是**隐含**在树状结构或注释里的。而 GOAP 将目标定义为**一系列期望达成的 World State 的组合**：

```
"存活"目标    = { isAlive: true, isPoisoned: false }
"击杀敌人"目标 = { enemyHealth: 0 }
```

### 核心三要素

**目标集 (Goal Set)**：AI 所有可能达成的目标，每个目标可设置优先级和前置条件。

**动作集 (Action Set)**：AI 可以执行的原子行为，每个动作包含：

```
前提条件 (Preconditions)：执行前 World State 必须满足的条件
效果 (Effects)：执行后 World State 的改变
成本 (Cost)：执行该动作的代价（数值，用于比较路径优劣）
```

**成本的意义**：当多个行为序列都能达成同一目标时，GOAP 选择总成本最低的路径（本质是**动态规划**或**最短路径**问题）。

### 逆向规划（GOAP 的灵魂）

从最终目标出发，**反向推导**需要执行哪些动作（类似"以终为始"的人类规划）：

```
目标：{ isPoisoned: false }
↓ 寻找能达成此效果的动作
"使用解药"(Effect: isPoisoned=false) → 成为计划的最后一步
↓ 检查前置条件：{ HasAntidote: true }，当前不满足
↓ 设定新子目标：{ HasAntidote: true }
"去商店买药"(Effect: HasAntidote=true) → 成为倒数第二步
↓ 持续此过程直到所有前置条件都被当前世界状态满足
最终计划：[前往商店, 购买解药, 使用解药]
```

**未满足状态栈算法 (Unsatisfied States Stack)**：

逆向规划的具体实现方式——用一个**栈**追踪所有尚未被满足的前置条件：

```
初始化：将目标所有 World State 需求推入"未满足状态栈"

循环：
  1. 取栈顶的未满足状态 S
  2. 在动作集中找到能产生效果 S 的所有动作
  3. 选择成本最低且前置条件当前可被满足的动作 A
  4. 将 A 加入计划序列
  5. 将 A 的前置条件中尚未满足的项推入栈
  6. 重复，直到栈为空（所有前置条件已被当前世界状态满足）

示例（目标：isPoisoned=false）：
  栈：[isPoisoned=false]
  → 找到动作"使用解药"，效果=isPoisoned=false，前置=HasAntidote=true
  → 栈：[HasAntidote=true]（isPoisoned=false 已被计划覆盖）
  → 找到动作"购买解药"，效果=HasAntidote=true，前置=AtShop=true
  → 栈：[AtShop=true]
  → 找到动作"前往商店"，效果=AtShop=true，前置=none（已满足）
  → 栈为空，计划完成：[前往商店, 购买解药, 使用解药]
```

**规划转化为图搜索**：

```
节点：状态的组合 (Combination of States)
边：动作 (Actions)
边的权重：动作的成本 (Cost)
起点：最终目标（逆向规划）
终点：当前世界状态
算法：A*（启发式 = 距当前状态的"距离"估计）
```

### GOAP 的优缺点

| 优点 | 缺点 |
|------|------|
| 目标与行为解耦，设计师无需手动编排逻辑 | 计算开销大，运行时动态构建图并执行 A* |
| 动态行为，AI 能产生超越设计师预期的"涌现行为" | 世界状态量化困难，RTS 等复杂游戏难以用布尔值描述全局 |
| 减轻设计师工作负担 | 适用于状态相对确定的单机流程驱动型游戏 |

> [!tip] "不完美的美" (Imperfect Beauty)
> GOAP 使用 A* 搜索，但并不追求绝对最优路径——当启发函数稍微高估时，A* 会找到一条"近似最优"但非全局最优的计划。
>
> 这恰恰是 GOAP 的魅力所在：**次优的行为往往比最优行为更像真实的生物**。
> - 最优路径：NPC 每次都以数学意义上的最低成本行动，行为高度可预测
> - 次优路径：NPC 偶尔做出"不那么高效"的选择，产生"它在独立思考"的幻觉
>
> 这种"有意引入的不完美"是游戏 AI 中著名的设计哲学。

## 蒙特卡洛树搜索 (MCTS)

MCTS 是连接经典 AI 与机器学习的桥梁，被 AlphaGo 和《全面战争》等使用。

### 核心思想

不遍历完整决策树，而是通过**有限次模拟**来评估最有潜力的分支：

```
当面临决策点时，在"脑海中"快速推演成百上千种未来可能性
→ 统计每种可能性的胜负结果
→ 选择综合来看最有希望获胜的下一步
```

**问题建模**：

```
状态 (State)：当前局面的完整快照
动作 (Action)：在该状态下可以执行的操作
游戏树：状态为节点，动作为边，形成树状结构
```

### MCTS 核心迭代步骤

```
选择 (Selection)    → 从根节点出发，用 UCB 公式选择最有潜力路径，到达可扩展节点
扩展 (Expansion)    → 为该节点创建一个或多个新的子节点
模拟 (Simulation)   → 从新节点开始，用默认策略快速模拟到游戏结束，获得胜/负结果
反向传播 (BP)       → 结果沿路径传回根节点，更新路径上所有节点的 Q（获胜次数）和 N（访问次数）
```

重复以上四步，直到达到终止条件。

#### 终止条件 (Termination Conditions)

MCTS 的迭代何时停止，取决于资源约束：

| 终止条件 | 适用场景 | 说明 |
|----------|----------|------|
| **时间限制** | 实时游戏（最常用） | 每帧或每个决策点分配固定计算预算（如 10ms），到时强制返回当前最优结果 |
| **内存限制** | 内存受限环境 | 游戏树节点数达到上限时停止扩展，防止内存溢出 |
| **迭代次数** | 回合制游戏 | 固定模拟次数（如 1000 次），适合有明确计算预算的场景 |

> [!important] 关键设计原则
> MCTS 的优雅之处在于：**随时可以中断并给出"目前最好"的答案**。不同于 Minimax 等需要搜索到固定深度的算法，MCTS 在任意时刻停止都能输出有意义的结果——迭代次数越多，答案越精确，但即使只迭代几次也比随机选择好。这使它天然适合实时决策场景。

### UCB 算法：探索与利用的平衡

$$UCB(i) = \frac{Q_i}{N_i} + C\sqrt{\frac{\ln N_p}{N_i}}$$

| 项 | 含义 |
|----|------|
| $Q_i/N_i$ | **利用项**：节点 i 的历史胜率（越高说明越好） |
| $C\sqrt{\ln N_p / N_i}$ | **探索项**：$N_i$ 越小（访问越少）此项越大，鼓励探索未知节点 |
| $C$（探索常数） | 权衡利用与探索的超参数，需根据场景调优 |

**类比**：
- **利用 (Exploitation)**：总去自己最喜欢的餐厅（已知最优）
- **探索 (Exploration)**：冒险尝试新餐厅（未知潜力）

### 最终决策策略

| 策略 | 标准 | 说明 |
|------|------|------|
| **Max Child** | 选 Q 值最高 | 总获胜次数最多 |
| **Robust Child** | 选 N 值最高 | 被访问次数最多，最受算法信任 |
| **Max-Robust Child** | 同时拥有最高 Q 和最高 N | 最理想但可能不存在 |
| **Secure Child** | 用 LCB（下置信界）= $Q_i/N_i - C\sqrt{\ln N_p / N_i}$ | 结合胜率和可靠性 |

### MCTS 的优缺点与适用场景

| 优点 | 缺点 |
|------|------|
| 行为灵活生动，内在随机性让 AI 更"聪明" | 计算复杂度高 |
| 可产生超越设计师预期的策略 | 世界状态量化困难（RTS 等复杂游戏难以用布尔值描述） |
| 适用于庞大搜索空间 | 行为影响模糊时难以建模 |

**MCTS 最佳场景**：
1. **回合制 (Turn-based)**：游戏进程离散，有清晰轮次
2. **行为结果明确**：每个动作对游戏状态的改变可以精确计算

**混合 AI 架构示例**：

```
MCTS（顶层战略）     → 判断"现在应该推塔还是打野"
行为树 / HTN（战术）  → 将战略指令分解为"清兵线→攻击防御塔→注意敌方英雄"
FSM（底层执行）      → 控制具体移动、技能释放、普通攻击
```

## 机器学习在游戏 AI 中的应用

### 四大机器学习范式

| 范式 | 本质 | 核心特点 | 游戏应用 |
|------|------|----------|---------|
| **监督学习 (Supervised Learning)** | 分类器/回归器 | 学习带标签的"标准答案"数据 | 识别玩家行为模式，预测购买道具 |
| **无监督学习 (Unsupervised Learning)** | 聚类算法 | 无标签，自主发现数据中的规律和结构 | 玩家画像分类（肝帝/氪金/社交达人） |
| **半监督学习 (Semi-supervised Learning)** | 介于两者之间 | 少量标签引导大量无标签数据学习（小样本学习） | 设计师提供少量风格示例，AI 生成大量内容 |
| **强化学习 (Reinforcement Learning)** | 试错学习 | AI 通过与环境交互，最大化长期奖励 | AlphaStar、游戏 NPC 行为学习 |

### 强化学习与马尔可夫决策过程 (MDP)

#### MDP 基本组件

| 组件 | 定义 | 游戏举例 |
|------|------|---------|
| **智能体 (Agent)** | 决策的执行者 | 游戏 AI 角色 |
| **环境 (Environment)** | 外部世界，包含所有规则和状态 | 游戏世界 |
| **状态 (State, S)** | 对当前世界的完整描述 | 马里奥坐标 + 金币位置 + 敌人位置 |
| **动作 (Action, A)** | 可以执行的操作集合 | 向左走 / 向右走 / 跳跃 |
| **奖励 (Reward, R)** | 环境根据动作给予的即时反馈 | 吃金币 +1；碰到怪物 -10000 |

#### 核心循环

```
AI 观察状态 S → 基于策略 π 执行动作 A → 环境进入新状态 S' → 获得奖励 R → 重复
```

#### 关键数学概念

**状态转移概率 $P(S'|S,A)$**：在状态 S 执行动作 A 后，转移到状态 S' 的概率。世界是随机的 (Stochastic)，AI 无法 100% 控制结果。

**策略 $\pi(A|S)$**：在状态 S 下选择执行动作 A 的概率。输出的是**概率分布**而非确定动作。

**折扣因子 (Discount Factor, γ)**：介于 0 到 1 之间，衡量未来奖励相对于当前奖励的重要性。

$$G_t = R_{t+1} + \gamma R_{t+2} + \gamma^2 R_{t+3} + \cdots$$

| γ 值 | AI 特征 |
|------|---------|
| 趋近 1（如 0.999） | 更有"耐心"，重视长期规划，愿意为未来的大回报牺牲眼前小利 |
| 较小（如 0.95） | 更"短视"，倾向于立即获得奖励，反应更迅速 |

### 深度强化学习：以 AlphaStar 为例

#### 构建 DRL 框架的五大步骤

**Step 1：量化状态 (State)**

AlphaStar 将游戏世界解构为两类数据：

```
空间信息（多层地图）：
  高程图 (Height Map)
  战争迷雾图 (Fog of War)
  地表状态图（虫族菌毯 Creep）
  影响力图 (Influence Map)

离散信息（单位列表）：
  单位类型、归属、血量、位置……
```

**Step 2：定义动作 (Action)**

一个完整动作回答：谁执行？对什么目标？在哪里？

**Step 3：设计奖励 (Reward)**

| 类型 | AlphaStar | OpenAI Five (DOTA 2) |
|------|-----------|----------------------|
| **核心奖励** | 稀疏奖励：胜利 +1，失败 -1 | 高频多维度：击杀英雄、推塔、补刀等每个积极行为都有奖励 |
| **辅助奖励** | 伪奖励：与人类玩家决策的 KL 散度（控制在 [-1,1]，不能压过最终目标） | — |
| **特点** | 目标纯粹，训练难度高 | 训练平滑，便于调整 AI "性格" |

> [!tip] 通过奖励塑造 AI 性格
> - 提高"击杀英雄"奖励权重 → AI 更具攻击性
> - 加大"死亡"惩罚 → AI 变得更谨慎保守

**Step 4：网络架构**

核心框架：**编码器 (Encoder) + 解码器 (Decoder)**

| 编码器（"炼丹炉"） | 解码器（"翻译官"） |
|-------------------|-------------------|
| 接收多样化输入，编码为高维内部状态向量 | 将内部状态向量解码为具体可执行的动作 |
| 输出谁也读不懂的数字向量，但蕴含 AI 对局势的全部理解 | 输出：下一步指令、选择哪个单位、操作地图哪个位置 |

**不同数据类型的处理网络**：

| 数据类型 | 特点 | 处理网络 |
|----------|------|----------|
| 确定性状态（资源量、科技等级） | 结构固定的数值向量 | **MLP（多层感知机）** |
| 图像/地图类（小地图、战争迷雾） | 二维空间结构，局部关联性强 | **CNN + ResNet（残差网络）** |
| 不定长序列（单位列表） | 变长，元素间有关联 | **Transformer（自注意力机制）** |
| 整合与记忆决策 | 需要跨帧记忆历史信息 | **LSTM（长短期记忆网络）** |

**ResNet 的核心创新**：跳跃连接 (Skip Connection)——允许前层原始信息直接传到更深层，防止高频细节信息丢失，大幅提升训练效率。

**LSTM 为什么重要**：

```
AI 的侦察单位刚才看到了敌方部队，随后战争迷雾覆盖了该区域。
没有记忆的 AI：认为那里是安全的（危险！）
有记忆的 AI（LSTM）：记住"敌人可能还潜伏在那附近"，做出更谨慎的决策
```

**Step 5：训练策略**

**两阶段训练范式**：

```
阶段一：监督学习（模仿人类）
  · 用大量人类玩家历史对局数据作为"教材"
  · 最小化 AI 决策与人类玩家决策的 KL 散度
  · 快速建立基础认知，达到"优秀业余玩家"水平
  · 上限：不会超过训练数据的质量

阶段二：强化学习（自我进化）
  · 以阶段一模型为起点进行自我博弈
  · 通过多元化对手生态，避免陷入局部最优
```

**AlphaStar 的对手联盟（避免局部最优的关键）**：

```
主智能体的训练对手：
  · ~35%：与当前版本的自己对抗（快速迭代）
  · ~15%：与所有历史版本的自己对抗（防止遗忘过去策略）
  · ~50%：与两种特化的"利用体"(Exploiter) 对抗
      联盟利用体 (League Exploiters)：攻击整个联盟的普遍弱点
      主要利用体 (Main Exploiters)：专门针对主智能体的最新漏洞
```

类比：多元化的军事演习——"蓝军"专门研究"红军"弱点，迫使红军不断进化。

#### SL vs RL 的选择

**关键判断标准：奖励的稀疏性**

```
密集奖励 (Dense Rewards)：行为很快得到反馈 → 强化学习效果好
稀疏奖励 (Sparse Rewards)：行为与结果关联遥远 → 监督学习或传统方法更务实
```

**成本现实**：

| 系统 | 训练成本 |
|------|----------|
| AlphaStar | 据称约 2.5 亿美元 |
| GPT-3 单次训练 | 数千万美元 |

> [!note] 来自《帝国时代 IV》的实践智慧
> **混合 AI 架构**才是务实之选：
> - 宏观战略层 → **神经网络**（从复杂局面提取特征，做出策略性决策）
> - 微观执行层 → **行为树 / FSM**（逻辑清晰、稳定可控、易于策划配置）
> - 点缀优化 → 在传统框架内嵌入小型专用神经网络（成本极低，提升行为人性化）

### 游戏 AI 的未来展望

**机器学习的革命性价值**：将游戏 AI 从"被设计好的脚本执行者"转变为"能够自主学习的智能体"，能够产生**涌现行为 (Emergent Behavior)**——发现超越设计师认知的全新策略。

**目标**：构建一个像现实世界一样充满无限可能的、可信的虚拟世界，让玩家每次都能遇到行为不重复、仿佛在"独立思考"的 NPC。

**硬件趋势**：目前游戏内 AI 推理主要在 CPU 上运行。随着 GPU Tensor Core 和移动端 NPU 的普及，AI 加速将变得更唾手可得，这是工程选择 (Engineering Decision) 而非技术瓶颈。
