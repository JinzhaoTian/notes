渲染架构演进本质上是不断解决 CPU 与 GPU 协同效率、渲染复杂度管理和内存带宽与容量矛盾的历史。

## 变迁历史

### 固定管线模式

约2000年前后

1. **架构特征**：
	- 图形API仍是固定功能管线（DirectX 7/8，OpenGL 1.x）。
	- 引擎仅做薄封装，将 `SetRenderState`、`DrawPrimitive` 等调用组织成更易用的材质、网格对象。
	- 渲染流程在代码里是顺序的、线性的，没有复杂多Pass管理。

2. **变革驱动力**：
	- 硬件只能做固定顶点光照、单纹理等，渲染逻辑简单，薄封装已足够。
	- 可编程着色器尚未普及，没有处理大量独立着色器变体的需求。

### 即时渲染模式

Immediate Mode，可编程管线前期至 DX11 时代。这里“即时渲染”不是OpenGL 1.0的`glBegin`/`glEnd`，而是指**引擎按代码逻辑，直接、顺序地向图形驱动提交渲染命令，立即执行**的模式。

1. **架构特征**：
	- 基于状态机（DX9/11，OpenGL）。每一帧代码串行设置着色器、纹理、混合状态，然后Draw，驱动在后台隐式管理资源同步。
	- 材质系统、多Pass光照（如前向渲染多遍光）通过硬编码或简单循环组织。
	- 资源绑定和状态切换散落在渲染逻辑各处，容易产生冗余状态切换。

2. **遇到的瓶颈与革新原因**：
	- **CPU 单线程瓶颈**：所有 Draw 调用必须由单一线程串行提交，而多核 CPU 已普及，驱动层的隐式锁争用进一步降低效率。
	- **驱动开销爆炸**：状态验证、资源转换、隐式屏障完全由驱动猜测执行，Draw Call 数量一旦上千就容易 CPU bound。
	- **多 Pass 管理混乱**：延迟渲染兴起后，G-Buffer、光照、后处理等十余个 Pass，纹理间依赖、状态切换全靠程序员人为保证，极易出错且难以维护。
	- **无法充分利用硬件**：移动端 Tile-Based GPU（如 PowerVR、Mali）需要明确知道 Render Target 的 Load/Store 操作才能避免反复读回主存；而桌面端 GPU 拥有异步计算、拷贝队列，却被隐式同步白白浪费。

这些痛点最终催生了新一代**显式图形API**（DX12、Vulkan、Metal），并带来了 Render Pass 与图形命令缓冲的强制显式化。

### Render Pass 模式

显式帧结构，随 Vulkan/Metal/DX12 诞生

1. **架构特征**：
	- **Render Pass 对象成为一等公民**：引擎必须预先声明该Pass涉及哪些附件（颜色、深度）、附件的加载/存储动作（Load/Clear/DontCare/Store），以及子通道（Subpass）之间的依赖关系。
	- 渲染命令被录制到命令列表，而非直接提交，允许多线程并行构建命令。
	- 资源状态转换（如 Shader Resource → Render Target）由应用显式插入屏障。

2. **解决了什么**：
	- **移动GPU性能质变**：Render Pass 的 Load/Store 语义让 Tile-Based GPU 可以把中间结果完全留在片上缓存，避免带宽浪费，功耗和性能收益巨大。
	- **多线程命令录制**：可在不同线程独立录制不同Render Pass的命令，再串行提交，极大解放CPU。
	- **资源过渡精确可控**：不再依赖驱动猜测，减少了不必要的流水线停顿。

3. **还未解决的问题**：
	- 虽然单个 Pass 内已标准化，但**整个帧几十个 Pass 之间的资源生命周期、屏障插入、显存复用**仍然要靠手动管理，错误频发且难以全局优化。
	- 随着渲染技术爆发（实时反射、阴影级联、SSAO、TAA、各种后处理、Ray Tracing），帧结构变得极其复杂，纯手工“连线”已成为不可能的维护任务。

### Render Graph 模式

图驱动的帧生成，现代标杆

1. **架构特征**：
	- 整帧的渲染被抽象为一个**有向无环图（DAG）**，节点是渲染 Pass，边是资源（纹理、Buffer）的读写依赖。
	- 引擎先声明所有 Pass 及输入输出资源，形成一个“惰性构建”的图，再编译、优化，最后执行。
	- 代表：Frostbite 的 Frame Graph、虚幻引擎的 RDG（Render Dependency Graph）、Unity 的 Render Graph。

2. **核心革新原因**：
	- **自动化资源生命周期与内存别名**：图分析可算出每个临时资源的有效区间，自动分配、复用显存块，使高峰显存用量下降30-50%。
	- **自动屏障与状态转换**：根据依赖边推导所有必要的硬件屏障和资源布局转换，插入最优位置并合并，彻底杜绝手动错误。
	- **无痛并行化**：图可以轻松识别没有依赖的Pass，将其命令录制作业分发到多线程并行完成。
	- **动态Pass裁剪**：若某个Pass的输出最终不被画面引用，可直接剪除。比如某个阴影级联完全在视锥之外，可直接跳过。
	- **异步计算融合**：在图中标出可在计算队列异步执行的Pass，系统自动插入跨队列同步，让图形和计算重叠。


## 先进渲染架构深度解析

当前和下一代的先进渲染架构，都是以 Render Graph 为中枢，融合 **GPU 驱动渲染**、**异步计算**、**光线追踪**和**流式加载**的复合系统。

#### 1. 声明式、延迟执行与图编译优化

- 用户代码并不直接执行绘制，而是声明Pass（输入输出、参数、渲染委托），系统在所有声明结束后，得到一个不可变的完整图。
- 编译阶段进行：
    - **生命周期分析**：给每个资源标注 FirstUse / LastUse，规划内存池分配。
    - **Pass合并/重排**：在满足依赖的前提下调整执行顺序，最大化纹理缓存局部性。
    - **屏障合并与降级**：例如连续两个计算Pass，中间的 UAV 屏障可合并成一个；若 Pass 只读，则无需任何屏障。
- 执行阶段才真正分配暂存内存、录制命令列表并提交。

#### 2. 暂存资源系统与大容量内存别名

先进架构把所有仅在帧内有效的中间纹理（如 GBuffer、阴影贴图、模糊中间结果）视为**暂存资源**，不做实际显存分配，只做“虚拟声明”。编译后，一块物理内存会在不同时间片被不同格式、大小的资源复用，只有在需要导出到下一帧或外部时，才做物理备份。这使得4K分辨率下大量全屏 Pass 的显存开销降到最低。

#### 3. 异步计算与多队列深度集成

现代图形队列（Graphics）和计算队列（Compute/Async）可以并行工作。高级 Render Graph 支持：
- 标记某些 Pass 为 `AsyncCompute`，并明确指出其与图形队列的同步点。
- 系统自动在图中插入跨队列信号量/栅栏，使光照、后处理、GPU 粒子、剔除等密集计算与下一批图形 Pass 重叠运行，显著缩短帧时间。

#### 4. GPU驱动渲染与图形工作图（GPU Work Graph）

为彻底消除 CPU 提交瓶颈，架构将**裁剪、剔除、绘制间址生成**等决策全交给 GPU：
- 利用 Compute Shader 进行视锥剔除、遮挡剔除，生成间接绘制缓冲区。
- 最新一步是 **GPU Work Graph**（DX12 Ultimate / Vulkan Device Generated Commands），允许 GPU 侧自行根据计算结果动态产生新的渲染任务，CPU 只提供一个入口节点。
- 引擎的 Render Graph 也需相应扩展，支持描述此类“GPU生成的子图”，并正确表达其与 CPU 侧资源依赖，目前仍在标准化早期。

#### 5. 光线追踪的无缝集成

光追调用（Ray Tracing Pass）被融入 Render Graph 中，作为需要加速结构（TLAS/BLAS）的特殊 Pass：
- 图跟踪加速结构的更新依赖，如果场景没变化，自动跳过 BLAS 重建。
- 光追结果通常写成 Texture 节点，后续的降噪、合成 Pass 就在同一图内获得该依赖，从而自动插入状态转换和屏障。

#### 6. 面向数据与ECS的架构趋同

渲染架构进一步与实体组件系统（ECS）融合，场景图、材质参数、变换信息直接以结构化 Buffer形式送入 GPU，CPU 端只处理高层次图构建与提交，减少数据拷贝与状态验证。这种**数据通路**与  **Render Graph 的依赖描述**相结合，使得未来帧的整体生成逻辑高度声明化和自动化。
