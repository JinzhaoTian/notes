## 5 个基础概念（文章默认你已了解）

不懂这 5 个，后面会一直卡：

**① Prefill（预填充）和 Decode（解码）** 大模型生成是“一个字一个字往外蹦”的。分两步：先把你的整段输入一次性读进去、算出缓存（Prefill），再一个 token 一个 token 往外生成（Decode）。 Prefill 是**算力密集**（矩阵大、并行度高），Decode 是**内存带宽密集**（每步只算一个 token，但要反复读整个模型的权重和缓存）。两者脾气完全不同，这是后面 P/D 分离的根因。

**② KV Cache** Transformer 每生成一个新 token，都要“回看”前面所有 token。如果每次重算，代价是平方级的。所以把前面算过的 Key/Value 存起来复用，这就是 KV Cache。 它的问题：**很占显存**，而且**存在哪、能不能复用**，直接决定了后面要不要“搬家”（迁移）。

**③ Batch（批）与 Continuous Batching（连续批处理）** GPU 一次算一条请求太浪费，于是把多条请求拼成一批一起算。传统 batch 要等整批做完才收新请求；continuous batching 是**每生成一个 token 就重新组一次批**，谁算完谁走、新请求随时插进来。

**④ TP、EP、MoE、Worker、副本**

- **TP（张量并行）**：一个模型层切到多张卡上算，每层都要通信（AllReduce），所以对网络延迟极敏感；
- **EP（专家并行）/ MoE**：混合专家模型里，不同“专家”放在不同卡上，请求要按需路由到对应专家（All-to-All 通信）；
- **Worker / 副本**：一个跑着模型的推理实例（通常占一张或多张 GPU），同一模型可以有多个副本。

**⑤ TTFT、TPOT、P99**

- **TTFT**：首字延迟，从发请求到看见第一个字；
- **TPOT**：之后每个 token 的间隔；
- **P99**：99% 的请求都快于这个值——看尾延迟，平均值会骗人。

## 00｜不是一个组件决定路径，而是一串决策共同决定路径

**这节在说什么**：别问“谁调度”，先问“你说的是哪条路径”。

作者把“路径”拆成四类，这是全文的骨架：

|路径|含义|主要决定者|
|---|---|---|
|用户入口路径|请求怎么进来、能不能进|推理网关|
|计算路径|落到哪个模型副本、哪个 Prefill/Decode 节点、哪组 GPU|Router + Scheduler|
|缓存路径|KV Cache 在哪、命中还是迁移|Router + Scheduler + KV 管理|
|网络数据路径|数据包实际怎么走、堵不堵|网络（ECMP/ECN/PFC）|

为什么要这么拆？因为**同一个词在不同层含义不同**。你只盯着 HTTP 入口看，会以为“网关转发成功 = 路径正确”；其实真正的成本发生在后面三层。

**五个角色，一句话分工**：

- 网关：**能不能进、进哪个门**；
- Router：**往哪个方向送**；
- Scheduler：**什么时候算、和谁一起算**；
- KV Cache：**隐藏的搬家成本**；
- 网络：**只负责送，并在堵的时候反馈**（ECN/CNP/PFC）。

> 一句话记住：**路径不是一条线，是一叠决策。**

## 01｜推理网关：决定“资格”，不决定“位置”

**这节在说什么**：网关很重要，但别高估它。

**它干的活，逐条翻译**：

- **鉴权**：你是不是合法用户；
- **租户识别**：你属于哪个客户/业务线（多租户平台要分开算账、分开限流）；
- **模型 API 暴露**：对外只暴露 `chat/completions` 这类统一接口，背后有多少模型你不用管；
- **协议转换**：把各家 SDK 的请求统一成内部格式（典型是 OpenAI-compatible）；
- **限流**：你这个租户每秒最多多少请求/token；
- **熔断**：后端挂了就快速失败，别把请求堆死；
- **请求大小检查**：上下文超长直接拒掉，避免打爆显存；
- **SLA 分级**：这个请求是“金卡”还是“普通”，决定排队优先级；
- **灰度发布**：新模型先放 1% 流量；
- **入口负载均衡**：把请求分到多个网关实例/服务入口。

**关键区分**：网关是**控制面入口**，它关心“合法性、入口压力、服务治理”，**不掌握 GPU 的实时状态**（排了多长、KV 还剩多少）。

作者用**收费站**打比方：能决定你能不能上高速、从哪个口上，但决定不了你走哪条车道、在哪堵。

> 一句话记住：**转发成功，只说明它进来了，不说明它走得对。**

## 02｜Router：第一道“关键选择器”

**这节在说什么**：Router 从“负载均衡器”进化成了“懂推理状态的路由器”。

**它要回答的问题**：这个请求发给哪个后端？哪个模型副本？哪个 Worker？哪个 Prefill 实例？哪个 Decode 实例？**哪个副本的 KV 命中概率更高？**

**普通负载均衡 vs KV-aware routing**：

- 传统 L4/L7 负载均衡：轮询、最少连接、一致性哈希——它只看“连接数/请求数”；
- **KV-aware routing**：还要看“这个请求的前缀，在哪个副本的 KV Cache 里已经算过”。

为什么重要？如果两个请求有相同的系统提示词（比如一大段人设/工具说明），打到同一个副本就能**直接复用已算好的 KV**，TTFT 大幅下降；随机打散等于让每个副本都重算一遍。

作者提到 **NVIDIA Dynamo 的 Router** 明确要求“动态发现”：Router 得持续跟踪 worker 实例和 KV cache 状态，否则它看到的是过期地图。

**Router 一旦有拓扑意识，影响的不只是延迟**：

- KV 是否命中；
- Prefill 和 Decode 是否就近；
- 是否跨 Rack（机架）；
- 是否制造 KV 迁移流量；
- 是否造成 **Incast**（多打一，很多请求同时拉同一个 KV Owner）；
- 是否让某条 **RoCE Rail** 变热（GPU 集群里每张卡常配一张网卡走固定“轨道”，跨轨道要绕）。

**它的局限（作者特意强调）**：

- 只看得到“候选后端”，看不到后端内部每个 iteration 的 batch 细节；
- 算不准这个请求会在 Scheduler 里排多久；
- 控制不了底层 NCCL、RDMA、ECMP 最终怎么走。

> 一句话记住：**Router 决定“方向”，但它不是全能。**

## 03｜Scheduler：决定“时机”，还会“制造网络流量”

**这节在说什么**：Scheduler 这个词最容易混，先分清两类。

**第一类：集群级 Scheduler** 决定请求/任务分配给哪个实例组、哪个节点、哪个资源池。典型是 K8s 调度器（配 Volcano、Kueue 等）。它管**资源分配**，分钟级。

**第二类：引擎内部 Scheduler** 请求已经进了某个推理引擎，它决定：什么时候进 Prefill、什么时候进 Decode、怎么组 batch、怎么分配 KV block、怎么控制 token budget。典型是 vLLM / SGLang / TensorRT-LLM 内部的调度器。**对尾延迟影响最大的是这一类。**

**两个具体机制**：

- **vLLM 的 prefix caching**：scheduler 会调 **KV cache manager** 查“这段前缀算过没有”，命中就跳过计算，并分配 slot（槽位）。所以调度和 KV 分配是**紧耦合**的；
- **TensorRT-LLM**：把 **In-flight Batching**（就是连续批处理）、**Chunked Prefill**（长输入切块，和 decode 交错跑，避免一个长请求把所有人拖慢）、KV Cache、Scheduler 放在一起讨论。说明现代引擎的调度器不只是“排队”，而是在**持续调配 prefill/decode 之间的资源**。

**为什么它会影响网络（全文最精彩的一段）**： Scheduler 决定了——

- 哪些请求在**同一时间窗口**被放出来；
- 哪些请求被组进**同一个 batch**；
- 哪些请求**同时**进 Prefill / 同时进 Decode；
- 哪些请求**同时**访问 KV Cache；
- 哪些 GPU **需要同步**（触发 NCCL 集合通信）。

后果：

- 一瞬间放出一批请求 → **microburst**（微突发，毫秒级流量尖峰）；
- 一批请求同时拉同一个 KV Owner → **Incast**；
- TP/EP 组跨节点 → 触发 **NCCL/RDMA** 通信；
- 一个慢请求卡住 → 拖累整个 batch 的后续。

> 一句话记住：**Scheduler 决定的不是“从哪进来”，而是“什么时候、以什么形态变成后端通信”。**

## 04｜P/D 分离后，路径决策变得更复杂

**这节在说什么**：一旦 Prefill 和 Decode 拆到不同节点，路径从“一条”变成“两段 + 一次搬家”。

**为什么要分离**：前面说过，Prefill 吃算力、Decode 吃带宽，混在一起会互相干扰（长 prompt 的 prefill 一跑，所有 decode 的 TPOT 都抖）。拆开后各自优化，吞吐更高。

**代价是路径变长**：

代码块

```
请求 → Prefill 节点 A（算 KV）
      → KV Cache 从 A 迁到 B
      → Decode 节点 B（逐 token 生成）
```

如果 B 是 **TP 组**，B 不是一张卡而是一组卡；如果带 **MoE/EP**，还要再经过 expert 节点。

作者引 **NVIDIA Dynamo 的 disaggregated serving**：高性能解耦的关键是**高效 KV 传输**，KV 可以直接从 prefill 引擎的显存传到 decode 引擎的显存（VRAM→VRAM）。

**核心洞察**：

- **KV 传输不再是边角问题，它就是主路径的一部分**；
- **“算力路径”和“缓存路径”被拆开了**：算力在 A，缓存要追到 B；
- 如果 Router 只看“哪个 Decode 空闲”，不看 **KV locality**（KV 在哪），就会出现：请求进得很顺、后端也有空闲 Decode，但 **KV 在远处**，于是每一步都在“还债”。

> 一句话记住：**P/D 分离不能只看 GPU 利用率，必须看 KV 的位置和迁移代价。**

## 05｜网络层：决定“怎么转发”，不决定“业务该去哪”

**这节在说什么**：给网络工程师划清边界——网络是执行者，不是决策者。

**网络确实决定的**：

- 走哪台 Leaf（接入交换机）、哪条上联；
- **ECMP** 哈希到哪条链路（等价多路径，按五元组哈希选路，哈希不均就会有的链路热、有的闲）；
- 拥塞时是否打 **ECN** 标记；
- 是否回 **CNP**；
- 是否触发 **PFC**。

**把这条拥塞反馈链讲清楚**（RoCE 网络的典型闭环）：

1. 交换机发现出口队列超过阈值 → 在数据包 IP 头打 **ECN** 标记；
2. 接收端看到标记 → 回一个 **CNP**（拥塞通知包）给发送端；
3. 发送端收到 CNP → 按 **DCQCN** 算法降速；
4. 如果还压不住，队列快满 → 交换机发 **PFC** 暂停帧，让上游“先别发”（逐跳反压）。

**网络不决定的**：这个请求该不该去 B、KV 该不该从 A 迁到 B、Decode 组该不该跨 Rack、Scheduler 该不该把这些请求一起放出来。**这些是上层的事。**

**NCCL 的角色**：AllReduce、AllGather、ReduceScatter、AlltoAll 这些**集合通信**，是 TP/EP 场景下后端执行时产生的通信模式。网络只是**承载**它们，不会替上层重新选副本或 KV 位置。

> 一句话记住：**网络能缓解错误流量形态带来的拥塞，但不能替 Router 和 Scheduler 做业务决策。**

## 06｜一个慢请求，可能是这样被“共同制造”出来的

**这节在说什么**：用一个完整故事，把前面所有概念串起来。这是全文的“案例复盘”，建议重点看。

故事线：

1. **网关**：鉴权、限流、租户识别都过了，放行——没问题；
2. **Router**：看到一个远端 Decode 比较空闲，但**没考虑 KV locality 和跨 Rack 成本**，把请求打过去了——问题埋下；
3. **KV 迁移**：Prefill 在近端做完，KV 要跨 Rack 迁到远端 Decode——**多了一笔本可避免的流量**；
4. **Scheduler**：远端 Decode 上还有一批请求，为了提高吞吐，把多个请求组进同一个时间窗口，它们**同时**要 KV——**Incast 出现**；
5. **网络**：交换机出口队列抬升 → ECN 标记增加 → CNP 返回 → 发送端降速 → 压力继续就触发 PFC，**同优先级的其他流也被殃及**；
6. **用户**：TTFT 变长、TPOT 抖动、P99 上升。

**最精彩的是“五方各说各话”**：

- 网关：我放行很快；
- Router：我选的是空闲节点；
- Scheduler：我在提高 batch 效率；
- 网络：我只是看到队列起来了；
- 业务：用户慢了。

**每个人都没完全错，但系统整体错了。** 这就是推理系统最难排障的地方：**局部合理，全局错误**。

> 一句话记住：**慢请求往往不是单点故障，而是多个“局部最优”叠成了“全局最差”。**

## 07｜真正要观测的，不是“组件是否正常”，而是“决策是否对齐”

**这节在说什么**：排障思路要从“看组件健康”升级到“看路径证据链”。

传统排障问：网关正常吗？Router 正常吗？Scheduler 正常吗？网络正常吗？——**这些问题太粗**，因为每个组件都可以“正常”，但组合起来是错的。

要问的是：**它们的决策有没有对齐？**

- 网关认为这是高优先级请求；
- Router 却把它发到远端低成本候选；
- Scheduler 为了吞吐把它排进大 batch；
- KV 在另一个 Rack；
- 网络那条 Rail 刚好已经热了。

**要打通的字段（路径证据链）**，我按用途分组：

|类别|字段|为什么需要|
|---|---|---|
|身份|Request ID、Tenant、Model|把所有日志串成一条|
|入口|Gateway ingress time|排队从哪开始|
|路由|Router decision、candidate list|它为什么选这个、备选是谁|
|执行|Chosen Prefill/Decode、Scheduler queue time、Prefill start/end、Decode step latency|时间花在哪一段|
|缓存|KV Owner、是否 hit、是否 fallback|有没有“搬家”|
|网络|TP/EP group、NIC/Rail、ECN/CNP/PFC|堵在哪、和谁同时|
|结果|TTFT、TPOT、P99|用户实际感受|

如果这些打不通，你只能看到碎片：一个慢请求、一个高队列、一个 CNP 增加、一个远端节点……**但你不知道它们是不是同一件事**。

> 一句话记住：**推理排障的核心，不是证明某个组件坏了，而是证明一条路径为什么变贵了。**

## 08｜到底谁真正决定路径？——分层回答

**这节在说什么**：给出最终答案，而且答案是“分情况”的。

|你问的路径|主要决定者|
|---|---|
|用户入口路径|**Gateway**：能不能进、进哪个 API 服务、走哪个入口策略|
|后端实例路径|**Router**：哪组 Worker、哪个副本、哪个 Prefill/Decode 候选|
|执行时间路径|**Scheduler**：什么时候算、和谁算、等不等 KV block、进哪个 batch|
|数据面网络路径|**网络**：按目的地址、ECMP、队列状态转发与反馈|

但如果你问的是“**用户最终体验到的那条完整路径**”——**都决定了一部分**。

作者的关键判断：**最关键的是“最早把请求绑定到具体计算位置和 KV 位置的那一层”**。在 P/D 分离系统里，这个角色往往是 **Router + 上层 Scheduler 的组合**。

**为什么“最早”这么重要？** 因为路径有**锁定效应**：一旦请求被绑定到远端 Decode，后面的 KV 迁移、跨 Rack 流量、队列争抢就都成了“既定成本”，Scheduler 和网络只能在既定框架里补救。**越早的决策，越不可逆。**

最后五句总结：

> Gateway 决定入口，Router 决定方向，Scheduler 决定时机，KV Cache 决定迁移成本，网络决定承载代价。

> 一句话记住：**真正决定体验的，不是“谁转发了请求”，而是“谁把请求绑定到了具体的计算、缓存和网络代价上”。**

## 09｜对算力网工来说，最该盯什么？

**这节在说什么**：给网络工程师的行动清单——不用变成推理框架开发者，但要知道上层在制造什么流量。

四个盯点：

1. **请求有没有被打到远端 Decode？** 只看 IP 通不通不够，要看是否跨 Rack、跨 Pod、跨 Rail，是否偏离合理拓扑；
2. **KV Cache 有没有被迫长距离迁移？** 长上下文、多轮对话、P/D 分离场景尤其明显；
3. **Scheduler 有没有制造同一时间窗口的集中通信？** 同时 Prefill、同时拉 KV、同时 Decode，就是 Incast 和 microburst 的土壤；
4. **ECN/CNP/PFC 是不是和慢请求同一时间发生？** 它们不是孤立计数，必须和 Request ID、Router 决策、Scheduler queue time 对齐看。

**结论**：算力网工最该推动平台补的，不是“再多一张端口带宽图”，而是**路径级 Trace**。

> 一句话记住：**不只看“链路有没有满”，要看“上层把什么流量组织成了什么形状”。**

---

## 10｜路径不是画出来的，是一次次决策叠出来的

**这节在说什么**：收束全文，强调三个组件**不是同义词**。

- **Gateway**：入口秩序
- **Router**：后端方向
- **Scheduler**：执行时机
- **网络**：承载与反馈
- **KV Cache**：隐藏的路径成本
- **用户体验**：所有这些共同结算的结果

作者最后那句话是全篇的题眼：

> **真正昂贵的路径，往往不是入口转发多了一跳，而是计算位置、KV 位置和网络拓扑没有对齐。**

所以一个优秀的推理系统，不能只追求“能转发”、不能只追求“GPU 利用率高”、也不能只追求“每个组件单独健康”，而要追求：**请求、计算、缓存、调度、网络，在同一条低代价路径上对齐。**
